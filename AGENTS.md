# Постійні інструкції Courier Route

- Перед роботою прочитай `docs/assignment.txt`, `PROJECT_PLAN.md`, README, актуальний звіт блоку та наявні інструкції репозиторію. Розрізняй оригінальні вимоги викладача, погоджені проєктні рішення й фактичний стан реалізації.
- Виконуй лише поточний доручений блок і необхідні виправлення. Блоки 1–6 прийнято; явне наступне завдання дозволило тільки блок 7. Після блоку 7 зупинись перед блоком 8 до наступного завдання керівника проєкту; ця межа не забороняє наступний блок, якщо користувач явно його доручив.
- Зберігай погоджений стек: TypeScript strict, Node.js 24.x LTS і npm 11.x, Express, HTML/CSS/TypeScript і Vite, PostgreSQL/`pg`, `worker_threads`; надалі Traefik, Docker/Kubernetes/HPA/Metrics Server. Один npm-проєкт із `src/server`, `src/client`, `src/shared`; без зайвих workspaces і мікросервісів.
- Не додавай сторонні функції, UI-фреймворки, фальшиві маршрути, демонстраційні задачі, удаваний прогрес чи штучні затримки. Працюй з умовними координатами та евклідовою довжиною; наближений пошук не означає доведену глобальну оптимальність.
- Блок 2 прийнято після перегляду коду та доступних повторних перевірок керівника: він повторив 11 unit, але не 13 PostgreSQL integration-сценаріїв через відсутність придатної БД. Успішне виконання цих 13 тестів підтверджує звіт виконавця, а не незалежний запуск керівника. Відкрита браузерна перевірка не дорівнює успішному візуальному прийманню.
- Блок 3 прийнято: керівник незалежно повторив typecheck/build, 47 non-DB тестів (11 unit + 36 route/HTTP), TS/built CLI й benchmark 500/200 млн; алгоритм тривав у нього приблизно 21,48 с, best length збіглася. 13 PostgreSQL-тестів підтверджено звітом виконавця; керівник їх не повторив. На момент приймання блоку 3 браузерна перевірка була відкрита; поточний UI перевірено у блоці 5. Історичний `docs/block-03-report.md` не переписуй.
- Блок 4 прийнято: PostgreSQL jobs, queued/claim, API власника, збережений прогрес/історія/cancel та атомарні active/outstanding-ліміти. Виконавець пройшов 87 тестів; керівник незалежно повторив 50 non-DB (11 unit + 36 route/HTTP + 3 jobs config), typecheck/build, TS/built CLI та production HTTP. 37 PG-сценаріїв (13 auth + 24 jobs) він не повторював через відсутність придатної БД/TEST_DATABASE_URL; їх підтверджує звіт виконавця. Історичний `docs/block-04-report.md` не переписуй.
- Блок 5 прийнято керівником: українська форма маршруту, active/history, керований polling, cancel, runtime-перевірка відповідей та SVG збереженого completed. Typecheck/build, 124 тести та 14 груп реального Chrome production/dev пройшли; desktop/360 px скриншоти оглянуто. Керівник повторив npm ci, typecheck/build, 87 non-DB, CLI й HTTP; 37 PG, 14 Chrome та огляд PNG підтверджені виконавцем, керівник їх не повторював через відсутність PostgreSQL/Chrome і PNG не оглядав. Історичний `docs/block-05-report.md` не переписуй. Vite proxy має відповідати тільки `^/api(?:/|$)`, щоб не перехоплювати `/api.ts`. Ліміти UI надходять із API; невизначений POST не повторюй, спочатку читай історію. Покоління сеансу/вибору та abort мають захищати всі старі запити; logout/401 очищують приватний стан і чернетку без cancel прийнятої job. SVG використовує збережений вхід, рівний масштаб X/Y та індекси 0→1..N→0; 100% лише completed. Реєстр і ETA додано в блоці 6; HTTPS/Traefik — блок 7. HPA й адмінпанель не реалізовуй наперед.
- Блок 6 прийнято: міграція 003, реєстр живих виконавців/одного слота, bounded heartbeat/TTL, coherent queued snapshot, min-heap ETA й UI. Typecheck/build, 156 тестів (49 справжніх PG) і 16 Chrome production/dev груп пройшли, PNG оглянуто; факти й прогноз/очікування у `docs/block-06-report.md`. Керівник незалежно повторив npm ci/typecheck/build, 107 non-DB (11 unit + 36 route/HTTP + 3 jobs config + 43 client + 14 queue config/estimator/read-budget), TS/built CLI та production/dev HTTP. Перевірив ZIP із 111 файлами на f6c528f5b4b1602a201027bf015f83fd9e53a238 і 25 захищених файлів. 49 PG (13 auth + 24 jobs + 12 queue), 16 Chrome і PNG підтверджені виконавцем; керівник їх не повторював і PNG не оглядав. Історичний звіт 6 не переписуй. Міграцію 003 після застосування не редагуй. Freshness визначає DB-час; paused/stopping/expired виключені, busy звіряється з running. TTL не замінює lost_after. Після commit claim не додавай серійних DB-очікувань, що споживають чинний 21000 мс резерв. Detail GET має спільний 8-секундний бюджет перед auth; metadata тільки queued, SQL-збій — 503, stale ETA позначена явно. Модель приблизна, не countdown/обіцянка старту, власна тривалість цільової не входить до wait. Не реалізовуй блоки 8–10 наперед.
- PostgreSQL є джерелом усіх читань/скасувань задач; admission синхронізуй коротким advisory transaction lock, claim — row lock/SKIP LOCKED. Не запускай worker до commit й не звільняй claim-резервацію до узгодження terminal у БД. Усі progress/terminal UPDATE обмежуй id/running/claim token; token приватний. Прийнятий у running запит cancel має пріоритет при звичайній фіналізації. Завершення worker при shutdown — failed/server_shutdown, інфраструктурна втрата контролю — окрема причина; не називай їх добровільним cancel. Втрачені running після збереженого timeout/deadline/grace завершуй failed/worker_lost без автоматичного повтору.
- Фактичний recovery grace враховує configured minimum, два polling-інтервали та 21000 мс на bounded claim/progress/terminal DB-операції; default 21500 мс. При зміні DB-таймаутів узгоджуй цей резерв. Це не збільшує timeout самого worker. Не повертай затриману фіналізацію на звичайний polling і не запускай безмежні негайні повтори SQL після помилки.
- Один спільний executor на HTTP-процес виконує щонайбільше один worker; busy встановлюється синхронно, прихованої локальної черги немає. Матриця/початковий маршрут/пошук працюють у worker; обмежений вхід перевіряється до його створення й копіювання надмірних структур. Worker отримує лише вхід/runId з порожніми `env`/`execArgv`, без DB URL, паролів і cookie; route CLI не залежить від PostgreSQL.
- Прогрес має відображати фактичні ітерації; 100 можливе лише за перевіреного completed після завершення потоку. Timeout/cancel реально зупиняють worker, а слот звільняється після фактичної зупинки; timeout — `failed/timeout`, скасування — `cancelled`. Shutdown HTTP включає executor. Перевіряй TS/built, повторний запуск після кінцевих станів і справжній HTTP під час pending пошуку в worker того самого процесу. Це не замінює двох серверів за балансувальником.
- Інтерфейс та інструкції користувача пиши українською, внутрішні ідентифікатори коду — англійською. Зберігай сторонні файли та зміни користувача, не виводь секрети.
- Виконуй доречні перевірки та виправляй виявлені помилки. HTTP-перевірку не називай візуальною. Не вигадуй успішних результатів: блокування і неперевірене явно фіксуй. Після перевірок зупиняй непотрібні тимчасові процеси.
- Актуалізуй `PROJECT_PLAN.md` і звіт відповідного блоку. Продуктову вимогу не позначай реалізованою лише тому, що її архітектуру описано. Функції наступних блоків не реалізовуй наперед.
- Використовуй справжній PostgreSQL і окрему роль застосунку без superuser-прав. Підготовка локального кластера проєкту не повинна змінювати чужі кластери; слухай лише loopback. Міграції запускай явно, новими версіями; не змінюй уже застосований SQL та не очищуй робочу БД.
- Інтеграційні тести запускай лише з явним `TEST_DATABASE_URL` на окремій БД із тестовим ім'ям; до очищення перевір фактичні host/port/database проти робочого підключення. Відсутня БД — заблокована перевірка, а не пропущений успіх. Моки не доводять спільність сесій; потрібні два незалежні HTTP-процеси.
- Не виводь PostgreSQL URL з паролем, вміст `.env`, паролі, їхні хеші, токени/cookie чи повні auth-тіла в чат, звіт, логи або історію shell. Пароль локальної ролі PostgreSQL зберігай тільки в ігнорованому `.env` з обмеженими правами. Тимчасові auth-тіла та cookie для ручних перевірок зберігай лише в ігнорованих файлах і видаляй після перевірки. PostgreSQL керується окремо; після перевірок зазнач, чи залишено його запущеним, і точні команди керування.

- Блок 7 завершено виконавцем: 168 тестів (49 PG), 8 container, 10 deployment/fault і 9 HTTPS Chrome груп пройшли, 7 PNG оглянуто; факти у docs/block-07-report.md. Незалежного приймання керівника для блоку 7 ще немає. Production image nonroot Node 24.18.0/npm 11.16.0; HOST loopback за замовчуванням і 0.0.0.0 у контейнері. X-Instance-Id завжди UUID фактичного handler. Власні Colima profile/kind courier-route; kubeconfig тільки .local/deploy/kubeconfig, context kind-courier-route та явний namespace для kubectl. Дві однакові app replicas за namespace-scoped Traefik без affinity/retry POST; TLS завершується на Traefik, усередині HTTP/PostgreSQL TCP. Окремий PG 18/PVC, nonsuper role та явний compiled migration Job до rollout; паролі/CA/PVC/успішний Job повторно використовуються. Stop чекає app shutdown до зупинки PG, даних не видаляє. Fault-тести лише у випадковому власному test namespace після перевірки labels/owner/container/node; cleanup видаляє тільки його disposable PVC. CA/key/Secret/kubeconfig/profile/PNG не комітити. Browser SPKI-виняток — лише конкретний попередньо перевірений leaf у власному тимчасовому Chrome; це не довіра звичайного профілю. HPA/Metrics Server/адмінпанелі немає.

## Git і змістовні коміти

Ця організаційна вимога користувача діє для блоку 1 та всіх наступних блоків і виправлень. Вона не є додатковим пунктом завдання викладача чи користувацькою функцією застосунку.

1. Локальний Git-репозиторій цього проєкту вже створено в корені з основною гілкою main. Перед роботою перевір фактичний Git-корінь, гілку, status та історію; працюй у наявному репозиторії й не переініціалізовуй його. Лише якщо власного репозиторію немає, після перевірки кореня створи його через git init -b main, не утворюючи випадково вкладеного репозиторію.

2. Перевір наявні user.name і user.email та використовуй справжню налаштовану Git-ідентичність. Не вигадуй ім'я чи email, не підставляй дані асистента та не змінюй глобальні налаштування. Якщо ідентичності немає, виконай незалежну частину роботи й повідом, які саме значення потрібні для комітів. Не заявляй про створений коміт, якщо Git його не створив. Для блоків 1–2 достатньо локального репозиторію; віддалений сервіс і push без окремого завдання не налаштовуй.

3. Коміть регулярно за змістом роботи: після завершеної самостійної частини функціональності, суттєвого виправлення, узгодженої зміни структури або завершеного оновлення документації. Один коміт має містити один логічно завершений набір пов'язаних змін. Не накопичуй усі майбутні блоки в одному коміті та не роби коміт після кожного дрібного редагування. Кількість комітів визначається реальною роботою.

4. Перед комітом переглянь git status, звичайний і підготовлений diff та виконай перевірки, доречні для цих змін. Для коду це npm run typecheck, npm run build та перевірки зміненої поведінки; у блоці 2 обов'язкові змістовні unit/integration перевірки БД та авторизації на справжній окремій тестовій БД. Окремий коміт тільки з документацією не вимагає повторного запуску незмінного коду. Форматувальні перевірки не повинні змінювати дослівний оригінал docs/assignment.txt. Не коміть код із відомими невиправленими помилками перевірок; блокування середовищем явно зазначай як частковий/заблокований результат, не видавай за успіх.

5. Використовуй короткі конкретні назви англійською у форматі type(scope): description; scope можна опустити, якщо зміна загальна. Орієнтир — до 72 символів у заголовку. Типи:

   - feat — нова функціональність;
   - fix — виправлення помилки;
   - refactor — зміна структури без зміни поведінки;
   - test — змістовні тести;
   - docs — документація;
   - chore — технічне налаштування;
   - build або ci — збирання чи автоматизація перевірок.

   Приклади адекватних назв:

   - docs: define project requirements and implementation plan
   - chore: configure TypeScript and project scripts
   - feat(server): add health endpoint
   - feat(client): show backend availability
   - fix(server): correct production asset paths
   - docs: record block 1 verification results

   Це приклади формулювань, а не вимога створити саме стільки комітів чи розбивати взаємозалежний каркас на неробочі частини. Назва повинна точно відповідати фактичному diff. Не використовуй беззмістовні назви на кшталт update, changes, fix stuff, final або done.

6. Підготуй .gitignore до першого коміту й доповнюй перед створенням локальних даних. Не включай node_modules, dist, тимчасові логи, локальні .env, секрети, PostgreSQL-кластери й файли БД, cookie-файли та дампи. package-lock.json, безпечний .env.example, SQL-міграції й тести мають відстежуватися. Вибірково додавай файли поточного завдання та перевіряй підготовлений diff, щоб не включити сторонні зміни користувача.

7. Зберігай історію роботи: не переписуй уже створені коміти й не відкидай сторонні зміни заради чистого статусу. Якщо після коміту виявлена окрема помилка, виправ її, перевір і створи новий fix-коміт.

8. Наприкінці роботи наведи у відповіді список створених за це завдання комітів з короткими хешами та назвами, активну гілку й остаточний git status --short. Якщо залишилися зміни, поясни кожну групу; власні завершені зміни мають бути закомічені. Сторонні зміни зберігай.

9. Обов'язково запиши ці правила у Git-розділ AGENTS.md. У PROJECT_PLAN.md познач їх як постійний процес для всіх блоків. У README.md коротко опиши створений репозиторій, основну гілку та формат назв комітів.
