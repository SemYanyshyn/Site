ВИКОНАЙ БЛОК 1 ПРОЄКТУ COURIER ROUTE

Ти реалізуєш навчальний вебпроєкт у відкритій папці VS Code. Код і команди виконуєш самостійно в межах доступного середовища. Потрібно завершити лише блок 1: уточнена постановка, перевірка середовища, створення Git-репозиторію, документація та працездатний мінімальний каркас. Під час роботи роби змістовні коміти після завершених логічних змін.

МЕТА ВСЬОГО ПРОЄКТУ

Вебзастосунок розраховує короткий маршрут одного кур'єра через задані точки на координатній площині. Кур'єр починає зі складу, відвідує кожну точку доставки та повертається на склад. Результат: порядок відвідування, сумарна евклідова довжина та схема маршруту. Координати умовні; одиниці довжини умовні, не кілометри.

Обрано ітеративний наближений пошук: показуємо найкращий знайдений маршрут, не заявляємо про доведену глобальну оптимальність. Обчислення мають бути реальними. Кількість точок і обмежений обсяг пошуку забезпечують різну трудомісткість; штучні затримки для імітації роботи заборонені.

Обов'язково реалізувати всі пункти 1–8 оригінального завдання та HTTPS. Пункти 6–8 і HTTPS у джерелі дають додаткові бали, але в погодженому обсязі нашого проєкту включені всі.

Не додавай карти реальних доріг, GPS, геокодування, адреси клієнтів, облік доставок, CRM, склад запчастин, оплату, сповіщення, AI-функції чи порівняння багатьох алгоритмів. Робочі сторінки та інструкції для користувача мають бути українською. Внутрішні ідентифікатори коду — англійською.

ПОГОДЖЕНИЙ СТЕК

- Основна мова: TypeScript із strict-перевіркою типів.
- Backend: Node.js підтримуваної LTS-гілки та Express.
- Frontend: HTML, CSS, TypeScript. Для збирання та локальної розробки можна використати Vite; React та інші UI-фреймворки не потрібні.
- Важкі обчислення в майбутньому: worker_threads у Node.js.
- Спільна БД та черга: PostgreSQL; доступ до БД з Node.js через pg.
- HTTPS і балансування в майбутньому: Traefik.
- Розгортання в майбутньому: Docker, Kubernetes, HPA, Metrics Server.
- Основний інструмент керування залежностями: npm із package-lock.json.

Не змінюй цей стек на C#, Bun, Deno, Python, Next.js, NestJS чи інший без окремого рішення керівника проєкту.

ПОСТІЙНА ВИМОГА КОРИСТУВАЧА: GIT І ЗМІСТОВНІ КОМІТИ

Ця організаційна вимога діє для блоку 1 та всіх наступних блоків і виправлень. Вона не є додатковим пунктом завдання викладача чи користувацькою функцією застосунку.

1. Користувач ще не має репозиторію для цього проєкту. Створи локальний Git-репозиторій у корені проєкту з основною гілкою main: git init -b main. Перед цим перевір фактичний Git-корінь, щоб не створити випадково вкладений репозиторій. Якщо проєкт уже у власному репозиторії, працюй у ньому та збережи наявну історію; не переініціалізовуй її.

2. Перевір наявні user.name і user.email та використовуй справжню налаштовану Git-ідентичність. Не вигадуй ім'я чи email, не підставляй дані асистента та не змінюй глобальні налаштування. Якщо ідентичності немає, виконай незалежну частину роботи й повідом, які саме значення потрібні для комітів. Не заявляй про створений коміт, якщо Git його не створив. Для блоку 1 достатньо локального репозиторію; віддалений сервіс і push у цьому завданні не налаштовуй.

3. Коміть регулярно за змістом роботи: після завершеної самостійної частини функціональності, суттєвого виправлення, узгодженої зміни структури або завершеного оновлення документації. Один коміт має містити один логічно завершений набір пов'язаних змін. Не накопичуй усі майбутні блоки в одному коміті та не роби коміт після кожного дрібного редагування. Кількість комітів визначається реальною роботою.

4. Перед комітом переглянь git status, звичайний і підготовлений diff та виконай перевірки, доречні для цих змін. Для змін коду першого блоку це npm run typecheck, npm run build та потрібні HTTP-перевірки. Окремий коміт тільки з документацією не вимагає повторного запуску незмінного коду. Форматувальні перевірки не повинні змінювати дослівний оригінал docs/assignment.txt. Не коміть код із відомими невиправленими помилками перевірок.

5. Використовуй короткі конкретні назви англійською у форматі type(scope): description; scope можна опустити, якщо зміна загальна. Орієнтир — до 72 символів у заголовку. Типи:
- feat — нова функціональність;
- fix — виправлення помилки;
- refactor — зміна структури без зміни поведінки;
- test — змістовні тести;
- docs — документація;
- chore — технічне налаштування;
- build або ci — збирання чи автоматизація перевірок.

Приклади адекватних назв:
- docs: define project requirements and implementation plan
- chore: configure TypeScript and project scripts
- feat(server): add health endpoint
- feat(client): show backend availability
- fix(server): correct production asset paths
- docs: record block 1 verification results

Це приклади формулювань, а не вимога створити саме стільки комітів чи розбивати взаємозалежний каркас на неробочі частини. Назва повинна точно відповідати фактичному diff. Не використовуй беззмістовні назви на кшталт update, changes, fix stuff, final або done.

6. Підготуй .gitignore до першого коміту. Не включай node_modules, dist, тимчасові логи, локальні .env та секрети. package-lock.json і безпечний .env.example мають відстежуватися. Вибірково додавай файли поточного завдання та перевіряй підготовлений diff, щоб не включити сторонні зміни користувача.

7. Зберігай історію роботи: не переписуй уже створені коміти й не відкидай сторонні зміни заради чистого статусу. Якщо після коміту виявлена окрема помилка, виправ її, перевір і створи новий fix-коміт.

8. Наприкінці роботи наведи у відповіді список створених за це завдання комітів з короткими хешами та назвами, активну гілку й остаточний git status --short. Якщо залишилися зміни, поясни кожну групу; власні завершені зміни мають бути закомічені. Сторонні зміни зберігай.

9. Обов'язково запиши ці правила у Git-розділ AGENTS.md. У PROJECT_PLAN.md познач їх як постійний процес для всіх блоків. У README.md коротко опиши створений репозиторій, основну гілку та формат назв комітів.

АРХІТЕКТУРНІ ОБМЕЖЕННЯ ДЛЯ НАСТУПНИХ БЛОКІВ

Задокументуй їх у плані, але поки не реалізовуй:

1. Щонайменше два однакові серверні екземпляри застосунку за балансувальником, які реально виконують різні обчислювальні задачі. Два потоки одного серверного процесу не замінюють двох серверних екземплярів.
2. Один серверний екземпляр одночасно виконує одну важку задачу у worker thread та продовжує обслуговувати HTTP-запити.
3. Користувачі, сесії, вхідні дані задач, черга, статуси, прогрес, запит скасування та результати зберігаються централізовано у PostgreSQL. Авторизація та керування задачею працюють через будь-який серверний екземпляр.
4. Призначення задачі виконавцю атомарне. Два сервери не повинні одночасно почати виконувати одну задачу. Глобальні ліміти не можна реалізувати тільки локальними лічильниками окремих серверів.
5. Стани задач: queued, running, completed, cancelled, failed. Скасування обчислення реально звільняє виконавця. Перевищення максимального часу зупиняє роботу й дає failed із причиною timeout.
6. Ліміти розміру задачі, обсягу пошуку, часу виконання, кількості незавершених задач користувача та загальної черги будуть конфігурованими. Конкретні обчислювальні значення визначимо в наступних блоках за вимірами. Не видавай наші припущення за числа з оригінального завдання.
7. Черга показує приблизний час очікування за розміром задач, доступними виконавцями та вимірами тривалості. Прогрес відображає фактичну роботу.
8. Для демонстрації автоматичного розширення обрано мінімум 2 та максимум 4 серверних екземпляри. Межа 4 — наше проєктне рішення, не число з умови викладача. Автомасштабування має реально запускати додаткові екземпляри та включати їх у виконання задач.
9. Адміністратор бачить усі серверні екземпляри, активних обчислювальних виконавців і задачі, прогрес, чергу та фактичне використання CPU і пам'яті.

3. РЕАЛІЗУЙ МІНІМАЛЬНИЙ ПРАЦЕЗДАТНИЙ КАРКАС

Організуй невеликий один npm-проєкт із розділеними src/server, src/client та src/shared. Не створюй зараз складну систему мікросервісів чи набір npm-workspaces.

Backend:
- TypeScript + Express.
- GET /api/health повертає JSON зі status: "ok" та instanceId. Ідентифікатор стабільний протягом запуску та відрізняється між серверними процесами.
- Це перевірка доступності поточного процесу, не перевірка готовності ще не підключеної БД.
- Невідомі API-маршрути повертають коректний 404.
- Реалізуй тільки потрібну каркасу конфігурацію порту, базову обробку помилок і коректне завершення HTTP-сервера.

Frontend:
- Мінімальна охайна сторінка українською з назвою "Планувальник маршруту кур'єра" та одним реченням про призначення.
- Статус доступності backend отримується справжнім HTTP-запитом до /api/health.
- При недоступності сервера показується зрозуміле повідомлення.
- На цьому етапі немає фальшивих маршрутів, демонстраційних задач, непрацюючих кнопок, форм входу чи удаваного прогресу.

Розробка і збирання:
- Локальний frontend може працювати через Vite із проксі /api на Express.
- Зібраний frontend віддається самим Express, щоб у звичайному зібраному режимі використовувалося одне походження для сторінок і API.
- src/shared можна використати для невеликого типу відповіді health. Не вигадуй наперед десятки моделей і контрактів майбутніх функцій.
- Додай .gitignore; згенеровані dist, node_modules та локальні секрети не комітяться.
- .env.example містить тільки актуальні для каркаса параметри з безпечними прикладами.
- Не додавай Dockerfile, SQL-схеми, Kubernetes-маніфести, авторизацію, worker_threads чи обчислювальний алгоритм до їхніх блоків.

Забезпеч фактичні кореневі команди:
- npm install
- npm run dev
- npm run typecheck
- npm run build
- npm start

Вибери для них прості, сумісні інструменти. TypeScript-компіляція backend і збирання frontend мають реально працювати. Врахуй шляхи .js-імпортів, обраний формат модулів, шляхи зібраних файлів і розміщення майбутніх worker-файлів.

4. ПЕРЕВІР РЕЗУЛЬТАТ

Запусти встановлення залежностей, перевірку типів та збирання. Запусти зібраний сервер і перевір справжні HTTP-відповіді:
- /api/health: 200, JSON, коректні поля;
- /: 200, HTML застосунку;
- ресурси зібраного frontend доступні;
- невідомий /api/...: 404.

Перевір режим npm run dev. Якщо доступний браузерний інструмент, перевір відображення сторінки та фактичне отримання статусу. Якщо браузер недоступний, прямо познач візуальну перевірку як не виконану; HTTP-перевірку не видавай за візуальну.

Для цього каркаса достатньо перевірки типів, збирання й інтеграційного HTTP-запуску. Не додавай тести, що лише повторюють реалізацію health, або фіктивний npm test, який завжди успішний. Змістовні тести алгоритму та обробки задач з'являться у відповідних блоках.

Виправ виявлені помилки в межах блоку 1. Не позначай блок готовим, доки не виконано доступні обов'язкові перевірки. Якщо перевірка заблокована середовищем, зафіксуй причину, а не вигадуй результат. Після перевірок зупини тимчасово запущені процеси, які більше не потрібні.

5. ЗАВЕРШИ БЛОК І НАДАЙ ЗВІТ

Актуалізуй PROJECT_PLAN.md та docs/block-01-report.md. Переконайся, що постійні Git-правила записані в AGENTS.md і дотримані протягом виконання. Перевір підготовлені зміни, виконай доречні фінальні перевірки та закоміть решту власних завершених змін, включно з планом, інструкціями і звітом. Комітів може бути кілька відповідно до логічно завершених частин; вимоги зробити рівно один коміт немає.

У файлі звіту можна зазначити хеші, відомі до його коміту. Остаточний хеш коміту зі звітом наведи в повідомленні користувачу після створення коміту. Не створюй нескінченну серію комітів тільки для внесення в сам файл звіту хешу його останнього коміту.

У звіті для керівника проєкту вкажи:
1. Статус блоку: готово / частково / заблоковано та конкретна причина.
2. ОС, архітектура, доступна RAM, версії інструментів і відсутні залежності майбутніх етапів.
3. Що реально створено та які архітектурні рішення зафіксовано.
4. Коротке дерево проєкту й основні змінені файли.
5. Точні команди запуску, локальні адреси та вимоги до оточення.
6. Виконані перевірки й фактичні результати; окремо — те, що не вдалося перевірити.
7. Нові залежності та коротко навіщо кожна.
8. Які функції наступних блоків ще не реалізовані.
9. Корінь Git-репозиторію, активна гілка, створені за блок коміти з короткими хешами та змістовними назвами, остаточний статус робочого дерева або чітка причина, чому коміти заблоковані.
10. Ручні дії користувача, якщо без них неможливо продовжити, і що саме блокує роботу.

Після завершення блоку 1 зупинись. Блок 2 не починай: наступне завдання надійде після перевірки результату керівником проєкту. Якщо сумніваєшся в рутинній технічній деталі каркаса, прийми просте рішення в межах цього завдання та задокументуй його.
