   f9dae57 docs: record block 1 verification results
   Фактичний стан поточного репозиторію має пріоритет: користувач міг додати власні зміни після архівування.

Змістовні інтеграційні тести БД та авторизації в цьому блоці обов'язкові для їх приймання. Документаційний коміт не потребує повторного запуску незмінного коду. Не позначай неперевірений код як перевірений: коли тест заблокований середовищем, зафіксуй це та статус частково/заблоковано; не приховуй відомих помилок.

   Це не обов'язкова кількість чи послідовність комітів. Назва точно описує diff; update, final, done або fix stuff не підходять.

ПОСЛІДОВНІСТЬ РОБОТИ

1. ПЕРЕВІР ФАКТИЧНИЙ СТАН І ПІДГОТУЙ POSTGRESQL

Переглянь наявні файли й налаштування; збережи сторонні зміни. Не відновлюй проєкт з нуля.

Середовище користувача в попередньому звіті: macOS arm64, 24 GiB RAM, Node 24.18.0, npm 11.16.0. docker, kubectl і psql були відсутні в PATH. Перевір поточний стан — відсутність psql у PATH ще не доводить відсутність встановленого PostgreSQL. Перевір відомі встановлення та Homebrew, не скануючи особисті файли.

Потрібен справжній PostgreSQL. Основний варіант для цього macOS — підтримувана стабільна PostgreSQL 18 через наявний Homebrew. Якщо вже є придатна підтримувана версія чи налаштоване підключення, використовуй їх замість паралельного встановлення. Зафіксуй реальну версію і спосіб запуску. Не використовуй RC/beta чи SQLite як заміну.

Якщо встановленого сервера немає, а Homebrew доступний, встанови потрібний пакет і підготуй окреме локальне середовище проєкту в межах доступних дозволів. Не оновлюй сторонні пакети без потреби, не змінюй чужі кластери й налаштування. Якщо Homebrew або потрібний доступ відсутній, закінчи незалежний код і документацію та наведи одну конкретну наступну дію користувача для підключення PostgreSQL. Не оголошуй блок готовим без реальних DB-перевірок.

Створи окрему БД застосунку та окрему тестову БД. Збережи їхні дані між звичайними перезапусками. Застосунок не повинен працювати як PostgreSQL-superuser. Використовуй окрему роль проєкту з потрібними правами; пароль генеруй локально та зберігай тільки в ігнорованому .env. Не показуй його в чаті, звітах, історії команд чи логах.

Локальний кластер, якщо він потрібен, має слухати лише loopback; його дані та логи виключи з Git. Документуй фактичні команди початкового налаштування, запуску і зупинки. Не створюй зараз Docker/Kubernetes-інфраструктуру лише для обходу відсутності PostgreSQL.

2. ДОДАЙ КОНФІГУРАЦІЮ БД ТА МІГРАЦІЇ

Використай pg і невеликий спільний Pool для кожного HTTP-процесу. Орієнтир — до 5 з'єднань на процес; врахуй майбутні 2–4 екземпляри. Додай кінцеві таймаути підключення та SQL-запитів, обробку помилок пулу й коректне його закриття при завершенні. Невеликий рефакторинг src/server/index.ts для відділення конфігурації, app та запуску дозволений, якщо він спрощує перевірки і подальшу роботу.

Параметри середовища повинні включати:
- PORT — наявний порт сервера.
- DATABASE_URL — підключення до БД застосунку.
- TEST_DATABASE_URL — окреме підключення для інтеграційних тестів.
- APP_ORIGINS — явний список дозволених походжень сторінки для POST-запитів; у локальній розробці це Vite та, за потреби, зібраний Express.
- SESSION_TTL_SECONDS — додатний обмежений строк сесії; базовий вибір 28800 секунд, 8 годин.
- COOKIE_SECURE — false для поточного локального HTTP; true для майбутнього HTTPS.

Поточні значення за замовчуванням і їхні межі — проєктне рішення. Валідуй конфігурацію при запуску. Підключення, паролі та секрети не виводь. Не передавай DATABASE_URL у VITE_* чи клієнтський bundle. Нові npm-команди повинні читати конфігурацію узгоджено з уже наявним --env-file-if-exists=.env. Приклади в .env.example — тільки безпечні placeholders, без реальних облікових даних.

Створи версійовані SQL-міграції й невеликий runner на TypeScript через pg. Не додавай ORM чи великий migration framework для кількох таблиць.

Потрібно:
- Облік застосованих версій міграцій.
- Послідовне застосування нових міграцій у транзакціях.
- Усі SQL-команди однієї транзакції виконуються через один отриманий client; release у finally.
- Звичайний повторний запуск не застосовує вже виконану міграцію і не знищує дані.
- Одночасні запуски runner не застосовують одну міграцію двічі: використай PostgreSQL advisory lock на окремому client, який тримається протягом запуску runner.
- Міграції запускаються окремою явною командою; не перебудовуй схему автоматично в кожному HTTP-процесі.
- Жодних DROP/TRUNCATE робочої БД під виглядом налаштування чи тестів.

Мінімальні таблиці:
- users: UUID, логін, його нормалізована унікальна форма або еквівалентна надійна унікальність, password_hash, role, created_at.
- sessions: хеш токена як унікальний ключ, user_id із зовнішнім ключем, created_at, expires_at.
- Таблиця версій міграцій.

Для role достатньо user/admin з обмеженням допустимих значень; реєстрація завжди створює user. Панель і створення адміністратора залишаються для блоку 9. Не додавай відкритого API призначення ролей чи стандартного адміністратора з відомим паролем.

Для часу використовуй timestamptz. Додай потрібні індекси сесій та унікальність логіна на рівні БД. Оброби конфлікт унікальності при конкурентній реєстрації. Користувацькі дані передавай параметрами $1, $2, ...; не складай SQL з отриманих рядків.

3. РЕАЛІЗУЙ АВТЕНТИФІКАЦІЮ Й СПІЛЬНІ СЕСІЇ

Для ідентифікації достатньо username і password. Не збирай телефон, email чи адресу.

Логін: 3–32 ASCII-символи з літер, цифр, "_" та "-". Для порівняння обріж пробіли по краях і приведи до нижнього регістру. Дотримуйся однакових правил у реєстрації та вході; регістр не створює іншого користувача.

Пароль: 15–128 символів; Unicode дозволений, пробіли не обрізай, регістр не змінюй, пароль не скорочуй. Межі перевіряй послідовно на клієнті й сервері. Не вводь додаткової обов'язкової суміші великих літер, цифр і знаків.

Паролі:
- Хешуй асинхронним scrypt із node:crypto.
- Використовуй окрему криптографічно випадкову сіль щонайменше 16 байтів для кожного пароля.
- Погоджений набір: N=32768, r=8, p=3, maxmem=64 MiB; довжина похідного ключа — 64 байти. Зберігай версію формату, параметри, сіль і хеш, щоб перевірка була однозначною.
- Порівнюй буфери однакової довжини через timingSafeEqual.
- Не використовуй синхронний scrypt у HTTP-обробнику. SHA-256 без password KDF не використовуй для паролів.
- Не повертай і не логуй пароль, його хеш або повне тіло запиту.

Для сесій використай просту серверну модель з непрозорим токеном:
- Успішний вхід створює новий токен із щонайменше 32 криптографічно випадкових байтів.
- Токен передається тільки в HttpOnly cookie, не в JSON-відповіді, URL, localStorage або sessionStorage.
- У PostgreSQL зберігається SHA-256 токена, user_id і строк дії. Для випадкового токена SHA-256 застосовується для перевірки, це не спосіб хешування пароля.
- У cookie: Path=/, HttpOnly, SameSite=Lax, узгоджений Max-Age/Expires та Secure згідно з COOKIE_SECURE. Domain не задавай без потреби.
- Перевіряй сесію за спільною БД на кожному захищеному запиті, включно з expires_at. Cookie ще може існувати після серверного відкликання; це не робить сесію дійсною.
- При кожному успішному вході токен оновлюється. Якщо клієнт надіслав попередню сесію, її відклич; не залишай відомий старий токен чинним після заміни.
- Вихід видаляє/відкликає серверну сесію та очищує cookie з відповідними атрибутами.
- Прострочені сесії не авторизують. Передбач просте видалення прострочених записів без окремого сервісу чи складного scheduler.
- Не використовуй MemoryStore, локальну Map, файл або локальний кеш як джерело чинності сесій.
- Не потрібні JWT, refresh-token flow, Redis чи новий auth-фреймворк. Для коректного парсингу/серіалізації cookie можна додати невелику підтримувану бібліотеку cookie.

Відповіді з даними користувача не повинні містити password_hash чи token_hash. Роль береться з БД, а не з поля у запиті. Додай middleware перевірки входу, який надалі використають API власних задач; повний контроль доступу до задач буде перевірено в блоці 4.

4. ДОДАЙ МІНІМАЛЬНИЙ API

POST /api/auth/register
- JSON: username, password.
- 201 та безпечні дані створеного користувача.
- Без автоматичного входу: після успіху інтерфейс пропонує увійти.
- 409 для зайнятого нормалізованого логіна.
- Не приймай role/admin та інші поля як налаштування користувача.

POST /api/auth/login
- JSON: username, password.
- 200, безпечні дані користувача і Set-Cookie нової сесії.
- 401 із однаковим зрозумілим повідомленням для невідомого логіна й неправильного пароля.
- Невдала спроба не створює чинної сесії.

GET /api/auth/me
- 200 із безпечними даними поточного користувача.
- 401 без чинної сесії, з простроченим чи підробленим токеном.
- Cache-Control: no-store.

POST /api/auth/logout
- Відкликання поточної сесії й очищення cookie.
- 204; повторний вихід без чинної сесії також безпечний.
- Це POST, не GET.

Додай лише невеликі спільні типи запитів/відповідей, які реально використовуються зараз. Клієнтські TypeScript-типи не замінюють runtime-валідацію.

Для auth-POST:
- Приймай application/json, перевіряй типи, довжини й допустимі поля.
- Обмеж JSON-тіло, наприклад 16 KiB, саме для auth. Не прив'язуй майбутні дані задач до випадково малого глобального ліміту.
- Некоректний JSON/дані — 400; надмірне тіло — 413; неправильний Content-Type — 415; заборонене походження — 403.
- Обробник помилок не повинен перетворювати всі ці очікувані відмови на 500.
- Для помилок авторизації надай стабільний code та українське message. Внутрішні SQL-помилки, stack trace і рядки підключення клієнту не віддавай.

Захист запитів із cookie:
- Для всіх auth-POST перевіряй Origin за явним APP_ORIGINS; відсутній, "null" або не дозволений Origin відхиляй.
- Список включає фактичне походження Vite, наприклад http://127.0.0.1:5173, та зібраної сторінки, наприклад http://127.0.0.1:3000, для відповідного локального запуску.
- Використовуй точне порівняння нормалізованих походжень; не startsWith, не довільний Host і не "*".
- Залиш dev-проксі /api; не відкривай CORS "*" із credentials для обходу проблем.
- curl та інтеграційні тести POST мають передавати дозволений Origin і application/json; задокументуй це.
- Cookie-Secure=true перевір його заголовком; наявність атрибута не позначає реально виконану вимогу HTTPS. TLS з'явиться лише в блоці 7.

5. ЗБЕРЕЖИ HEALTH І ДОДАЙ ПЕРЕВІРКУ ГОТОВНОСТІ

GET /api/health зберігає контракт блоку 1: status:"ok" та стабільний протягом процесу instanceId. Це liveness поточного процесу; БД і сесія йому не потрібні.

Додай GET /api/ready:
- 200 лише за доступної БД і застосованих необхідних міграцій.
- 503 за недоступного PostgreSQL чи непідготовленої схеми.
- Короткий кінцевий таймаут; без паролів, адрес підключення та внутрішніх stack traces у відповіді.
- Не маскуй відсутні таблиці як успішну готовність.

Коректна конфігурація з тимчасово недоступною БД не повинна робити health успішною авторизацією. HTTP-процес може відповідати health=200, ready=503 та auth=503. Синтаксично некоректна або відсутня обов'язкова конфігурація має зрозумілу відмову при запуску. Помилку БД не підміняй відповіддю "неправильний пароль".

Порядок middleware має зберегти справжні маршрути до фінального API-404. Перевір production static, dev-проксі, помилки та завершення сервера після нового рефакторингу. SIGINT/SIGTERM мають закривати і HTTP, і пул БД у межах кінцевого часу.

6. ЗРОБИ ПРОСТИЙ РОБОЧИЙ ІНТЕРФЕЙС АВТОРИЗАЦІЇ

Збережи стиль мінімальної української сторінки. Додай:
- Реєстрацію: логін, пароль, пояснення допустимих меж і кнопка.
- Вхід: логін, пароль і кнопка.
- Стан "Ви увійшли як …" і вихід для авторизованого користувача.
- Відновлення стану через /api/auth/me при завантаженні/оновленні сторінки.
- Зрозумілі повідомлення про валідацію, зайнятий логін, невдалий вхід і недоступну БД.

Форми можна перемикати на одній сторінці; новий frontend router не потрібен. Не показуй одночасно зайві неактуальні форми після входу. На час запиту блокуй повторне відправлення та показуй короткий стан дії. Використовуй labels, коректні input types, autocomplete і доступні повідомлення. Не вставляй отриманий логін через innerHTML.

Запити відносні /api/... із cookie для того самого походження. Cookie не читається JavaScript. Після logout стан входу скидається. За 401 після завершення строку сесії інтерфейс пропонує увійти знову.

Не додавай кнопок запуску маршруту, фальшивих задач чи admin-сторінок. Основний інтерфейс координат і результатів залишається блоком 5. Поточний користувач бачить тільки вже працездатні дії.

7. ВИКОНАЙ ЗМІСТОВНІ ПЕРЕВІРКИ

Використовуй невеликий набір тестів на node:test та наявний TypeScript-інструментарій, якщо немає конкретної причини для іншого. Jest/Vitest або великий E2E-фреймворк заради цього блоку не потрібні.

Тести з PostgreSQL запускай на справжній окремій тестовій БД:
- TEST_DATABASE_URL обов'язковий для інтеграційного запуску.
- Перевір, що host/port/database тестового підключення не вказують на робочу БД; порівняння сирих рядків URL недостатнє.
- Використовуй явно тестове ім'я, наприклад courier_route_test; setup має відмовлятися від очищення непридатної чи невизначеної БД.
- Не читай cookie, хеші чи справжні облікові дані користувача для демонстраційних логів.
- Моки, SQLite і тести, які лише перевіряють факт виклику pg, не підтверджують спільну БД.
- Відсутню БД не пропускай мовчки з повідомленням "усі тести пройшли".

Додай фактичні npm-команди для міграцій, перевірки підключення, перевірок авторизації та запуску тестів. Локальний TypeScript runner допустимий; після build також має бути зрозумілий шлях запуску міграцій зібраним JavaScript із доступними SQL-файлами. Не створюй порожнього npm test.

Обов'язкові сценарії:
1. Міграції на чистій тестовій БД створюють потрібну схему. Повторний і конкурентний запуск не дублює версії та не знищує записи.
2. Реєстрація зберігає користувача; у БД немає plaintext-пароля. Два одночасні запити з логінами різного регістру не створюють дубль.
3. Правильний пароль дозволяє увійти; неправильний пароль і невідомий користувач дають 401 з узгодженим повідомленням.
4. /me без cookie, з підробленою або простроченою сесією повертає 401. Строк дії в тесті можна змінити безпосередньо в тестовій БД; не чекай багато хвилин.
5. Після перезапуску HTTP-процесу користувач і непрострочена сесія працюють через PostgreSQL.
6. Два незалежні запущені HTTP-процеси A і B мають різні instanceId та однакову тестову БД. Увійди через A, передай цю cookie до /me на B — отримай того самого користувача. Вийди через B — та сама cookie більше не авторизує через A. Заміна app-об'єкта в одному процесі недостатня.
7. Повторний успішний вхід видає інший токен; попередній надісланий токен відкликано. У sessions зберігається його хеш, не сам токен.
8. Перевір атрибути cookie, узгоджене очищення при виході та конфігурацію Secure. Не логуй реальні значення токенів.
9. Невалідні поля, role:"admin", поганий JSON, великий body та неправильний Content-Type відхиляються передбачувано, без випадкового 500.
10. POST із дозволеним Origin працює; чужий, "null" і відсутній Origin відхиляються. Дозволене походження Vite працює через справжній dev-проксі.
11. За недоступної БД health залишається liveness, ready дає 503, авторизація дає 503. Для цього запускай окремий тестовий процес з недоступною адресою, не зупиняй чужу чи робочу БД.
12. Перевір пароль/хешування, його однакові правила Unicode та довжини, відсутність небезпечного скорочення/trim пароля. Перевір, що публічна реєстрація не надає роль admin.

Виконай також:

- npm run typecheck.
- npm run build.
- Змістовні unit/integration тести.

Якщо браузер доступний, перевір реєстрацію, вхід, оновлення сторінки, вихід, видимі повідомлення про помилки та відсутність горизонтального переповнення на вузькому екрані.
