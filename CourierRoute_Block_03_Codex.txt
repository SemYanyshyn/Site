1. ЗАФІКСУЙ МІНІМАЛЬНИЙ КОНТРАКТ ОБЧИСЛЕННЯ

Запропонований контракт реалізуй в невеликому src/shared/route.ts або еквівалентному місці:

Вхід:
{
  warehouse: { x: number, y: number },
  points: Array<{ x: number, y: number }>,
  iterations: number,
  seed?: number
}

warehouse — склад з індексом 0.
points[0] має індекс 1, points[1] — 2 і так далі.
Масив містить лише доставки; склад окремий. Порядок масиву стабільний, його індекси достатні для майбутньої візуалізації й БД.

Успішний результат містить щонайменше:
- order: масив індексів [0, ..., 0], де кожен індекс доставки 1..N трапляється рівно раз;
- length: фактична сумарна евклідова довжина замкнутого маршруту;
- initialLength: довжина початкового допустимого маршруту;
- seed: фактично використане ціле зерно;
- iterationsRequested та iterationsCompleted;
- elapsedMs: виміряний час;
- позначення, що це найкращий знайдений наближений результат.
Для дозволеного дострокового завершення на тривіальному вході зазнач причину й фактичну кількість ітерацій.

Не потрібні адреси, кілометри, час поїздки, вартість чи додаткові ідентифікатори клієнтів.

Валідація виконується в runtime до створення worker:
- Коректні об'єкти/масиви та лише погоджені поля.
- Для кожної координати typeof number, Number.isFinite і погоджена межа модуля.
- Мінімум одна доставка, кількість не перевищує серверну межу.
- iterations — додатне безпечне ціле в межах серверного ліміту.
- seed за наявності — ціле 0..4294967295; нуль є чинним значенням.
- Рядки з цифрами, NaN, Infinity, пропущені/зайві поля, дробові лічильники й перевищення меж відхиляються з конкретною українською помилкою.
- Збіг координат різних доставок або складу дозволений: це різні індекси, їх не можна втрачати через deduplication.
- Якщо seed відсутній, згенеруй його на серверній стороні, збережи у нормалізованому вході та результаті. В майбутньому блок 4 збереже саме цей вхід у БД.

Не змінюй надісланий користувачем масив/об'єкти під час обчислення. Не покладайся лише на TypeScript-типи чи майбутню клієнтську перевірку.

2. РЕАЛІЗУЙ ОДИН РЕАЛЬНИЙ АЛГОРИТМ

Погоджений метод: початкова побудова допустимого маршруту найближчим сусідом, потім ітеративний пошук simulated annealing з перестановками 2-opt. Обидва етапи — одна послідовність пошуку; не додавай користувацького меню алгоритмів.

Реалізуй на TypeScript самостійно, без OR-Tools, зовнішнього API та Python/C#-підпроцесів.

Потрібна поведінка:
- Відстань між точками евклідова, без округлення в обчисленні.
- Склад залишається початком і кінцем; змінюється порядок лише доставок.
- Одна ітерація пошуку — розгляд реальної 2-opt зміни, обчислення зміни довжини та рішення про її прийняття.
- Покращення приймаються; можливість тимчасового погіршення залежить від температури, яка зменшується за задокументованим розкладом.
- Використай власний невеликий детермінований PRNG із заданим seed, без глобального Math.random для пошуку.
- Зберігай найкращий знайдений маршрут окремо від поточного. Вихід не може бути гіршим за початковий у межах обґрунтованої floating-point похибки.
- Однаковий нормалізований вхід, seed і завершений бюджет дають той самий order та length. Час і моменти повідомлень прогресу не зобов'язані збігатися.
- Для довжини використовуй number/Float64 з урахуванням похибки. Фінальну довжину перерахуй за фактичним order; не віддавай тільки накопичену суму дельт.
- За використання інкрементальних дельт унеможлив накопичення похибки, яке дає неправдиве "найкраще" значення. Періодична перевірка допустима, якщо вона служить алгоритму.
- Для 1–2 доставок і нульової довжини передбач коректне швидке завершення без нескінченного вибору двох різних індексів, ділення на нуль або NaN.
- Не заверши пошук лише через тимчасову відсутність покращень, видаючи локальний мінімум за доведений глобальний оптимум. Звичайний нетривіальний випадок працює до обмеженого бюджету чи фактичної зупинки.

Опиши складність підготовки, однієї спроби та пам'яті. Не стверджуй, що весь 2-opt крок завжди O(1): навіть якщо дельта рахується за двома ребрами, застосування розвороту може залежати від довжини сегмента. Відстані можна рахувати на вимогу або зберігати в обмеженій матриці, врахувавши її розмір після валідації N.

Повернення за максимальним часом не видавай за completed: у нашому погодженому життєвому циклі це failed з причиною timeout. Найкращий частковий маршрут не підміняє успішно завершений результат. Успішний результат називай "найкращий знайдений маршрут", без обіцянки глобальної оптимальності.

Заборонено штучні sleep/setTimeout для збільшення тривалості, порожні цикли, повтори вже готового розрахунку тільки для завантаження CPU, паузи для малювання прогресу та інші імітації. Таймери для контролю часу, throttling повідомлень і тестового очікування запуску не є імітацією, але самі не повинні затримувати пошук.

4. ВИКОНУЙ ПОШУК У WORKER THREAD

Створи невелику зрозумілу структуру, наприклад:
- src/shared/route.ts — контракт, валідація або її клієнтськи безпечна частина;
- src/server/route/algorithm.ts — власне обчислення;
- src/server/route/worker.ts — запуск алгоритму та повідомлення parentPort;
- src/server/route/executor.ts — worker, слот, прогрес, таймаут, скасування й очищення.
Це орієнтир, не вимога створити зайві прошарки.

Важкі етапи, включно з побудовою матриці/початкового маршруту, виконуються у worker, а не в головному HTTP-потоці. У головному потоці лишається обмежена валідація та керування.

Один серверний процес має один спільний обчислювальний executor і щонайбільше одну активну важку задачу:
- Встановлюй зайнятість синхронно перед асинхронним запуском, щоб конкурентні start не створили два worker.
- Другий одночасний start відхиляється явною помилкою executor_busy.
- Не створюй окремий executor для кожного майбутнього запиту.
- Не додавай зараз локальну приховану чергу. Спільна PostgreSQL-черга з'явиться в блоках 4/6.
- Після фактичного завершення/зупинки один слот звільняється, і можна запускати наступний розрахунок.

Сервіс надає:
- start нормалізованого/перевіреного входу;
- доступ до Promise одного кінцевого результату та callback/подій фактичного прогресу;
- cancel активного запуску;
- shutdown для завершення процесу.
Внутрішній runId допустимий для зіставлення подій; це не заміна майбутнього запису задачі у PostgreSQL.

Врахуй реальні шляхи:
- ESM, NodeNext, .js-імпорти та наявну структуру dist/server.
- Запуск worker у режимі розробки через TypeScript-інструментарій і запуск зібраного .js після build.
- Наявність .js або .ts у файловій системі сама по собі не доводить, що loader worker завантажить залежності.
- Перевір обидва режими й запуск з іншої робочої папки.
- Зібраному worker не потрібні tsx/Vite чи вихідні .ts файли для виконання.
- Не запускай рекурсивно worker з preload чи під час імпорту модуля.

Не передавай у worker паролі, session cookie чи DATABASE_URL: обчислення потребує тільки маршруту, серверних меж і технічних даних запуску. Врахуй, що Worker за замовчуванням успадковує process.env: передай порожнє або явно мінімальне env без секретів. У worker немає pg.Pool і він не читає/оновлює БД. Поточний стан задач у PostgreSQL та його оновлення з executor будуть у блоці 4.

5. РЕАЛЬНИЙ ПРОГРЕС, ТАЙМАУТ І СКАСУВАННЯ

Прогрес:
- Стани етапу: підготовка, пошук, завершення; внутрішні ідентифікатори англійською.
- Під час пошуку передавай фактичні completedIterations, totalIterations і узгоджений відсоток.
- Відсоток монотонний, у межах 0..100. До успішного завершення він менший за 100; 100 — тільки після готового перевіреного результату.
- Частота повідомлень обмежена, орієнтир 100–250 мс для довгої задачі; останній стан не губиться.
- Повідомлення надсилаються з реально виконаного циклу. setInterval усередині синхронно зайнятого worker не забезпечує такої роботи.
- Підготовка та швидке дострокове завершення тривіального випадку відображаються чесно, без вигаданих ітерацій.
- Помилка користувацького callback/слухача не має залишити забутий worker або обвалити HTTP-процес.
- Наразі це внутрішній прогрес. Не позначай вимогу інформування користувача виконаною до API/UI блоків 4/5.

Таймаут:
- Контролюється батьківським потоком і охоплює запуск worker, важку підготовку, пошук і завершення.
- Час вимірюється монотонним годинником.
- За перевищення виконавець реально припиняє worker; повертає один кінцевий стан failed з reason:"timeout" і зрозумілим повідомленням.
- Не залишай обчислення працювати після повернення timeout.
- Дочекайся фактичного завершення потоку, перш ніж вважати слот вільним.
- Таймаут і скасування не залежать від того, чи worker встиг надіслати прогрес.

Скасування:
- Реально припиняє активне обчислення, дає один кінцевий стан cancelled і звільняє слот після завершення worker.
- Для негайної зупинки можна використовувати worker.terminate(); врахуй його асинхронне завершення.
- Не обмежуйся parentPort.on("message") зі скасуванням усередині суцільного CPU-циклу: він може не обробити цю подію.
- Повторний cancel безпечний; cancel уже завершеної задачі не змінює її результат.
- Пізні повідомлення після скасування, error/exit і одночасний успіх не створюють другого результату.
- Відміна не є failed/timeout і не повинна перетворюватися на completed через пізнє повідомлення.

Життєвий цикл:
- completed повертає повний валідний результат.
- failed з reason timeout означає реальне перевищення часу.
- failed з reason worker_error означає аварію/неочікуваний вихід/некоректний результат worker.
- cancelled означає фактичну зупинку за запитом.
- Немає "завжди успішного" fallback, фальшивого маршруту чи неявного синхронного обчислення в HTTP-потоці після помилки worker.
- Очищуй таймери, listeners і посилання; worker з фінальним результатом також має справді завершитися.
- Додай executor.shutdown до коректного завершення серверного процесу поряд із HTTP і pg.Pool. За активного розрахунку SIGINT/SIGTERM не чекає повного 30-секундного бюджету, а припиняє роботу у межах наявного граничного shutdown.

До блоку 4 це поведінка обчислювального сервісу, не збережений життєвий цикл HTTP-задач. Термінальні стани узгоджені з ним заздалегідь; queued зараз не потрібен.

6. ДОДАЙ ВІДТВОРЮВАНІ CLI-ПЕРЕВІРКИ ТА ВИМІРИ

Підготуй невеликі вхідні JSON-приклади без секретів, зокрема:
- простий перевірюваний маршрут;
- нетривіальний набір для звичайного пошуку;
- важкий набір або детермінований генератор для перевірки CPU, прогресу та меж.

Не вставляй величезні випадкові масиви чи логи в репозиторій. Годиться невеликий генератор із фіксованим seed і явною кількістю точок.

Додай фактичні npm-команди:
- Запуск route demo через TypeScript у розробці.
- Запуск того самого зібраним JavaScript після build.
- Тести алгоритму/executor.
- Обмежений benchmark.
Точні назви обери прості, наприклад route:demo, route:demo:built, test:route, route:bench; вони повинні працювати, а не бути заглушками.

Для малого, середнього й важкого входів виміряй:
- Кількість точок, бюджет та seed.
- Фактично виконані ітерації.
- Реальний elapsedMs і CPU-час.
- Початкову й найкращу знайдену довжину.
- Успішне завершення або timeout; кількість отриманих повідомлень прогресу.
- Використання пам'яті хоча б на рівні процесу з точним позначенням, що саме виміряно; RSS процесу не називай точною пам'яттю одного worker.

Принаймні один допустимий нетривіальний сценарій має показувати помітне реальне обчислення та кілька прогрес-подій; орієнтир — кілька секунд на цій машині. Підбери обмежений бюджет за вимірами. Не сповільнюй код, не вимикай корисні оптимізації та не додавай фіктивну роботу для досягнення бажаної тривалості. Тривалість залежить від обладнання.

Кінцеві межі й реальні виміри запиши в docs/block-03-report.md. Не вигадуй результати. Підбери окремий короткий серверний timeout у тесті, який справді перериває реальний пошук; цей тест не вимагає чекати стандартних 30 секунд.

7. ПЕРЕВІР КОРЕКТНІСТЬ ТА НЕБЛОКУВАННЯ HTTP

Використовуй node:test та наявний інструментарій. Тести мають перевіряти поведінку, а не повторювати ті самі формули з реалізації без незалежних очікувань.

Потрібні змістовні перевірки:

Вхід і маршрут:
- Порожній/завеликий points, пропущені поля, зайві поля, нечислові/нескінченні/позамежні координати.
- Непридатні iterations/seed; seed=0 працює.
- Одна й дві доставки; простий квадрат/прямокутник з відомою довжиною; від'ємні, дробові та однакові координати.
- Нульова довжина без NaN і нескінченного циклу.
- Кожна доставка відвідана рівно раз, склад на обох кінцях, зайвих індексів немає.
- Фінальна length відповідає незалежно перерахованій довжині order в межах обґрунтованої похибки.
- Найкращий результат не гірший за initialLength.
- Детермінованість за однакових seed/входу/бюджету та відсутність мутації вхідних даних.
- Наближений пошук не тестується як гарантований глобальний оптимум на довільному випадковому наборі. Повний перебір малих задач допустимий як допоміжний тестовий еталон, але не як production-алгоритм.

Executor:
- Обчислення реально працює в іншому thread, а не просто повертає Promise синхронного пошуку.
- Другий одночасний start не запускає другий важкий worker.
- Прогрес монотонний, з фактичних лічильників; 100 лише за completed.
- Скасування довгого реального пошуку зупиняє thread, повертає cancelled і дозволяє наступний запуск.
- Повторний cancel і cancel після завершення безпечні.
- Короткий timeout дає failed/timeout, зупиняє thread і дозволяє наступний запуск.
- Error/exit без результату дає worker_error та не залишає зайнятий слот.
- Помилка створення worker, ранній cancel та пізні повідомлення не залишають завислого Promise чи таймера.
- Один запуск отримує рівно один термінальний результат.
- Успіх, cancel, timeout і аварія звільняють реальні ресурси; наступна задача після кожного випадку успішно працює.
- Запуск worker у TypeScript/dev та зібраному JS; для built перевір артефакт без вихідних .ts, за потреби в окремій тимчасовій папці.
Тестова ін'єкція аварійного worker допустима тільки для сценарію помилки; успіх/cancel/timeout перевіряються на реальному пошуку.

HTTP під навантаженням:
- Запусти справжній Express createApp/HTTP-сервер і executor в одному процесі.
- Поки worker реально виконує важкий пошук і його Promise ще pending, кілька справжніх /api/health мають успішно відповідати.
- Виміряй час цих відповідей. Не вважай перевіркою неблокування запити, відправлені вже після завершення worker.
- Не запускай обчислення в іншому незалежному процесі поруч із HTTP і не називай це перевіркою ізоляції worker у сервері.
- Не додавай до production API тестовий /run чи /test endpoint; тестовий harness може напряму керувати executor в процесі.
- Перевір SIGINT/SIGTERM за активного worker: потік і HTTP завершуються, процес виходить, таймери/слоти не зависають.
- Відсутність БД не заважає liveness. Для тесту неблокування не потрібно маскувати фальшивою БД успішну авторизацію.

Регресія:
- npm run typecheck; npm run build.
- Наявні 11 unit і 13 реальних PostgreSQL integration-тестів після змін конфігурації/shutdown мають залишитися працездатними.
- Виконай їх на окремій тестовій БД за існуючим захистом; не змінюй 001_auth.sql, паролі чи чинні сесії користувача без потреби.

- Якщо середовище змінилося й DB/browser-перевірка заблокована, збережи точне обмеження. Не замінюй PostgreSQL SQLite/моком і не повідомляй успіх пропущених тестів.
- Завершуй непотрібні тимчасові HTTP-процеси та worker. PostgreSQL для локальної розробки можна лишити працювати, явно вказавши його стан і команди керування.
