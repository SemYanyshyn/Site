1. ДОДАЙ МІГРАЦІЮ Й КОНТРАКТИ ЗАДАЧ

Додай нову версію SQL, наприклад migrations/002_jobs.sql. 001_auth.sql не змінюй. Онови runner/список необхідних версій, копіювання SQL у build та перевірку готовності. Міграції запускаються явно, зберігають дані й працюють повторно та конкурентно.

Мінімальний запис jobs має містити:
- UUID задачі; user_id з FK на користувача.
- Нормалізований RouteInput із фактичним seed у jsonb.
- status: queued | running | completed | cancelled | failed.
- Реальні progress: stage, completedIterations, totalIterations, percent.
- created_at, updated_at, started_at, finished_at з timestamptz за потреби стану.
- Запит скасування, наприклад cancel_requested_at.
- instanceId виконавця, який відповідає його /api/health, для зв'язку фактичного виконання з сервером.
- Приватний claim token, який відрізняє поточне призначення.
- Фактичний серверний timeout для запуску та час, після якого його можна визнати втраченим.
- Результат RouteResult тільки за completed; безпечну причину/повідомлення за failed.

Точні назви SQL-колонок обери узгоджено. Не створюй окремі таблиці для кожного статусу, копії черги в пам'яті чи журнал подій як нову продуктову функцію. Однієї jobs та потрібних індексів достатньо.

Додай constraints для станів, коректних лічильників/відсотка, зв'язку результату з completed і finished_at із кінцевим станом. За queued progress=0; running <100; completed=100. Cancelled/failed не стають completed і не отримують удаваного результату.

Потрібні індекси для вибору queued, історії/активних задач власника та пошуку прострочених running. Історія має стабільний порядок created_at + id, а не випадковий порядок рядків.

Збережи незмінними RouteInput/RouteResult блоку 3, якщо реальна інтеграція не виявила необхідної корекції. Нові спільні JobSummary/JobDetails/API-типи описують тільки поточні функції. Runtime-валідація лишається обов'язковою.

PostgreSQL — джерело стану для ВСІХ користувацьких читань/скасувань. Локально допустимі лише посилання на фактично запущений worker, claim і останній ще не записаний progress; це не заміна БД.

2. СТВОРЕННЯ Й АТОМАРНІ ЛІМІТИ

Початкові проєктні значення:
- JOBS_MAX_ACTIVE_PER_USER=3.
- JOBS_MAX_OUTSTANDING=100 для всієї системи.
- JOBS_POLL_INTERVAL_MS=250 для базового dispatcher.
Це не числа з умов викладача. Валідуй кінцеві додатні цілі значення й розумні верхні/нижні межі конфігурації; запиши їх у README/.env.example. На всіх серверних процесах використовуй однакові налаштування.

Active/outstanding тут означає queued + running. Запит скасування running продовжує займати ліміт до справжнього завершення. Завершена історія не витрачає цей активний ліміт. Пагінація обмежує відповідь історії, а не кількість усіх збережених записів; не видавай одне за інше.

Створення:
- Користувач визначається зі спільної серверної сесії, не з JSON.
- Валідуй RouteInput за фактичними route-лімітами; перевищення не створює jobs і worker.
- Згенеруй seed один раз, якщо його не надіслано; у БД зберігається вже нормалізований вхід із seed.
- У короткій транзакції атомарно перевір обидва ліміти й INSERT queued.
- COUNT + INSERT без спільної синхронізації недостатні. Використай, наприклад, один короткий PostgreSQL advisory transaction lock для всіх admission-транзакцій, потім count/insert на одному client у READ COMMITTED. Не тримай цей lock під час обчислення.
- Не використовуй локальні Map/counters як глобальний ліміт.
- Claim змінює queued на running і не збільшує outstanding; кінцеві переходи його зменшують. Нових неатомарних шляхів вставки чи повернення у queued не повинно бути.
- За ліміту користувача — 429 з окремим code; за загальної місткості — 503 з іншим code. Зрозуміле українське message; без створення зайвого запису.
- Відповідай 202 тільки після підтвердженого commit. Обчислення не очікується всередині POST.

Не додавай автоматичного видалення старої історії, нового API керування профілями чи повторного запуску готової задачі. Користувач може подати нову задачу звичайним POST.

3. РЕАЛІЗУЙ HTTP API З ПЕРЕВІРКОЮ ВЛАСНИКА

Усі /api/jobs потребують чинної спільної сесії. Використовуй наявний requireAuth та безпечні помилки code/message. Для мутацій потрібні той самий точний Origin із APP_ORIGINS та JSON, що й у блоці 2. За потреби винеси спільний guard із auth без зміни його поведінки.

POST /api/jobs
- Тіло — саме RouteInput, не userId/status/instanceId/timeout/claim.
- 202 і зафіксований початковий запис queued або його узгоджене представлення зі стабільним id; Location: /api/jobs/:id.
- Не повертай completed до закінчення роботи; не затримуй відповідь до результату.
- Поганий вхід/розмір — передбачувані 400/413; ліміти — 429/503; недоступна БД — 503.

GET /api/jobs
- Лише задачі поточного користувача.
- Пагінація: за замовчуванням limit=20, максимум 50; offset або cursor із явною валідацією й стабільним порядком.
- Потрібний фільтр status=active для queued/running. Без фільтра — вся власна історія, включно з кінцевими станами.
- Можна підтримати конкретний один status із погодженого переліку. Зайві способи сортування/пошуку не потрібні.
- Невалідні query-параметри відхиляй перед SQL.
- Список повертає компактні summary, без повних масивів входу й результату для кожного рядка. Конкретна задача відкривається окремо.

GET /api/jobs/:id
- 200: власна задача, нормалізований вхід, стан, збережений прогрес, ознака запиту скасування, часові поля та результат тільки за completed.
- failed має безпечну причину й українське пояснення.
- За потреби executedBy містить фактичний instanceId; не передавай приватний claim token.
- Невалідний UUID — 400; відсутня або чужа задача — однаковий 404.
- Не читай поточний стан з executor лише тому, що запит надійшов до його сервера.

POST /api/jobs/:id/cancel
- Порожній JSON-об'єкт.
- queued: атомарно cancelled, finished_at, без запуску worker; 200 з актуальним станом.
- running: зафіксувати cancel_requested_at у БД; 202 з поточним running/cancelRequested=true, поки executor ще працює.
- Коли потік справді зупинено, власник виконавця записує cancelled.
- Повторний cancel безпечний. Для кінцевої задачі — 200 з незміненим кінцевим станом; нового запуску немає.
- Чужа й відсутня задача — той самий 404.
- Запит на сервер B мусить скасувати задачу, яку рахує A.

GET /api/jobs/limits
- Розмісти перед /:id.
- Повертає безпечні актуальні route-ліміти та maxActivePerUser для майбутньої форми блоку 5.
- Не повертає env, паролі, DB URL, чужі задачі чи фіктивні метрики.

Для job API встанови Cache-Control: no-store. Дані користувача й результати іншого власника не повинні потрапити у відповіді, навіть якщо надіслати його UUID чи поле user_id.

Auth зберігає обмеження 16 KiB. Для POST job введи окремий кінцевий body limit, наприклад 256 KiB, придатний для route-стелі. Невалідний JSON=400, надмірний body=413, неправильний Content-Type=415, заборонений Origin=403. Наявний error handler не повинен називати будь-яке перевищення "16 KiB", якщо воно сталося в job router. Не відкривай CORS "*", JWT/Bearer-обхід чи тестовий неавторизований endpoint.

4. ДОДАЙ СПІЛЬНИЙ DISPATCHER НА НАЯВНИЙ EXECUTOR

У startServer є один RouteExecutor. Додай поруч один coordinator/dispatcher, передай йому цей executor, pg.Pool та той самий instanceId. Не створюй другий executor у router чи для кожної задачі.

Базова робота:
- Працює незалежно від HTTP-запиту й переживає від'єднання браузера.
- Немає накладених poll-циклів: синхронний guard перед першим await і явна активна claim-резервація.
- Вільний процес атомарно вибирає одну queued за created_at/id.
- Використай коротку транзакцію SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1 та UPDATE ... RETURNING або коректний еквівалент.
- У тій самій транзакції queued → running, фіксуються instanceId, новий claim token, started_at і серверний timeout.
- Не запускай worker до commit. Якщо claim не дістався, worker не створюється.
- Два сервери не можуть почати одну задачу. Не покладайся на "обидва спочатку перевірять статус".
- Транзакції завершуються до важкого пошуку; client повертається пулу у finally.
- Поки є активний claim, вільний уже завершений worker сам по собі не дозволяє взяти нову задачу до узгодження попереднього кінцевого запису з БД.
- Немає прихованої локальної черги. Нова задача бере дані з PostgreSQL, а не з масиву в процесі.
- Не додавай автоматичних повторних обчислень та повернення running у queued у цьому блоці.

Усі progress/terminal UPDATE виконавця обмежуються id, status=running та його claim token. Пізній callback або старий власник не може переписати вже завершену чи інакше призначену задачу. Claim token — технічний захист запису, не токен авторизації користувача.

Для реального результату використовуй наявний RouteOutcome. Не перенось calculateRoute у HTTP-потік і не повертай "демонстраційний" результат за помилки. Якщо збережений вхід неможливо виконати за узгодженою конфігурацією, дай конкретний failed, а не нескінченно переставляй його між станами.

Прогрес у БД:
- З реальних onProgress, збереження приблизно раз на 150–250 мс для довгої задачі; останній коректний стан не губиться.
- Не запускай необмежену кількість одночасних UPDATE з async callback. Один запис у польоті й останній очікуваний snapshot достатні.
- Прогрес монотонний; stage та counters узгоджені з RouteProgress.
- Внутрішні 100 від executor НЕ записуються як running=100. Completed, result, percent=100 і finished_at фіксуються одним кінцевим оновленням.
- Пізній progress не скидає cancel_requested_at і не змінює кінцевий стан.
- Executor ізолює помилки callback: тому coordinator сам обробляє відмову DB-оновлення та керує своєю задачею; не очікуй, що throw у callback автоматично зупинить worker.
- Користувач бачить однакові дані через A і B з БД; polling GET достатній. SSE/WebSocket зараз не потрібні.

5. СКАСУВАННЯ, КІНЦЕВІ СТАНИ Й ВТРАТА ВИКОНАВЦЯ

Скасування через інший сервер:
- HTTP B записує прапорець у PostgreSQL, а не шукає worker у власній Map.
- Coordinator A регулярно перевіряє прапорець активної задачі, зокрема коли executor busy.
- Якщо запит є, викликає cancel саме відповідного runId і чекає фактичного завершення потоку.
- Лише потім записує cancelled і звільняє свою claim-резервацію для наступної задачі.
- Перевірка cancel не залежить від нової progress-події: підготовка або відсутність покращень не блокують скасування.

Одночасний cancel/finish:
- queued → running/cancelled вирішується атомарно, без GET-потім-безумовного UPDATE.
- Якщо cancel_requested_at уже записано, поки задача ще running, пізній результат completed не має його проігнорувати.
- За звичайної фіналізації перечитай/заблокуй актуальний рядок або зроби еквівалентний умовний атомарний UPDATE: за прийнятого запиту скасування кінцевий стан cancelled, без result.
- Якщо completed/failed/cancelled вже зафіксовано раніше, повторний cancel не переписує цей стан.
- Для гонки timeout/cancel задокументуй узгоджене правило; стан один, старі progress/результати його не змінюють.
- Не позначай running cancelled у HTTP-відповіді, поки виконавець ще фізично працює.

Звичайні кінцеві результати:
- completed: RouteResult після перевірки й виходу worker, result + progress=100 + finished_at одним commit.
- failed/timeout: parent timeout реально зупинив обчислення; частковий маршрут не є completed.
- failed/worker_error: аварія, некоректний результат чи неочікуваний вихід; HTTP-процес працює далі.
- cancelled: реальне користувацьке скасування з БД та припинений worker.
- Після кожного з цих станів наступна queued запускається, якщо є ресурс.

Несподівана смерть процесу не повинна залишати running назавжди:
- В момент claim зафіксуй у БД фактичний серверний timeout запуску.
- Мінімальний варіант відновлення: після started_at + timeout + невеликого задокументованого grace перевести досі running у failed/worker_lost через умовний атомарний UPDATE.
- Базовий grace можна обрати 5000 мс, у тесті — контрольоване коротше значення. Він має враховувати bounded DB-операції та запуск/завершення worker; не оголошуй живу нормальну задачу втраченою до її допустимого часу.
- Перевірку проводить будь-який живий coordinator, також після перезапуску. Вона не обмежується лише старими задачами власного instanceId.
- Не позначай усі running втраченими при старті нового сервера: інший сервер може їх активно рахувати.
- Не запускай автоматично втрачену задачу вдруге. Для цього блоку достатньо чесного failed, збереженої історії та можливості подати нову задачу.
- Така перевірка deadline не вимагає окремого сервісу heartbeat/оркестратора чи нової інфраструктури. Окремий облік серверної потужності належить наступним блокам.

Недоступна БД:
- Public API не відповідає 202 до commit і не повертає успішний результат, якого немає в БД.
- Coordinator припиняє нові claim та не входить у CPU busy loop повторних SQL-помилок.
- За втрати можливості контролювати активну задачу через БД зупини власний worker і відрізни інфраструктурну зупинку від запиту користувача.
- Кінцеве оновлення можна обмежено повторити після відновлення БД; поки воно не узгоджене, не накопичуй інші локальні роботи.
- Якщо процес не встиг зберегти кінцевий стан, після відновлення БД спрацює описане worker_lost-відновлення.
- Не перетворюй відмову SQL на completed чи на порожню історію з 200.

Коректне завершення:
- Зупини нове приймання/claim, скасуй активний worker і дочекайся його виходу.
- Для задачі, зупиненої через shutdown, збережи failed/server_shutdown, якщо користувацький cancel не був прийнятий раніше; не видавай її за добровільно скасовану користувачем.
- Запиши доступний кінцевий стан ДО закриття pg.Pool.
- Заверши poll/retry/progress-таймери й promises. Збережи п'ятисекундну граничну зупинку процесу.
- Якщо БД недоступна, не чекай нескінченно; подальше worker_lost-відновлення має бути можливим.
- Наявні route-HTTP тести можуть напряму запускати executor у startServer без jobs-claim. Збережи коректне припинення й такого активного worker через executor.shutdown.
- Наявні CLI route demo/bench залишаються незалежними від БД.

6. ПЕРЕВІР СПРАВЖНЮ БД ТА ДВА СЕРВЕРНІ ПРОЦЕСИ

Нові автоматизовані тести — на node:test та наявному інструментарії. Для jobs integration потрібні реальний PostgreSQL, перевірена окрема TEST_DATABASE_URL, роль без superuser та ізольована випадкова схема з гарантованим cleanup.

Збережи наявний guard host/port/database, DNS/loopback та URL overrides. Не очищуй робочу БД. Нові міграції застосовуються до тестової схеми. Відсутня БД не позначається "усі тести пройшли", тести не пропускаються мовчки.

Процеси A і B повинні запускати production startServer/coordinator/executor з однаковою БД та лімітами, різними портами/instanceId і справжніми worker. Не замінюй їх двома app-об'єктами або моками. Тут ще немає load balancer — це перевірка готовності прикладного рівня до нього.

Додай фактичну команду на кшталт npm run test:jobs. Узгодь npm test та послідовність запуску наборів, щоб спільні порти й cleanup не конфліктували. Built-тести запускаються після build; документація має вказувати цей порядок.

Обов'язкові сценарії:

1. Міграції:
- Чиста схема, повторне застосування й конкурентні runner.
- Існуючі користувачі/сесії з 001_auth збережені.
- Ready=503 до повної схеми jobs та 200 після неї; health лишається liveness.
- Build містить новий SQL; built runner працює з ним.

2. Створення й виконання:
- Без сесії job API відмовляє.
- Валідний POST повертає 202 до закінчення важкої задачі; у БД є нормалізований вхід із seed.
- Від'єднання клієнта після прийняття не зупиняє job.
- Реальний queued → running → completed дає правильний RouteResult із worker, збережений у БД.
- Тривіальний вхід проходить ті самі життєві переходи без фальшивих ітерацій.

3. Ізоляція власників:
- Два користувачі; другий не читає й не скасовує задачу першого.
- Історія/active фільтр не містять чужих рядків.
- userId, status, claim, timeout чи result у POST не дозволяють обійти валідацію/власника.
- Чужий і невідомий id дають однаковий 404; невалідний id/query — 400.

4. Ліміти:
- Завеликий вхід/iterations відхиляються до INSERT і worker.
- Конкурентні POST одного користувача через A та B не перевищують спільний active-ліміт.
- Конкурентні POST різних користувачів не перевищують загальний outstanding-ліміт.
- Перевір момент commit, виключи завершення задач під час тестового виміру квоти; кількість усіх коли-небудь прийнятих задач не є active-лічильником.
- Після кінцевого стану можна створити наступну задачу.
- Для детермінованого контролю черги допустимий приватний test harness, що тимчасово керує dispatcher; не додавай публічний HTTP-обхід.

5. Призначення:
- Одна queued за одночасних claim A/B запускається лише одним worker.
- Дві допустимі важкі задачі справді обчислюються різними процесами одночасно.
- У кожному процесі максимум один важкий worker.
- Доказ відсутності дублювання повинен спостерігати самі claim/start-події у тестовому harness, а не лише один фінальний рядок, який могли переписати.
- Старий/неправильний claim token не записує progress чи terminal.

6. Прогрес:
- Під час pending пошуку GET через B читає реальні монотонні лічильники задачі A.
- Running ніколи не має 100%; completed одразу має result, 100 і finished_at.
- Пізній/in-flight progress не змінює вже кінцевий стан і не стирає cancel.
- Записів у польоті та пам'яті для progress обмежена кількість.

7. Скасування:
- Queued cancel не запускає worker.
- Running A скасовується POST через B; thread A реально зупинено до записаного cancelled, наступна queued працює.
- Повторний cancel та cancel кінцевого стану безпечні.
- Гонка queued claim/cancel дає узгоджений стан.
- Гонка finish/cancel не перетворює прийняте скасування на пізній completed і не змінює вже committed completed.

8. Помилки:
- Короткий серверний timeout на реальному довгому пошуку → failed/timeout, припинений worker, наступна job виконується.
- Реальна помилка worker/контрольований error fixture → failed/worker_error й звільнений ресурс, HTTP не падає.
- Відмова БД — 503 для залежних API, а не успішна порожня історія. Health=200, ready=503.
- Після відновлення БД queued доступні, втрачені running не лишаються назавжди, пізній старий результат не перемагає terminal.

9. Перезапуск і смерть:
- Історія, вхід, прогрес/стан і готові результати збережені після перезапуску серверів; непрострочена сесія також працює.
- Заверши A примусово під час real running. Живий B або наступний запуск переводить втрачений running у failed/worker_lost після контрольованого deadline/grace.
- Не потрібен повторний запуск тієї самої задачі; перевір, що вона не виконується двічі.
- Відновлення не позначає ще допустиму активну задачу іншого сервера втраченою.

10. Завершення:
- SIGINT/SIGTERM за active job зупиняє worker, dispatcher і HTTP, звільняє Pool/таймери.
- У БД коректний server_shutdown або раніше запитаний cancelled.
- За відмови запису лишається можливість worker_lost-відновлення, а не нескінченне очікування.
- Після завершення тестів не лишилося HTTP-процесів, worker чи випадкових тестових схем.

Для синхронізації перевірок можна чекати фактичного стану/події, використовувати контрольовану конфігурацію й короткий deadline. Не сповільнюй production-алгоритм і не додавай в нього sleep, щоб гарантовано побачити running. Довга робота — той самий реальний пошук; error fixtures використовуються лише для сценарію аварії.

Перевір також:
- 256 KiB job/body та 16 KiB auth/body або фактично обрані узгоджені межі; поганий JSON=400, Content-Type=415, Origin=403.
- GET limits повертає актуальні безпечні параметри.
- Компактну стабільну пагінацію й active-фільтр, без необмеженого SELECT/відповіді.
- HTTP лишається доступним під час двох важких обчислень; POST не очікує їх завершення.
- Стани/result читаються через будь-який сервер, а не лише через той, що виконував.

Регресія обов'язкова:
- npm run typecheck, npm run build.
- Попередні 11 unit, 36 route/HTTP і 13 справжніх PostgreSQL auth integration-тестів.
- TS/built route demo; не повторюй великий benchmark без зміни алгоритму чи нової невирішеної причини.
- Production/dev HTML/JS/CSS, API-проксі, health/ready, авторизація й API-404.
- Якщо браузер став доступний, закрий перевірку наявних форм. Якщо ні — вона залишається відкритою, а HTTP не видається за browser pass.

Виправ проблеми в межах блоку. Не послаблюй тести для приховування гонок. Якщо правильна БД/дозволи недоступні, заверши незалежне, чітко познач перевірки заблокованими й не оголошуй весь блок готовим.

Створити веб застосування, backend якого здатний коректно обслуговувати трудомісткі запити користувачів.

Прикладами таких запитів можуть бути задачі: розв"язування системи рівнянь, метод скінченних елементів, розпізнавання образів, обробка зображень та інші, на вибір студента. 

Особливості:
1) Повинна бути обмежена максимальна трудомісткість одної задачі (кількість невідомих, час обчислення).У разі перевищення - помилка або відмова у виконанні. (Перевірку вхідних даних задачі можна виконати ще на клієнті (frontend)).
2) Оскільки запити трудомісткі, клієнт повинен інформуватись про хід виконання задачі (відсоток/етап виконання).
3) Клієнт повинен мати доступ до історії результатів виконання задач, переглядати стан поточної задачі (див. пункт 1.), скасувати виконання задачі, запустити виконання нової задачі. (максимальна кількість задач повинна бути обмежена, необхідні дані зберігатись в базі даних)
4) Авторизація клієнта (з використанням https (+бали))

---------------------------------------- Найважливіша частина завдання ---------------------------------------------
5) Веб застосування повинне забезпечувати т.з. балансування навантаження як мінімум для 2-ох серверів. 
(для цього повинен бути застосований так званий load balancer, в його ролі може виступати і сам веб сервер, а задачі виконуватись на кількох серверах застосувань (application server)).
---------------------------------------------------------------------------------------------------------------------------------


----------------------------------------- Додаткові бали --------------------------------------------------------------------------
6) (+бали) Якщо всі ресурси системи вичерпані, клієнт повинен бути повідомлений про те, що його запит поставлено у чергу та інформуватись про приблизний час очікування.
7) (+бали) Горизонтальне розширення за рахунок автоматичного запуску нових серверів (віртуальні машини, контейнери), максимальна кількість повинна бути обмежена.
8) (+бали) Панель адміністратора для моніторингу всіх запущених процесів та навантаження на систему серверів.
