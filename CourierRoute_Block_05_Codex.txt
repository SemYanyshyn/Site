2. ВИКОРИСТАЙ ФАКТИЧНІ КОНТРАКТИ БЛОКУ 4

GET /api/jobs/limits
  { route: { maxPoints, maxIterations, timeoutMs, maxCoordinate }, maxActivePerUser }

POST /api/jobs
  RouteInput = { warehouse: {x,y}, points: [{x,y}, ...], iterations, seed? }
  202 JobDetails, Location: /api/jobs/:id; у відповіді вже зафіксована queued та фактичний seed.

GET /api/jobs?limit=20&offset=0
  { jobs: JobSummary[], limit, offset }
  Порядок created_at DESC, id DESC; без input/result у списку.
  status=active означає queued/running; можливий один конкретний status.
  limit 1–50, offset 0–1000000. total/hasMore сервер зараз не повертає.

GET /api/jobs/:id
  JobDetails = JobSummary + input, а result лише за completed.
  Summary: id, status, progress, cancelRequested, createdAt, updatedAt,
  startedAt, finishedAt, executedBy; error {reason,message} лише за failed.
  Progress: stage preparing/searching/finishing, completedIterations,
  totalIterations, percent.

POST /api/jobs/:id/cancel
  Тіло {}. Queued → cancelled/200. Running → running із cancelRequested=true/202.
  Кінцевий стан → незмінний 200; через гонку це може бути і completed.

401 — немає чинної сесії; 400/413 — вхід або розмір; 429/USER_ACTIVE_LIMIT — особиста квота; 503/SYSTEM_OUTSTANDING_LIMIT — місткість системи; 503/DATABASE_UNAVAILABLE — БД. Чужий і невідомий id мають однаковий 404/JOB_NOT_FOUND. Помилка має {code,message}.

3. ФОРМА Й ПЕРЕВІРКА ВХОДУ

Спочатку після підтвердженого входу завантаж актуальні /api/jobs/limits. Показуй фактичні maxPoints, maxIterations, timeoutMs і maxActivePerUser простими словами. Timeout — серверна межа, а не гарантія тривалості й не поле для зміни користувачем. За помилки limits не вигадуй значення: поясни стан, дай повторити читання й не запускай неперевірений вхід.

Мінімальний формат введення:
- Два підписані поля X/Y складу; початково 0,0.
- Багаторядкове поле доставок: одна точка на рядок у форматі «x y», роздільник — пробіл або табуляція. Під полем короткий приклад і пояснення десяткової крапки. Порожні рядки можна ігнорувати; для некоректного рядка вкажи його номер.
- Поле кількості ітерацій: додатне ціле, не більше отриманого maxIterations. Обери помірне початкове значення в дозволеній межі, наприклад min(1000000, maxIterations); серверний максимум при цьому не змінюй.
- Необов'язковий seed: порожнє поле означає відсутній ключ у POST; явно введений 0 має залишитися нулем. Допустиме ціле 0…4294967295. Пояснення: однакові вхід/seed/бюджет роблять пошук відтворюваним; автоматичне значення після прийняття видно в деталях.

Не обов'язково додавати редактор із сотнями окремих рядків, drag-and-drop чи інтерактивне редагування карти. Одного зрозумілого способу введення достатньо. Дозволений один малий приклад із наявного examples/route-small.json для заповнення форми; він нічого не надсилає й не імітує результат. Генератори, готові «демонстраційні результати» й автоматичний запуск при відкритті не потрібні.

Клієнт перевіряє до POST:
- Склад і кожна доставка мають рівно два скінченні числа; модуль координат ≤ maxCoordinate.
- Щонайменше одна доставка, не більше maxPoints; рахуй кількість і відхиляй надмірний текст до зайвого створення великих структур.
- Від'ємні та дробові координати дозволені. Однакові координати НЕ видаляй: це різні точки доставки, як у серверному алгоритмі.
- iterations і seed — цілі в межах. Порожнє числове поле не перетворюється на 0 через Number(''); parseFloat не повинен прийняти «12abc» чи мовчки відкинути третю координату.
- Не обрізай/не округляй значення до дозволених меж. Пояснюй помилку й зберігай введене для виправлення.

Серверна валідація залишається остаточною, клієнтська її не замінює. Не імпортуй у Vite модулі з node:crypto, pg чи серверним executor. Використовуй браузерно безпечні спільні типи/чисті допоміжні функції або окремий невеликий parser форми, з перевіркою відповідності серверним межам.

Під час POST кнопка запуску заблокована, подвійний click не створює дві задачі. Після 202 вибери прийняту задачу, онови active/історію й почни читання прогресу. Користувач може подати наступну задачу, якщо квота дозволяє; редагування форми не змінює вже прийнятого запису.

400/413/429/503 показуй українською, без втрати вводу. Розрізняй особистий ліміт, заповнену чергу й недоступну БД. Локальний active-count може бути підказкою; через іншу вкладку він застаріває, тому серверна відповідь вирішальна. Не створюй додаткових задач для «перевірки ліміту».

Після мережевої помилки/timeout POST не повторюй його автоматично: commit міг уже відбутися. Повідом «Запит міг бути прийнятий. Оновіть історію перед повторним запуском» і запропонуй безпечне читання. Не додавай нову систему idempotency чи міграцію лише для цього блоку.

4. СТАНИ, ПОЛІНГ І СКАСУВАННЯ

Показуй фактичний стан із БД:
- queued → «У черзі». Можна сказати «Очікує призначення виконавцю». Не стверджуй, що ресурси гарантовано вичерпані; queued буває і коротким етапом перед claim. Немає вигаданих секунд або номера в черзі.
- running → «Виконується»; preparing → «Підготовка», searching → «Пошук маршруту», finishing → «Завершення».
- completed → «Завершено», результат і 100%.
- cancelled → «Скасовано», без результату.
- failed → «Помилка», безпечне українське пояснення error.message і доречний доступ до форми нової задачі.

Показуй percent та completedIterations/totalIterations з відповіді, а не власний таймер чи приріст на кожному polling. Running ніколи не відображай як 100%, зокрема 99.999 після округлення! Відформатуй його так, щоб 100 було лише за completed. Реальна коротка задача може перейти від queued одразу до completed між двома читаннями — це коректно, не розтягуй анімацією чи sleep. Для cancelled/failed не заповнюй індикатор до 100.

Кнопка «Скасувати» доступна для власної queued/running. Відправляє POST {} тільки відповідній задачі. Поки запит виконується, захисти від дубльованого натискання. За 202/cancelRequested=true покажи «Запит на скасування прийнято. Очікуємо зупинки» та продовжуй polling. Не перейменовуй running у cancelled локально. Завершення підтверджує наступний серверний стан; 200 completed через гонку слід показати як completed. Помилка cancel не означає зупиненого worker.

Полінг:
- Один керований цикл, орієнтовно раз на 1000 мс для активних задач і вибраної pending задачі. Не створюй setInterval для кожного рядка чи новий таймер при кожному render.
- Не накладай однакові запити, якщо попередній ще не завершено. Наступне читання плануй після завершення; ручне оновлення й cancel узгодь з цим циклом.
- Completed/cancelled/failed деталь не опитуй без потреби; інші активні задачі продовжують оновлюватися. Вся історія не повинна отримувати окремий detail-запит для кожного рядка на кожному tick.
- Active API має limit максимум 50, а настроюваний maxActivePerUser — до 100. Якщо UI показує всі незавершені задачі/їх кількість, дочитай потрібні обмежені сторінки; не вважай перші 50 завжди повним переліком. Без безмежного циклу пагінації.
- Мережевий збій/503 не перетворюй на порожню успішну історію чи failed самої задачі. Збережи останні дані з явним написом, що їх не вдалося оновити; обмежене повторне читання/відновлення без POST і без busy loop.
- При зміні вибраної задачі пізній detail попередньої не має переписати нову. Використай AbortController та/або лічильник покоління запиту; одного abort без перевірки актуальності може бути недостатньо, якщо відповідь уже обробляється.
- Таймери/запити прибираються при виході й завершенні роботи сторінки. Немає необмеженого накопичення listeners, promises чи замикань на старих масивах.

5. АВТОРИЗАЦІЯ, ІСТОРІЯ ТА ВІДНОВЛЕННЯ

Збережи реєстрацію, вхід, відновлення через /api/auth/me та вихід. Реєстрація сама не створює сеанс: поточний сценарій «зареєструватися, потім увійти» залишається. Пароль не зберігай; сесія тільки в наявній HttpOnly-cookie, без JWT/localStorage.

Jobs UI та приватні дані доступні після підтвердження /me або login. За 401 від jobs припини polling, очисть приватний стан і покажи вхід із поясненням завершення сеансу. За 503 не повідомляй, що пароль неправильний чи сеанс гарантовано завершений.

Після успішного logout очисть список/деталі/схему/приватний ввід і відміни запити. Познач нове покоління сеансу, щоб запізнілі відповіді користувача A не з'явилися після його виходу або входу B. Це стосується також limits/history/detail та завершення POST/cancel. Не зберігай масиви задач, координати, результати чи cookie в localStorage. Немає потреби додавати збереження чернеток між сеансами.

Історія:
- Список лише з GET /api/jobs поточного користувача; не синтезуй його з локальних результатів.
- Рядок має зрозумілий стан, дату створення, коротку довідку про прогрес/помилку та дію «Переглянути».
- Сторінки по 20, «Назад»/«Далі» або еквівалент. API не повертає total, тому не вигадуй загальну кількість/останню сторінку. Повна сторінка дозволяє перевірити наступну; порожня наступна обробляється зрозуміло. Offset не перевищує серверну межу.
- Після власного створення доречно повернути історію на першу сторінку. Періодичне оновлення не повинно скидати вибір користувача/його чернетку чи самовільно повертати з кожної сторінки на першу.
- Detail запитуй окремо для вибраного id. 404 означає недоступну/відсутню задачу, без висновку про її чужого власника.
- Вхід, параметри, seed і результат історичної задачі бери з її збережених input/result. Поточний draft форми не має змінювати схему або цифри старого результату.

Після reload віднови сеанс і прочитай active/історію з БД. Можна вибрати найновішу активну, інакше останню задачу. Немає повторного POST при reload або автоматичного повторного обчислення старого запису. Закриття сторінки та logout самі по собі не скасовують вже прийняту job. Нова задача створюється тільки явною дією користувача.

6. ПОКАЖИ ЗБЕРЕЖЕНИЙ РЕЗУЛЬТАТ І СХЕМУ

Лише за completed з перевіреним RouteResult покажи:
- «Найкращий знайдений маршрут» і коротке пояснення, що пошук наближений.
- Сумарну length в умовних одиницях. initialLength можна показати як довжину початкового маршруту, якщо це допомагає зрозуміти результат; не додавай порівняння різних алгоритмів.
- Порядок відвідування: склад → доставки за order → склад. Нуль у order — склад; deliveries мають індекси 1…N, посилаються на input.points[index-1]. Не сортуй результат заново.
- Фактичний seed, iterationsCompleted/iterationsRequested, elapsedMs із правильною назвою «Час роботи алгоритму». Це не час очікування в черзі та не повний час від POST.
- Для trivial_input/zero_length коротке зрозуміле пояснення швидкого завершення; 0 виконаних ітерацій не перетворюються на запитаний бюджет.

SVG без зовнішньої карти/бібліотеки:
- Полілінія або сегменти точно за result.order; старт і повернення на склад, усі точки у відповідних координатах.
- Склад візуально відрізняється й має позначення; доставки впізнавані за номерами, а текстовий порядок доступний окремо від зображення. Для щільних наборів не перетворюй 500 підписів на нерозбірливу пляму; жодні доставки з даних не видаляються.
- Рівний масштаб X/Y, достатні поля й коректне вписування в доступну область. Якщо Y екрану інвертується, зроби це послідовно для точок/ліній/підписів; візуальна геометрія має відповідати евклідовій.
- Від'ємні/дробові координати, усі X однакові, усі Y однакові, всі точки збігаються та дуже малі допустимі числа не дають ділення на нуль, NaN/Infinity чи обрізаного складу. Для нульового діапазону є безпечний запас.
- Responsive viewBox; схема не розтягує сторінку ширше екрана. Довжину бери з перевіреного серверного result, а не з пікселів SVG.
- Якщо всі координати збігаються, поясни накладання; текстовий список зберігає окремі доставки.

Не обчислюй simulated annealing/матрицю повторно в браузері, не запускай Web Worker як другий обчислювальний backend і не показуй часткову схему як готовий result за failed/cancelled. Попередній результат не повинен лишатися під заголовком нової running задачі.

7. ДОСТУПНІСТЬ І ПОВЕДІНКА ІНТЕРФЕЙСУ

- Семантичні form/label/button, зрозуміле повідомлення біля помилки, видимий focus і доступ з клавіатури.
- Progress має доступну текстову назву/значення; стани не відрізняються лише кольором. aria-live для основних змін без надмірного озвучування всього документа на кожному tick.
- Loading/empty/error/retry — справжні окремі стани: немає порожнього екрану чи вічного spinner після відмови.
- Кнопки блокуються тільки за доречної pending дії; важке серверне обчислення не блокує всю сторінку, читання історії чи введення нової задачі.
- Автооновлення не перебудовує сфокусовані поля так, щоб губилися курсор/текст, і не перехоплює focus без дії користувача.
- На широкому та вузькому екрані, орієнтир 360 px, поля/кнопки доступні. Довгі UUID/числа/порядок маршруту переносяться або мають локальний доречний scroll, без горизонтального переповнення всієї сторінки.
- Текстові значення з API рендери через textContent/безпечні DOM-методи. SVG створюй із перевірених чисел та контрольованих атрибутів; не вставляй неперевірені серверні дані через innerHTML.

8. ПЕРЕВІРКИ

Заверши необхідні перевірки самостійно. Наявні користувацькі процеси/БД не зупиняй. Для власних перевірок використовуй вільні порти; збережи виправлення auth-тесту щодо Vite port. Безпечний тестовий доступ, паролі та cookie не виводь і не коміть.

Автоматизовані перевірки клієнтської логіки на node:test та наявному інструментарії:
- Parser: допустимі від'ємні/дробові координати, дублікати, одна/максимум доставок, завеликий ввід, порожні поля, номер поганого рядка, зайва координата/сміття/NaN/Infinity, межі iterations і seed з валідним 0 та відсутнім seed.
- Відповідність клієнтських меж фактичним RouteLimits, без імпорту серверних Node-модулів у клієнт.
- Геометрія схеми: відомий квадрат, правильна індексація складу/доставок і замикання; від'ємні, вироджені та співпалі координати дають скінченні значення й рівний масштаб.
- Значуща асинхронна логіка: пізній detail не перемагає новий вибір; відповіді старого сеансу не повертають приватні дані після logout/login; polling не накладає запити/не розмножує таймери; cancel202 не стає локальним cancelled; невідомий результат POST не повторюється автоматично; running99.999 не показується як100.

Для ізольованої логіки можна контрольовано підміняти fetch/час. Це перевірка клієнтського стану, а не доказ справжньої БД чи браузерного відображення. Не пиши тести, що лише повторюють присвоєння констант або замінюють весь застосунок макетом. Вибери невелику структуру модулів, яку можна перевірити без саморобного фальшивого браузера.

Обов'язкова регресія:
- npm run typecheck і npm run build.
- Усі попередні 87 тестів: 11 unit + 36 route/HTTP + 13 auth PG + 3 jobs unit + 24 jobs PG/HTTP; нові клієнтські перевірки додай до npm test і документуй команду на кшталт npm run test:client.
- Справжній PostgreSQL із наявним TEST_DATABASE_URL, окремою перевіреною тестовою БД, випадковою схемою й cleanup. Guard host/port/database/URL/DNS і nonsuperuser роль не послаблюй. Немає правильної БД — це блокування, не skip/pass.
- TS/built CLI лишаються працездатними. Великий benchmark без зміни алгоритму повторювати не потрібно.
- Production HTML/JS/CSS, Vite dev/proxy, auth/ready/health та API-404 після змін клієнта.

Браузерне функціональне приймання є окремою потрібною перевіркою цього UI. Спочатку перевір доступні підключення/інструменти. Якщо підключеного браузера немає, використай доречний реально доступний локальний браузерний інструмент, якщо він працює в середовищі. Не встановлюй зайвий набір залежностей лише для формальної появи browser-команди й не називай HTTP або unit-тести візуальним pass.

У доступному браузері на справжньому застосунку перевір:
1) реєстрацію → вхід → відновлення після reload → вихід;
2) limits і відмову невалідного вводу без зайвого POST;
3) запуск малого квадрата, правильний результат/схему/seed=0;
4) справжню важку задачу: actual queued/running/progress, responsive UI, скасування до підтвердженого cancelled, запуск наступної;
5) кілька власних активних задач у квоті та зрозумілий 429; без вигаданого ETA;
6) відкриття історичного результату, зміна draft без зміни його схеми, наступну сторінку історії, reload без нового POST;
7) втрату сеансу/401, мережеву відмову/503 і відновлення, без чужих/застарілих приватних даних;
8) клавіатуру, вузький екран, відсутність console errors та помилок завантаження ресурсів.

Тестовий браузер використовує ізольований сеанс і окрему тестову схему; не виходь з реального сеансу користувача й не зупиняй його PostgreSQL заради симуляції помилки. Наявний guard тестової БД та підхід до випадкової схеми можна перевикористати. Для спостереження running використовуй реальну роботу та очікування фактичного стану, а не sleep в алгоритмі. Моки окремого сценарію інтерфейсу позначай як моки, не як end-to-end.

Якщо браузер реально недоступний, заверши всі незалежні частини й дай точний короткий ручний сценарій. У звіті розділи «код і автоматизовані перевірки завершені» та «інтерактивне/візуальне приймання заблоковано». Не оголошуй браузер перевіреним, не приховуй блокування й не переходь самостійно до блоку 6. Успішні результати попередніх виконавців/керівника не видавай за свої поточні запуски.

Створити веб застосування, backend якого здатний коректно обслуговувати трудомісткі запити користувачів.

Прикладами таких запитів можуть бути задачі: розв"язування системи рівнянь, метод скінченних елементів, розпізнавання образів, обробка зображень та інші, на вибір студента. 

Особливості:
1) Повинна бути обмежена максимальна трудомісткість одної задачі (кількість невідомих, час обчислення).У разі перевищення - помилка або відмова у виконанні. (Перевірку вхідних даних задачі можна виконати ще на клієнті (frontend)).
2) Оскільки запити трудомісткі, клієнт повинен інформуватись про хід виконання задачі (відсоток/етап виконання).
3) Клієнт повинен мати доступ до історії результатів виконання задач, переглядати стан поточної задачі (див. пункт 1.), скасувати виконання задачі, запустити виконання нової задачі. (максимальна кількість задач повинна бути обмежена, необхідні дані зберігатись в базі даних)
4) Авторизація клієнта (з використанням https (+бали))

---------------------------------------- Найважливіша частина завдання ---------------------------------------------
5) Веб застосування повинне забезпечувати т.з. балансування навантаження як мінімум для 2-ох серверів. 
(для цього повинен бути застосований так званий load balancer, в його ролі може виступати і сам веб сервер, а задачі виконуватись на кількох серверах застосувань (application server)).
---------------------------------------------------------------------------------------------------------------------------------


----------------------------------------- Додаткові бали --------------------------------------------------------------------------
6) (+бали) Якщо всі ресурси системи вичерпані, клієнт повинен бути повідомлений про те, що його запит поставлено у чергу та інформуватись про приблизний час очікування.
7) (+бали) Горизонтальне розширення за рахунок автоматичного запуску нових серверів (віртуальні машини, контейнери), максимальна кількість повинна бути обмежена.
8) (+бали) Панель адміністратора для моніторингу всіх запущених процесів та навантаження на систему серверів.
