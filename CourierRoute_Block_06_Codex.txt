1. ЗБЕРЕЖИ ПРАВИЛА СПІЛЬНОЇ ЧЕРГИ

Поточні default: JOBS_MAX_ACTIVE_PER_USER=3, JOBS_MAX_OUTSTANDING=100, JOBS_POLL_INTERVAL_MS=250. Квота active/outstanding охоплює queued+running, включно з cancel_requested до фактичної зупинки й terminal у БД. Кінцева історія квоту не витрачає. Ці числа — наші налаштування, не числа викладача.

Збережи:
- Спільний короткий admission advisory transaction lock, обидві квоти та INSERT в одній READ COMMITTED транзакції на одному client. За особистої квоти 429/USER_ACTIVE_LIMIT, за місткості системи 503/SYSTEM_OUTSTANDING_LIMIT без зайвого запису.
- 202 тільки після commit; HTTP POST не чекає CPU-результату. Зайняті worker не є причиною відхилити допустиму задачу, доки є місце у спільній черзі.
- Найстарішу queued за created_at/id атомарно бере один процес через FOR UPDATE SKIP LOCKED та UPDATE/commit. Worker стартує після commit.
- Один реальний worker на процес; явна claim-резервація не звільняється лише через executor.busy=false, доки не узгоджено terminal у БД. Немає локальної черги.
- Progress/terminal захищені id/running/private claim token. Прийнятий у running cancel має пріоритет при звичайній фіналізації, worker фізично зупиняється до cancelled.
- Timeout, worker_error, database_unavailable, server_shutdown і worker_lost не підміняються completed чи добровільним cancel.
- Втрачені running завершуються за вже збереженим lost_after, без автоматичного повторного обчислення. Не скорочуй цей deadline лише через застарілий heartbeat.

Нинішній effective worker-lost grace — max(configuredGrace, 2×poll + 21000) мс; default 21500. Він захищає обмежені claim/progress/terminal DB-операції та не збільшує timeout worker. Збережи його зміст. Реєстр виконавців і ETA не повинні ламати чи замінювати цей механізм.

2. МІНІМАЛЬНИЙ СПІЛЬНИЙ РЕЄСТР ВИКОНАВЦІВ

Додай нову SQL-міграцію, наприклад 003_executor_registry.sql. 001_auth.sql та 002_jobs.sql незмінні. Новий runner/required migrations, readiness та build мають знати нову схему. Міграції явні, повторювані й конкурентно безпечні; попередні користувачі/сесії/jobs/results зберігаються.

Достатньо однієї невеликої таблиці реєстру з:
- instance_id, тим самим UUID, який повертає /api/health поточного HTTP-процесу;
- started_at, last_seen_at та/або expires_at у timestamptz;
- ознакою готовності приймати нові claim/завершення процесу;
- фактичною зайнятістю свого одного слота; поточний job id за наявності, без приватного claim token у публічному представленні.

Можна уточнити назви/стани під фактичну інтеграцію. Не потрібні таблиці історії heartbeat, метрики на кожен tick, PID/hostname/адреси користувача чи нова платформа моніторингу. Для нинішньої архітектури місткість процесу дорівнює одному важкому worker; не визначай число слотів за кількістю CPU.

Реєструється тільки реально запущений екземпляр. Новий процес після restart має новий instanceId. Не створюй фіктивні записи «сервер 1/2» із конфігурації й не вважай описані майбутні replicas живими.

Heartbeat та строк свіжості:
- Усі дати для порівняння свіжості задає PostgreSQL, а не годинники різних машин або браузера. Наприклад, clock_timestamp() для поновлення; для одного розрахунку ETA зафіксуй один DB timestamp.
- Розумні початкові значення: EXECUTOR_HEARTBEAT_INTERVAL_MS=1000, EXECUTOR_LEASE_TTL_MS=15000. Вони — проєктні рішення. Перевір цілі скінченні межі та співвідношення: TTL має покривати кілька інтервалів і bounded DB-операцію; малий TTL не повинен оголошувати нормальний процес втраченим. Наприклад, interval 100–5000, TTL до 60000 та TTL ≥ 3×interval+6000 мс за нинішніх pool timeout. Узгодь обрані значення з фактичними DB-таймаутами й запиши їх у .env.example/README/тести.
- Максимум один heartbeat SQL у польоті, без накопичення черги promises або накладених timer-циклів. Запізнілий callback не повертає stopping у ready.
- Оновлюй стан зайнятості при доречних переходах та heartbeat. Слот зайнятий і під час claim/finalization, а не лише всередині CPU-пошуку.
- Внутрішній pause/resume тестового harness не означає здатність прийняти наступну задачу: paused процес не додає доступної майбутньої потужності, доки його не resume. Не додавай для цього публічний endpoint чи production env-обхід.

У розрахунку ресурсів враховуй лише свіжі екземпляри, які приймають claim. Busy екземпляр залишається майбутнім слотом, його час доступності ненульовий. Stopping/прострочений екземпляр не додає потужності. Для busy/idle зіставляй реєстр із running у jobs: щойно committed claim не можна вважати вільним лише через попередній idle heartbeat. За неповної/суперечливої інформації дай обережну оцінку чи unknown, а не вигадану вільну потужність.

Це облік для планування/оцінки, не заміна job claim token і row locks. Розуміння «heartbeat прострочено» не дає права перепризначити ту саму running іншому worker чи оголосити її скасованою до фізичної зупинки.

Інтеграція lifecycle:
- Не починай queued job, якщо власна реєстрація не підтверджена або втрачений надійний DB-контроль. Відновлення реєстрації/heartbeat після БД-відмови обмежене й не створює busy loop. Збережи вже реалізовану фізичну зупинку власного worker за інфраструктурної відмови.
- Shutdown припиняє нові claim/heartbeat, відмічає екземпляр недоступним для нової роботи за доступної БД, зупиняє worker і завершує доступний terminal до Pool.end. Дочекайся вже виданих операцій; жодних нових SQL після закриття pool. Збережи загальну п'ятисекундну межу, без нескінченних спроб.
- Якщо запис stopping неможливий або процес отримав SIGKILL, його виключає TTL; jobs відновлюються за своїм lost_after. Ці два часи мають різне призначення.
- Health залишається liveness навіть за БД-відмови. Ready перевіряє потрібну схему; busy не робить HTTP-сервер неготовим. Нові критерії готовності, якщо необхідні для коректного startup, опиши та перевір без підміни HTTP-ready ознакою вільного CPU.
- Прямий executor-run старого route harness та CLI зберігають свої перевірки/завершення. CLI не починає вимагати PostgreSQL чи реєстрацію.

3. РОЗРАХУЙ ПРИБЛИЗНИЙ ЧАС ДО ПОЧАТКУ JOB

Винеси невеликий чистий estimator, який отримує обмежений snapshot і повертає ETA. DB-читання та математичну оцінку розділи настільки, щоб перевірити модель без підміни справжніх інтеграційних тестів.

Вхід snapshot:
- Одна DB-дата розрахунку.
- Реальні свіжі виконавці та їхній стан.
- Running із instanceId, started_at, timeout, stage/counters/cancelRequested та необхідними часовими полями.
- Queued перед цільовою задачею в порядку created_at/id, з кількістю доставок і бюджетом, без повних координат/результатів чужих користувачів.
- Обмежена вибірка реальних завершених вимірювань для оцінки трудомісткості.

ETA — очікування до старту цільової job, не час завершення всього розрахунку. Тривалість самої цільової задачі до цього очікування не додається.

Паралельні слоти враховуються явно:
1) Для кожного придатного екземпляра визнач приблизний момент звільнення: idle — близько нуля/передачі, busy — очікуваний залишок та доречний запас фіналізації.
2) Послідовно розклади queued-попередників на слот, який звільниться найраніше, додаючи оцінену тривалість кожної попередньої задачі.
3) Найраніше звільнення після цих попередників — приблизний час початку цільової.

Це наш простий модельний підхід, не вимога викладача до конкретної формули. Не замінюй його «довжина черги × константа» чи «весь час / число серверів»: вони ігнорують різні залишки та бюджети. Немає потреби в ML, симуляторі ОС чи оптимізації розкладу. Порядок SKIP LOCKED є орієнтиром; оцінка не обіцяє точний порядок старту при всіх гонках.

Оцінки тривалості мають походити з даних:
- Для running з достатнім прогресом можна оцінити залишок за реальними completed/total та elapsed від DB started_at. Не діли на нуль; preparation/finishing потребують окремої обережної обробки. Врахуй чинний серверний timeout і факт, що requested cancel ще не звільнив ресурс.
- Для queued використовуй просту пояснювану модель за бюджетом і кількістю точок, підживлену обмеженою вибіркою completed. Наприклад, близькі розміри/невеликі групи за кількістю точок і виміряний час на ітерацію; за потреби запас підготовки/збереження. Обери й документуй конкретну формулу, її параметри та обмеження. Не вставляй швидкість з чужої машини або benchmark як універсальну константу.
- Для часу зайнятості слота корисне вимірювання finished_at−started_at; result.elapsedMs — тільки час алгоритму і не охоплює весь startup/збереження. Чітко вкажи, яку тривалість використовуєш і як враховано решту.
- Failed/cancelled, нульові/нечислові виміри та швидкі trivial_input/zero_length із 0 ітерацій не повинні навчати звичайний важкий пошук як миттєвий. Відомі тривіальні вхідні випадки можна оцінювати окремо, не видаляючи deliveries і не запускаючи алгоритм в estimator.
- Вибірка історії обмежена, наприклад останні 200 придатних вимірів; не скануй/не вивантажуй усю історію на кожному GET. Індекси та SQL мають відповідати фактичному запиту. Додай потрібний індекс у нову міграцію, не редагуй 002.

Холодний старт:
- Якщо ще немає придатних вимірів/прогресу, дозволена явно позначена консервативна попередня оцінка з фактичного server timeout та невеликого поясненого запасу передачі. Це не «виміряний середній час» і не гарантія верхньої межі очікування.
- Коли з'явилися реальні дані, модель повинна їх використовувати, а не завжди повертати timeout. Немає фальшивих початкових completed, прихованих обчислювальних прогрівів чи sleep.
- Якщо немає жодного свіжого придатного виконавця або даних недостатньо для осмисленого прогнозу доступності — estimatedWaitMs=null і зрозуміле пояснення unknown. Не повертай 0/Infinity/NaN як «час очікування» за відсутності серверів.

Усі ETA скінченні, невід'ємні й обмежені за дозволеним snapshot. Для повністю зайнятих слотів не позначай ресурс уже вільним через cancelRequested або completedIterations=total, поки terminal/фіналізація ще не завершені. Дозволений невеликий явний запас; називай його налаштуванням моделі, не виміром.

Оцінка може зростати/зменшуватися після нових вимірів, завершення, cancel, timeout, появи чи зникнення виконавця. Не змушуй її штучно монотонно спадати й не веди в браузері незалежний точний countdown. Це приблизна оцінка на момент snapshot, не обіцянка часу старту.

4. БЕЗПЕЧНИЙ SNAPSHOT ТА КОНТРАКТ API

Розшир наявний GET /api/jobs/:id додатковим полем queue тільки для queued. Збережи структуру інших полів і поведінку решти endpoints. POST /api/jobs може повертати прийняту queued без ETA: наступний звичайний detail GET її отримає. Не затримуй 202 заради «точнішого» прогнозу.

Мінімальний контракт queued detail:
queue: {
  estimatedWaitMs: number | null,
  calculatedAt: string,
  queuedAhead: number,
  executorCount: number,
  basis: 'measured' | 'mixed' | 'timeout' | 'unavailable'
}

- estimatedWaitMs — ціле число мілісекунд очікування до початку або null.
- calculatedAt — DB-дата snapshot у валідному ISO-форматі.
- queuedAhead — агрегована кількість queued-попередників, не лічильник незавершених усіх станів і не кількість користувачів.
- executorCount — свіжі придатні процеси, включно з тимчасово busy; не число вільних слотів і не HPA desired replicas.
- basis дає відрізнити оцінку з реальних даних, суміш із fallback, лише timeout-fallback та відсутню оцінку. Документуй точні правила.

За running/completed/cancelled/failed поле queue відсутнє; стару ETA не переносити у новий стан. Початковий POST snapshot без queue допустимий. Нова queued detail-відповідь GET повинна містити актуальний queue або передбачувану помилку читання, а не приховано продовжувати показувати старий прогноз.

Безпека й узгодженість:
- Чинна сесія, user id тільки з неї, Cache-Control no-store. Чужий і невідомий id однаково404, malformed UUID400. Не додавай неавторизований /queue/servers endpoint.
- Назовні тільки дані власної job та потрібні агрегати. Не передавай ids/координати/логіни/result інших користувачів, claim tokens, env/DB URL, PID чи приватну таблицю реєстру.
- JobDetails і queue належать одному узгодженому короткому snapshot: не відповідай running з ETA старої queued через гонку між окремими читаннями. Підійде одна SQL-команда з CTE або коротка read-only REPEATABLE READ транзакція на одному client. Візьми один DB timestamp для цього розрахунку; не утримуй admission lock заради прогнозу.
- Snapshot може застаріти одразу після відповіді, це нормально; його внутрішні поля мають бути узгоджені. Cancel/claim/новий heartbeat не блокуються на довгому estimator-транзакційному lock.
- З БД отримуй мінімальні скаляри. Кількість deliveries можна взяти через jsonb_array_length(input->'points'), не копіюючи всі чужі координати в Node. Не виконуй N+1 SQL для кожної задачі.
- Усі queued-попередники в межах чинного maxOutstanding мають бути враховані; не обрізай їх мовчки на 20/50/200 через UI pagination. MaxOutstanding до 10000 уже обмежує обсяг. Історичні samples мають окремий невеликий LIMIT.
- Прогноз не змінює jobs/status/cancel/claim і не записує ETA в БД на кожен polling: це похідне значення на момент читання, не новий журнал.
- DB-збій → передбачуваний503, health продовжує працювати. Не підміняй відмову SQL нульовою чергою/двома вигаданими серверами чи успішною «невідомою» відповіддю, якщо стан не вдалося прочитати.
- Час і кількість SQL обмежені; узгодь їх з 10-секундним клієнтським timeout. Прогноз не повинен блокувати HTTP або створювати необмежений SQL/CPU-запит. Використовуй наявний pool і параметризовані значення.

5. ОНОВИ НАЯВНИЙ UI БЕЗ ЗАЙВИХ ФУНКЦІЙ

У деталях queued покажи:
- «У черзі» та приблизне очікування, наприклад «Орієнтовно 12 с до початку». Значення з API, не власна константа.
- Коротко «Оцінка може змінюватися». Для timeout-fallback явно «Попередня оцінка за серверною межею часу», без удаваних статистичних вимірів.
- Для null — «Наразі немає доступної оцінки часу очікування»; якщо executorCount=0, поясни відсутність доступного виконавця. Немає 0 секунд замість unknown.
- Поки після POST queue ще не прочитано — «Оцінюємо час очікування…», без помилкового прогнозу.

Для дуже малого додатного часу покажи «менше секунди», для нульового прогнозу вільного слота — очікування призначення; не стверджуй, що job уже running. За потреби використовуй секунди/хвилини з помірним округленням, не десяткові мілісекунди з удаваною точністю. Агрегати queuedAhead/executorCount можна залишити другорядними; вони не повинні замінити саме час.

ETA оновлюється в наявному керованому polling вибраного detail. Не роби новий timer на кожну картку і не додавай detail-запит кожному рядку історії на кожен tick. Показ стану queued у списках зберігається; для оцінки користувач відкриває деталі потрібної задачі.

Runtime-валідація queue на клієнті обов'язкова: nullable скінченне ціле, допустимі межі лічильників, дата, basis та зв'язок зі статусом. Початковий create без queue приймається; некоректна нова metadata не будує брехливу цифру чи не падає всім UI. Онови спільні типи й browser-safe parser, не імпортуй серверний estimator/pg у Vite.

При зміні на running/terminal прибери блок очікування. CancelRequested саме по собі не означає завершення або вільного worker. Збережи:
- 100% тільки за completed, running99.999 не округлюється до 100;
- збережений result/SVG незалежно від draft;
- один цикл polling, покоління сеансу/вибору та abort для всіх нових даних;
- 401/logout очищують приватний стан; 503 лишає останні дані з явним попередженням про невдале оновлення. Стара ETA в такому разі позначена неоновленою, а не видається за поточну;
- жодного повторного POST на reload, за мережевої помилки чи через countdown;
- клавіатуру, focus, читабельність і відсутність overflow на360 px.

Забери поточний напис «Час очікування поки не оцінюється» і онови доречні пояснення. Не переробляй увесь дизайн чи авторизацію заради однієї queue-секції.

6. ПЕРЕВІРКИ НА СПРАВЖНІХ ПРОЦЕСАХ І БД

Додай npm-команду на кшталт test:queue та включи доречні автоматизовані сценарії до npm test. Не додавай залежність, якщо достатньо node:test/наявного pg/fixtures. Онови старі очікування переліку міграцій/readiness для нової схеми, не послаблюючи їх.

Чисті estimator/config/client тести:
- Межі heartbeat/TTL і співвідношення з DB-бюджетом, без NaN/Infinity/нульового інтервалу.
- Нуль, один, два виконавці; stale/stopping/paused виключені; busy слот не дорівнює вільному.
- Неоднакові залишки двох worker та неоднакові бюджети queued, правильна симуляція найранішого слота. Наприклад, за залишків [10000,30000]мс і одного попередника тривалістю6000мс ETA цільової=16000мс при нульовому тестовому запасі. Власна тривалість цільової не додається.
- Немає історії/прогресу → позначений timeout-fallback; реальні придатні samples → measured/mixed і залежність від трудомісткості, а не незмінна константа.
- Preparation, finishing, cancelRequested, малий/нульовий elapsed, 0 completed, trivial/zero та погані samples не дають ділення на0 або швидкості нескінченність.
- За фіксованих вхідних оцінок вилучення queued-попередника не збільшує очікування, додавання idle слота не збільшує його. Не вимагай монотонності від реального прогнозу після зміни даних/продуктивності.
- Nullable metadata, безпечне форматування, очищення ETA при running/terminal/logout, stale-відповіді сеансів/вибору та стан читання після503. Нові тести мають перевіряти поведінку, а не дублювати присвоєння констант.

Справжній PostgreSQL:
- Тільки наявний guard явного TEST_DATABASE_URL, окрема БД з тестовим ім'ям, перевірка фактичних host/port/database/DNS/URL overrides, nonsuperuser роль та випадкова схема. Робочу БД не очищуй. Cleanup прибирає тільки власні процеси/схеми/профілі.
- Міграція001→002→003 зберігає користувача/сеанс/job/result; clean/repeat/concurrent built runner; ready503 до повної схеми й200 після неї; SQL включений у build.
- Два незалежні production HTTP-процеси A/B зі спільною БД, справжніми executor/worker та різними instanceId. Це не два app-об'єкти й не моки heartbeat/алгоритму.

Ключовий наскрізний сценарій пункту 6:
1) У БД підтверджені два свіжі екземпляри; кожен має один слот.
2) A і B одночасно виконують по справжній важкій задачі. Читай фактичний running/progress, не додавай sleep у production-алгоритм.
3) Допустима третя задача приймається202, лишаєтьсяqueued, не створює третього worker у вже зайнятих процесах, читається через A і B.
4) Її detail показує coherent queue і скінченну числову ETA з поясненою basis, тоді як all slots зайняті. HTTP продовжує відповідати.
5) Звільнення/cancel/timeout однієї попередньої задачі реально звільняє слот після worker exit/terminal. Queued починає виконуватися саме один раз; ETA зникає, з'являється running.

Додаткові сценарії:
- Queued-попередник іншого користувача врахований у моделі; назовні видно лише агрегати, жодних його ids/координат/result. Чужий GET/cancel однаково404. Немає необмеженого list/table endpoint.
- Скасування queued змінює оцінку наступної; cancel running не звільняє ресурс до фактичної зупинки. Старі claim/progress/terminal не переписують новий стан.
- Нова свіжа реєстрація процесу додає реальну потужність; graceful stop прибирає її. SIGKILL перестає враховуватися після фактичного TTL, а його running відновлюється окремо за lost_after, без повторного виконання.
- Немає жодного придатного виконавця → null/unknown. Допустиму queued не відхиляй лише через тимчасову відсутність worker, якщо є місткість. Повернення виконавця робить її доступною для claim.
- Cold snapshot → позначена fallback; після завершеної нетривіальної справжньої job наступна оцінка використовує виміряні дані. Зафіксуй метод і вплив різних бюджетів.
- Наявні особиста/загальна квоти залишаються атомарними під одночасними POST A/B; повна черга дає503, без фальшивого queued. MaxOutstanding і UI pagination не змішуються.
- БД-відмова →503 для залежних API, health200, відсутність нових непідтверджених claim/heartbeat busy loop. Власний worker реально припиняється; відновлення БД повертає реєстрацію/чергу, історія збережена.
- Shutdown за idle/busy та БД-відмови має обмежений час, зупиняє таймери/worker/pool, без SQL після Pool.end. Пізній heartbeat не оживляє stopping. Попередній route-HTTP harness з прямим executor також коректно завершується.
- Обсяг читання history/queue обмежений, немає full координат всіх jobs/N+1, estimator не утримує глобальний admission lock. Додай осмислену перевірку максимального дозволеного snapshot на чистому estimator, без створення тисяч CPU-workers.

Для детермінованої синхронізації допускається приватний IPC harness і контрольовані fixtures/час у unit. Важкий наскрізний пошук, реєстрація, heartbeat/expiry, jobs/cancel та міжпроцесна БД мають бути справжніми. Не додавай production backdoor, не пом'якшуй гонки тестовими sleep усередині алгоритму.

Не обіцяй точність до фіксованого відсотка, якого не доведено. Для кількох справжніх queued задач запиши в звіт predicted wait на конкретний calculatedAt, фактичне очікування до started_at, basis та коротке пояснення відхилення. Не підганяй цифри/модель під один тест і не видавай консервативний холодний fallback за точний прогноз.

Регресія:

- TS/built CLI незалежні від БД. Великий benchmark без зміни алгоритму не повторюй.
- Production/dev HTML/JS/CSS, справжній API proxy, /api.ts не перехоплюється, health/ready, auth/ownership/API404.

Можна розширити чинний driver з ізольованим профілем/тестовою схемою; це вже працюючий інструмент, не потрібно знову зупинятися лише через відсутність connected Browser.
