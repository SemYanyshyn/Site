4. СПРАВЖНІЙ TRAEFIK LOAD BALANCER

Встанови Traefik підтримуваної закріпленої версії офіційним Helm chart із tracked values або компактними перевіреними manifests/RBAC. Обери ОДИН основний відтворюваний спосіб і задокументуй його. Не виставляй dashboard/API Traefik без авторизації; їхня публікація для цього блоку не потрібна. Обмежуй controller/provider нашим cluster/namespace та необхідними дозволами наскільки дозволяє обраний спосіб.

Весь UI та /api надходять через один зовнішній HTTPS origin Traefik. Traefik має бачити готові pod endpoints і реально розподіляти HTTP-запити між двома app pod. Для Kubernetes Ingress явно залиш nativeLB=false (Service annotation service.nativelb=false або рівнозначна настройка для обраного provider), щоб Traefik балансував pod endpoints, а не мав один ClusterIP як backend. Узгодь IngressClass/provider/версії. Sticky cookie не потрібна: сесії спільні в PostgreSQL.

Додай малий діагностичний response header X-Instance-Id для API, сформований тільки з реального UUID цього процесу, вже видимого в /api/health. Це дозволяє підтвердити, який pod обробив login/me/cancel/logout; не вводь для цього endpoint вибору сервера або довіру до клієнтського заголовка. Header і health.instanceId мають збігатися. Не повертай claim token, hostname, credentials чи чужі дані.

Розрізняй два механізми: Traefik розподіляє HTTP-запити; PostgreSQL dispatcher атомарно розподіляє важкі jobs. POST може обробити A, а job виконати B — це коректно. Не прив'язуй задачу до HTTP-процесу, який прийняв її. Не вимагай строго A/B/A/B при паралельному browser polling: доведи участь обох за серією реальних відповідей й trace.

Не додавай автоматичний retry middleware, який може повторити неідемпотентний POST jobs/register/login/cancel після невизначеного результату. Наявне правило клієнта «POST міг бути прийнятий → спочатку історія» збережи. Відмова pod не дає права непомітно повторно обчислити його running job. TTL лише прибирає executor із ETA; worker_lost визначається збереженим lost_after, без повторного запуску.

Після вилучення/NotReady pod Traefik має перестати надсилати йому нові запити після узгодження EndpointSlice/provider. Виміряй фактичний перехід; не обіцяй нуль помилок у момент аварії. Busy pod залишається маршрутизованим і відповідає на HTTP. Якщо обидва pod NotReady через БД, публічний Traefik може повернути 503; це не суперечить локальному /api/health=200 у живому pod. Тести й звіт мають розрізняти ці рівні.

5. HTTPS, COOKIE, ORIGIN ТА ДОВІРА ДО СЕРТИФІКАТА

TLS завершується на Traefik, до app Service у локальному кластері можна використовувати HTTP. Це захищає browser→Traefik; не заявляй про TLS app→DB чи повне шифрування всіх внутрішніх з'єднань. HTTPS вимагає справжнього TLS handshake, а не просто redirect/заголовка.

Для локального localhost підготуй проектну CA та server certificate з правильним SAN і обмеженим строком; ключі/сертифікати й generated TLS Secret зберігай тільки в ігнорованій .local з належними правами. CA private key не завантажується до Kubernetes; Traefik отримує лише потрібний server key/chain через kubernetes.io/tls Secret у належному namespace. Повторний deploy повторно використовує придатні credentials/CA, а не змінює довіру без потреби. Секрети не потрапляють у Git/ZIP/image, kubectl output чи звіт.

Не потрібні ACME/Let's Encrypt для локального hostname, платний домен, публічний DNS або автоматична зміна системного Keychain. Відтворювані HTTPS API-перевірки виконуються з явною довірою до нашої CA (наприклад curl --cacert / Node https ca), зі звичайною перевіркою hostname/строку/ланцюга. Перевір негативно неправильну CA/hostname. curl -k, NODE_TLS_REJECT_UNAUTHORIZED=0, rejectUnauthorized:false і глобальний --ignore-certificate-errors не є доказом перевіреної довіри й не повинні бути штатним способом запуску.

Для реального Chrome використовуй свіжий тестовий профіль із доступним способом довіри до локальної CA; якщо platform trust автоматизувати неможливо, допускається тільки ізольований test-process із SPKI allowlist конкретного попередньо перевіреного сертифіката. Окремо перевір chain/hostname звичайним TLS-клієнтом та явно опиши межу browser-доказу: SPKI-виняток не означає довіри CA у звичайному профілі користувача. Не змінюй його реальний Chrome/Keychain. У README коротко поясни локальну CA й ручне налаштування довіри для звичайного браузера, якщо воно потрібне; не називай таку відсутню довіру відмовою шифрування.

У Kubernetes APP_ORIGINS містить точний зовнішній HTTPS origin, включно з портом; COOKIE_SECURE=true. HttpOnly, SameSite=Lax, Path=/, host-only і правильне видалення cookie збережені. За публічним HTTP немає обробки auth/jobs — тільки коректний redirect на HTTPS з потрібним портом. Mutation guard продовжує перевіряти Origin, JSON/size; немає wildcard або заміни Origin довіреним X-Forwarded-Host. Старий локальний HTTP dev з COOKIE_SECURE=false та Vite має продовжувати працювати у своєму окремому конфігураційному режимі.

Не додавай app.set('trust proxy',true) навмання. Наявна Secure-cookie задається явною конфігурацією, тому trust proxy не потрібен лише заради її прапорця. Якщо нова поведінка використовує req.secure/protocol/ip, обґрунтуй межу довіри до реального proxy та очищення/перезапис X-Forwarded-* у Traefik; підставлений клієнтом заголовок не повинен змінювати origin/auth/TLS-рішення. Не додавай HSTS preload або глобальну браузерну політику для localhost заради цього блоку.

6. ОБОВ'ЯЗКОВІ ПЕРЕВІРКИ

Зберігай assertions старих тестів, а не послаблюй їх під нові manifests. Тестові URL/паролі/cookie/CA-ключі не друкуються. Використовуй наявний guard TEST_DATABASE_URL: окрема тестова БД з тестовим ім'ям, перевірка фактичних host/port/database, роль без superuser, випадкова схема. Не очищуй робочу БД.

Інфраструктурні destructive/fault перевірки роби лише у власному тестовому namespace/кластері й окремій БД, створених цим сценарієм. Основний host PostgreSQL та чужі namespace/pod/процеси не чіпай. За тестового hostname/порту узгодь Ingress/SAN/APP_ORIGINS і локальне resolver-рішення в самому тесті, без змін /etc/hosts. Scripts мають перевіряти context/namespace/ownership до видалення будь-якого власного pod. Після тестів прибери тільки власні тимчасові ресурси; демонстраційні дані/PVC збережи.

Не послаблюй наявний DB guard заради port-forward: адреса/порт SQL-сервера за тунелем можуть відрізнятися від адреси клієнтського URL. Стару PG-регресію можна повторити на наявній окремій host test-БД. Для SQL-спостереження у deployment-сценарії використовуй перевірений доступ усередині нашого namespace/тестового контейнера або явно перевірену відповідність тунелю конкретному PostgreSQL Service/pod/БД. localhost за тунелем сам по собі не доводить ідентичність БД. Паролі не передавай у CLI-аргументах.

Регресія: npm ci, typecheck, build, повний npm test (до змін 156 = 107 non-DB + 49 PG), TS/built CLI; production/dev HTML/JS/CSS, Vite ^/api(?:/|$) та /api.ts. Нові змістовні тести додай зверху; кількість не є самоціллю. Великий benchmark без зміни алгоритму не повторюй. Повтори наявні 16 Chrome-груп для старого локального сценарію, якщо відповідний код змінено, і додай реальний HTTPS/LB browser-сценарій для контейнерного розгортання.

Реальний наскрізний сценарій через ОДИН HTTPS URL, без звернення клієнта до портів A/B:
1) Підтвердь два Ready app pod з одним image/source, два endpoint, два різні фактичні instanceId. Серія HTTPS /api/health отримує обидва; API header збігається з UUID процесу. Не використовуй два app-об'єкти одного процесу або фіктивні відповіді.
2) Реєстрація/вхід через Traefik. Одну й ту саму Secure-cookie використовуй для /me, які реально обслуговують A і B. За header trace доведи спільну сесію, а не два незалежні входи.
3) Через балансувальник створи дві справжні важкі jobs у межах лімітів. Одночасно спостерігай два running з різними executedBy, що відповідають A/B; кожен pod має один зайнятий слот. HTTP залишається доступним під час actual search. Жодних sleep у алгоритмі.
4) Третя допустима job приймається 202, чекає queued у PostgreSQL та має числову ETA при двох зайнятих слотах. Читай progress/history/detail через обидва фактичні handler instanceId з тим самим сеансом. Не запускай третій worker в зайнятому процесі, не повертай executor_busy замість спільної черги.
5) Запит cancel важкої job має реально пройти через handler з іншим instanceId, ніж її executedBy. Якщо початковий безпечний cancel потрапив до власного pod, за наступним перевіреним сценарієм отримай потрібний cross-process trace; не додавай «route to server B» endpoint. Доведи фізичну зупинку/terminal і звільнення слота; queued стартує один раз, ETA зникає. Наявні claim/token-прогрес інваріанти збережені.
6) Completed результат/історія/SVG доступні після reload та з іншого handler. Другий користувач не читає і не скасовує чужу job (404); квоти залишаються спільними й атомарними для паралельних запитів через Traefik.
7) Logout, реально оброблений іншим handler, відкликає ту саму сесію: наступні /me/jobs через A і B отримують 401. Cookie Secure/HttpOnly/SameSite/Path та її видалення перевірені без друку токена.

Відмови й збереження стану:
- Graceful SIGTERM одного власного busy app pod: його worker фізично завершується, запис за доступної БД — failed/server_shutdown, registry перестає приймати claim. Інший pod обслуговує запити; Deployment замінює втрачений pod, новий має інший instanceId, а історія/сеанси не зникають. Не видавай цю заміну за HPA.
- Окрема аварійна втрата власного busy pod/process: після TTL він не дає ETA-потужності, його running не перевиконується і після збереженого lost_after стає failed/worker_lost. Заміна Kubernetes не є дозволом повторити цю job. Врахуй справжній grace, не прискорюй тест зміною production-інваріанта.
- Власний тестовий PostgreSQL restart з тим самим PVC: користувачі/сесії/готові jobs/results збережені, ready тимчасово неуспішний, liveness живого HTTP не залежить від БД. Після відновлення ймовірні infrastructure-failed jobs мають чесний стан, нові jobs працюють. Окремо зафіксуй публічний 503 Traefik, коли немає Ready endpoints.
- Неправильний Origin/TLS CA/hostname, HTTPS-cookie й HTTP→HTTPS redirect перевірені негативними випадками. Немає повторного POST або витоку секретів через логи/заголовки/assets.
- Busy pod не виключається readiness; два реально зайняті worker не роблять UI/API недоступними. Точні затримки й convergence запиши за фактом, без недоведених гарантій.

Chrome: реальні HTTPS auth/create/progress/cancel/history/result/reload/logout через Traefik; viewport desktop і 360 px, фактичний огляд PNG, немає overflow/console/resource errors/mixed content. Перевір форму з клавіатури, читабельність queue ETA/помилок і збереження input після API-відмов. Browser test не замінюй curl, HTTP не називай візуальним прийманням. Скриншоти залишаються тільки внутрішніми ігнорованими доказами.

Ключовий сценарій запускається відтворюваною командою (наприклад npm run test:deployment), завершується pass/fail, має bounded timeout, збирає безпечний trace instanceId/jobId/status, прибирає свої тестові ресурси й не скидає користувацькі дані. Schema validation/client dry-run/render Helm — корисні додаткові перевірки, але не доказ запущених replicas/TLS/LB. При реальному блокері заверши незалежне, наведи точний blocked сценарій і не позначай пропуск успіхом.
