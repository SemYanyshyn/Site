Додай один Metrics Server сумісної стабільної версії для нашого Kubernetes 1.36.1/arm64. Перевір офіційний compatibility matrix і release, закріпи точні image/version/digest та вихідну версію manifests у deploy/versions.json і tracked файлах. Потрібні справжні Metrics Server Deployment/Service/ServiceAccount/RBAC/APIService й доступ до kubelet; не досить контейнера Running. Перевір APIService v1beta1.metrics.k8s.io Available, /apis/metrics.k8s.io/v1beta1/nodes і namespaced pod metrics, kubectl top pods. Для реальних app containers мають надходити CPU/RAM, timestamp та window; дані оновлюються. Не підставляй константи, process uptime, кількість jobs чи вигадані CPU-відсотки замість вимірів.

Metrics Server — cluster add-on з необхідними cluster-scoped RBAC/APIService, на відміну від app/HPA. Перед установкою перевір точний наш kubeconfig/context/owner. Не перезаписуй чужий APIService/add-on з тим самим ім'ям і не видаляй kube-system/чужі ClusterRole. Нові ресурси познач власником; повторна установка ідентичної версії безпечна. Сумісний уже наявний сторонній add-on можна використовувати read-only, явно записавши походження, без привласнення його cleanup. HTTP-pod продовжує не отримувати service account token/прав Kubernetes.

Для локального kind спочатку з'ясуй фактичний TLS/адресний доступ до kubelet. Якщо потрібен --kubelet-insecure-tls через локальний kubelet certificate, допускається вузьке документоване виключення ТІЛЬКИ для нашого kind add-on, а не глобальне вимкнення TLS чи зміна зовнішнього HTTPS застосунку. Опиши також фактичну перевірку TLS aggregation API→Metrics Server за обраним офіційним manifest: не заявляй про перевірку сертифіката там, де її вимкнено. Поясни, що для зовнішнього production-кластера потрібні належні CA/сертифікати. Не послаблюй authn/authz Kubernetes та не використовуй kubeconfig insecure-skip-tls-verify для обходу налаштування.

Один Metrics Server достатній для single-node kind. HA install з вимогою кількох nodes, Prometheus, історична БД метрик та новий metrics endpoint застосунку тут не потрібні. Метрики — періодичні знімки для autoscaling, а не точний профайлер чи архів продуктивності. Установлення й очікування даних мають bounded deadlines і безпечну діагностику причин FailedDiscovery/FailedScrape/403/TLS, без секретів.

3. HPA AUTOSCALING/V2 ТІЛЬКИ ДЛЯ APP

Створи tracked HPA для Deployment app у нашому namespace:
- apiVersion autoscaling/v2; scaleTargetRef apps/v1 Deployment app.
- minReplicas=2, maxReplicas=4. Ці межі не змінюються заради проходження тесту.
- Реальна CPU utilization metric для app pod/container; для поточного одного app container достатньо Resource cpu. Позитивні CPU requests обов'язкові. Не використовуй фіктивний external metric або CPU іншого stress-pod.
- Явні scaleUp/scaleDown behavior з обмеженою швидкістю й стабілізацією. Не потрібні alpha/неперевірені feature gates або поля, які доступні лише в новішому Kubernetes.

Розумний початковий набір: target CPU averageUtilization=70%, scaleUp stabilization=0 та максимум +2 pod за 30 с, scaleDown stabilization=180 с та максимум -1 pod за 30 с. Можеш обґрунтовано уточнити ці параметри за фактичними вимірами; кінцеві значення мають бути однаковими в коді/manifests/README/тестах, не приховано зменшеними тільки в acceptance run. min/max 2/4 збережи.

Utilization — відношення використання CPU до requests, не до ліміту й не до всього Mac. За requests=250m ціль 70% означає приблизно 175m на app pod; насичений один worker близько 1 CPU може давати utilization понад 100%. У CPU входять потоки цього контейнера. Зафіксуй, що саме збирається і як читати одиниці. Не перенось benchmark іншої машини у метрики.

Контролер працює періодично, використовує часові знімки та консервативно поводиться з missing/unready metrics. Не обіцяй миттєвий scale-up чи точну секунду scale-down. Спостерігай HPA conditions/currentMetrics/currentReplicas/desiredReplicas/events, справжні pod/UID/Ready та EndpointSlices. Pending pod і desiredReplicas=4 не є чотирма готовими виконавцями.

Межа 4 стосується app Deployment цього namespace, не PG/Traefik/Metrics Server чи ізольованого паралельного тестового namespace. Під звичайним HPA-навантаженням фактичних app replicas/доступних слотів не більше 4. Окремо узгодь rollout: чинний maxSurge=1 може створити п'ятий pod при desired=4. Для дотримання межі під час оновлення обери maxSurge=0 з придатним maxUnavailable або інше доведене рішення; не обіцяй нуль недоступності, якщо його немає. Terminating pod рахуй окремо до фізичного виходу, а не приховуй. Саме maxReplicas не доводить жорстку межу всіх живих процесів під час rollout, це точно поясни у звіті.

Збережи обробку SIGTERM: нові claim припиняються, worker зупиняється, доступний terminal стає failed/server_shutdown, registry більше не додає доступну потужність; при аварії — звичайні TTL/lost_after. Scale-down не повинен непомітно губити running або перетворювати їх на добровільний cancel/completed. Основний acceptance: після припинення нових POST дай прийнятим jobs нормально завершитися, а потім дочекайся автоматичного 4→2. Стабілізація має прибирати дергання від коротких провалів CPU. Вона не є гарантованим drain протоколом; не заявляй, що HPA сам знає про зайняті jobs, і не додавай окремий контролер/довгий shutdown для такого твердження.

4. REPLICAS, ПОВТОРНИЙ DEPLOY, STOP І START

Нині provision щоразу застосовує app.json з replicas:2. Під HPA це може скидати фактичне розширення. Передай керування полем spec.replicas контролеру HPA: у повторному HPA-managed apply його не потрібно задавати. Початковий bootstrap/явний restart з нуля може встановити базові 2 до передачі керування. Перехід із попереднього client-side apply/last-applied виконай без випадкового скидання до default 1; врахуй офіційний порядок передачі поля. Не підміняй це циклом читання поточного числа й постійного kubectl scale.

HPA — єдиний автоматичний writer бажаної кількості app. Повторний deploy під навантаженням не видаляє HPA, не масштабує 4→2/1 й не втрачає дані. Не міняй ConfigMap/checksum без фактичної зміни, щоб простий repeat не перезапускав busy pod. Явне оновлення образу/конфігурації може робити rollout із задокументованою поведінкою jobs.

Інтегруй Metrics Server/HPA в наявний deploy:local та deploy:status. Новий чистий локальний запуск має діставати працездатне HPA-середовище, а не вимагати непомітної ручної команди після «успішного deploy». Відрізняй додаткову діагностику від обов'язкового кроку. deploy:status показує HPA/metrics availability і реальні replicas, не друкує Secrets.

deploy:stop має стійко залишати app/Traefik/PG зупиненими зі збереженими PVC/credentials/CA, а HPA не повинен боротися зі зупинкою. Обери й перевір явну паузу/видалення тільки власного HPA перед scale-to-zero або документований maintenance mode сумісної версії; наступний deploy:local коректно відновлює дві базові replicas й autoscaling. Це навмисний stop, не порушення активного minReplicas=2. Cluster add-on не видаляй при звичайній зупинці namespace; не чіпай паралельні тестові HPA/чужі ресурси.

Базова регресія блоку 7 навмисно перевіряє рівно два pod. Збережи її окремим явно статичним тестовим режимом provision з HPA disabled, не послаблюючи assertions до «будь-яка кількість». Новий autoscaling-тест має окремий HPA-enabled namespace із повним реальним циклом. Це приватна можливість deployment harness, не новий публічний endpoint керування сервером. Production demo після блоку 8 має HPA enabled за основним documented шляхом.

5. СПРАВЖНЄ ОБМЕЖЕНЕ НАВАНТАЖЕННЯ

Додай відтворюваний driver/команду, наприклад npm run test:autoscale. Він створює власний випадковий namespace/test-БД із перевіреними owner/context, використовує той самий compiled image/TLS/Traefik і конфігурацію HPA, що й demo, починає з двох Ready pod, проходить 2→4→2 та прибирає свої тимчасові ресурси. Розширюй наявні helpers; не копіюй весь provision у другу незалежну реалізацію.

Масштабування виконує тільки HPA. У вимірюваній фазі заборонено вручну/скриптом ставити replicas=3/4, повторювати kubectl scale як autoscaler, підставляти HPA metrics/status, запускати сторонній CPU burner або збільшувати worker_slots. Дозволені початковий bootstrap 2 і явний cleanup/stop після завершення proof; вони не є доказом autoscaling.

Навантаження — справжні валідні route jobs через один HTTPS API origin, нормальна авторизація/cookie, реальні ітерації й збережений прогрес. Жодних sleep/artificial CPU loops у production-алгоритмі. Одна коротка job може закінчитися раніше наступного metric scrape, тому підтримуй обмежений потік задач довше циклів scrape/HPA/readiness. Не збільшуй ROUTE_TIMEOUT_MS, max iterations чи квоти спеціально для тесту; поточні container-ліміти 500/200 млн/30 с достатні для повторюваних справжніх задач.

Врахуй персональний active-limit=3: один власник не заповнить чотири worker. Використовуй кілька створених лише цим тестом звичайних користувачів, наприклад 3 власники/до 9 одночасно прийнятих незавершених jobs. Зберігай global outstanding=100. 429/503 не обходяться, тисячі необмежених POST не потрібні. Логіни/паролі/cookie тільки в пам'яті/приватному тимчасовому профілі, не trace.

Driver має явні скінченні межі: число користувачів, загальне число accepted jobs, одночасні jobs/HTTP, тривалість подачі та загальний deadline. Орієнтир для подачі — до 120–180 с, до 200 accepted і до 9 незавершених; підбери перевірені межі під реальну машину та запиши їх. Вони не є вимогою викладача. Якщо метрики/нові replicas не з'явилися в межах дедлайну, fail із діагностикою, а не нескінченне навантаження.

Термінальні результати зчитуються, slots backfill робиться тільки в межах лімітів. Не повторюй невизначений POST після transport failure: спочатку історія/узгодження, як у чинному клієнті. Не створюй дублікати задля проходження throughput. Локальні паузи між запитами в test driver допустимі як обмеження частоти, але не підробляють тривалість алгоритму.

Збирай часовий trace з фактичними timestamp/window метрик і окремим часом спостереження: app CPU/RAM у коректних одиницях, HPA current/desired/conditions, deployment replicas/ready/terminating, pod UID/instanceId, кількість queued/running/terminal і executedBy власних test jobs. Достатньо bounded polling раз на кілька секунд, не високочастотний monitoring сервіс. Вивід — whitelist без credentials/повних входів/result/claim token.

Нормальні jobs мають завершитися коректно. Не зараховуй систематичні OOM/timeout/worker_lost/server_shutdown під звичайним навантаженням як успішне масштабування. Якщо це сталося, знайди причину й повтори після виправлення; окремі навмисні fault-сценарії мають власні очікувані terminal. Після подачі навантаження дочекайся terminal всіх прийнятих задач, стабілізаційного вікна й фактичного повернення до двох без ручного scale. Остаточний deadline враховує цей реальний час, а не скорочує його підміною годинника.

6. ДОКАЗИ ПУНКТУ 7 ТА ПОВ'ЯЗАНІ ПЕРЕВІРКИ

Обов'язковий успішний наскрізний цикл:
1) Дві базові Ready replicas, той самий реальний app image, два різні UID/instanceId, два ready endpoint; HPA min/max=2/4, Metrics API працює, CPU samples свіжі, ScalingActive/AbleToScale мають придатний стан.
2) Реальні важкі jobs зайняли обидва worker; наявна спільна черга приймає наступні допустимі задачі, HTTPS health/me/jobs відповідають, ETA чесна. CPU зростає саме в app containers із цими worker.
3) HPA сам змінює desired replicas понад 2 і досягає 4; Kubernetes створює додаткові pod. Не вимагай обов'язкового проміжного 3, якщо контролер перейшов 2→4 за один крок. Зафіксуй conditions/events/час, Ready/EndpointSlices і нові реальні UUID.
4) КОЖЕН із двох додаткових процесів реально отримує й виконує хоча б одну route job. Доведи running з додатним прогресом та completed/коректний результат за executedBy, а не лише Ready/health. Одночасно спостерігай роботу чотирьох окремих слотів під сталим навантаженням; на кожен процес максимум один running. Наявні атомарні claim/token інваріанти збережені.
5) HTTP-балансування додає нові ready endpoints: відповіді через один HTTPS origin надходять від усіх чотирьох фактичних instanceId, сесія працює без повторного входу. Немає sticky session або endpoint вибору pod. Для достатнього trace використовуй bounded безпечні GET, не POST-retry.
6) Поки чотири слоти зайняті, queued detail відображає реальні свіжі executorCount=4 та приблизну ETA з PostgreSQL. HPA desiredReplicas/новий Pending pod не додаються в ETA наперед. У перехідному snapshot допустимий чесний unknown; дочекайся узгоджених даних, а не підробляй їх. Після виходу процесів registry виключає їх за stopping/TTL, executorCount зрештою відповідає двом живим, lost_after не скорочується.
7) Під тривалим навантаженням HPA й фактичні нормальні app replicas не перевищують 4, а мінімум у стабільному активному стані — 2. Тестовий driver не керує scale. Підрахунок не включає PG/Traefik/Metrics Server; окремо показуй terminating і rollout, якщо вони траплялися.
8) Після припинення нових POST всі прийняті звичайні jobs завершуються, CPU падає; після реального stabilization HPA сам повертає app до 2. Дочекайся фізичної зупинки зайвих процесів, двох Ready endpoints і узгодженого реєстру; history/results/session/SVG збережені, наступна small job працює.

Додаткові перевірки:
- Повторний звичайний deploy/config apply при HPA=4 не скидає replicas до 2/1 і не створює непотрібного rollout. Перевір передачу spec.replicas/last-applied, а не лише відсутність поля у файлі. Якщо повторний deploy очікує rollout, він має підтримувати поточний autoscaled desired, а не hardcoded 2.
- Stop із увімкненим HPA реально залишає app/Traefik/PG зупиненими; start відновлює app/HPA/HTTPS без зміни PVC/credentials/CA/історії. Не тестуй це руйнуванням робочих користувацьких даних; використовуй власний тестовий namespace та helpers. Для demo повторюваність перевіряй без скидання БД.
- Недоступні/відсутні придатні CPU metrics не трактуються як 0% і не призводять до вигаданого успішного scaling/scale-to-zero. Перевір реальний negative case в окремому тестовому оточенні, не вимикаючи спільний add-on під чужим/demo HPA. Можна вузько перевірити missing-metric/misconfiguration path власного тестового HPA та відновлення; тоді назви саме цей випадок, а не повну відмову Metrics Server. Покажи condition/reason та відновлення після повернення правильних даних.
- Не готовий pod/відсутні metrics, Pending через нестачу ресурсів або порушення owner/context дають чесний fail/diagnostic. Ніякого fallback на manual replicas чи чужий cluster. Pure tests конфігурації/парсингу/guards не видаються за доказ роботи контролера.
- Спільні auth/ownership/cancel/квоти/історія не залежать від 2/3/4 процесів. Перевір хоча б cross-handler читання/cancel та відмову чужого доступу під autoscaling; прийнятий cancel справді завершив worker. Test-only audit може підтверджувати один committed claim, не додавай для цього production-таблицю або публічний debug endpoint.
- Під normal downscale не втрачається acknowledged job; при окремій навмисній інфраструктурній втраті збережені причини/TTL/lost_after/відсутність повторного запуску. Не називай продовження обчислення там, де чинний сервер його зупинив як server_shutdown.

Регресія: typecheck/build, повний npm test (до цього блоку 168 = 119 non-DB + 49 PG), TS/built CLI. Збережи meaningful assertions та DB safety guard. Повтори test:deployment у явно статичному ізольованому режимі (10 deployment/fault + 9 HTTPS Chrome-груп) для зміненого provision/stop. Container/browser-набори повторюй відповідно до змінених image/runtime/client частин; незмінний старий UI не потребує нового великого benchmark. Наявні 16 локальних Chrome-груп повтори, якщо змінено відповідний client/auth/dev код. Чесно наведи, які старі набори реально перезапущено.

Коротка реальна HTTPS Chrome-перевірка під HPA: залогінений користувач читає свою queued job/ETA і поточний прогрес, серверні UUID/кількість виконавців змінюються без нового входу, history/result/reload залишаються коректними, після повернення до 2 працює нова job. Desktop/360 px без console/resource/mixed-content/overflow помилок; PNG справді оглянь. Якщо весь scale-cycle займає хвилини, browser observer можна поєднати з одним реальним API load run; другий повний стрес-тест лише заради скриншота не потрібний. Не додавай в UI деталі HPA, Kubernetes, pod чи CPU diagnostics замість майбутньої адмінпанелі.

7. ІЗОЛЯЦІЯ, ЧАС ТЕСТУВАННЯ ТА БЛОКЕРИ

Мережа/метрики/ролі/кластер/worker мають бути справжніми. Mock/unit потрібні тільки для доречної перевірки bounded config/парсингу/guards, не замінюють сценарій 2→4→2. Не підміняй control-plane clock, Metrics API або справжній алгоритм тестовими константами. Не вмикай HPA для старих статичних тестів приховано й не послаблюй їх до тривіальних assertions.

Зберігай точні context/owner перевірки та явний namespace для kubectl. Для cluster-scoped ресурсів окремо перевір власність кластера й конкретного object. Тести не зупиняють host PostgreSQL, demo чи чужі workloads і не скидають global metrics для всіх namespace. Наявний TEST_DATABASE_URL guard залишається; SQL через deployment helpers використовує власну test-БД/роль без superuser. Cleanup видаляє тільки власний test namespace/PVC/HPA/profile/forwarding і не видаляє спільний Metrics Server, потрібний demo.

Тривалий тест веди автономно до завершення з короткими зрозумілими повідомленнями: що виміряно, чи з'явилися нові екземпляри, чи виконують jobs, що залишилося до cooldown. Не роби один мовчазний blocking wait на кілька хвилин: використовуй bounded polling/збереження прогресу. Загальні deadlines та ліміти навантаження обов'язкові, продовження за межами бюджету не допускається.

Якщо Docker/мережа/Metrics API/право встановлення add-on справді недоступні, заверши незалежні код/manifests/scripts/документацію та доступні перевірки, потім назви точний blocker і мінімальну ручну дію. Не зупиняйся на пропозиції плану, якщо робота вже доручена й доступна. Не називай HPA реалізованим/перевіреним лише через наявність YAML або kubectl top, і не позначай blocked як pass/skipped success.
