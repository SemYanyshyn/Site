1. АВТОРИЗАЦІЯ АДМІНІСТРАТОРА ТА ЯВНЕ ПРИЗНАЧЕННЯ РОЛІ

У users і PublicUser вже є role user/admin. Використай наявні PostgreSQL-сесії та requireAuth, додай серверний requireAdmin. Кожний /api/admin/* перевіряє актуальні сесію та роль через PostgreSQL до читання загальних задач, повернення кешу або звернення до Kubernetes. Без сесії — 401, дійсний звичайний user — 403, дійсний admin — дозволений read. При БД-відмові — коректний 503, не довіра до раніше закешованої ролі.

Клієнтський role, прихована кнопка, localStorage, заголовок, query чи тіло запиту не надають прав. Публічна реєстрація як і раніше створює лише user; спроба передати role=admin не підвищує привілеї. Не роби першу реєстрацію автоматично адміністратором і не додавай hardcoded admin/password або bypass env для HTTP.

Додай невеликий операторський CLI для явної зміни ролі ІСНУЮЧОГО користувача за username на admin або user, наприклад admin:role з аргументами --username та --role. Параметризований SQL, валідація логіна/ролі, зрозумілий результат для невідомого користувача й ідемпотентний повтор; без паролів/URL у логах чи argv. CLI використовує роль застосунку, не superuser. Надай перевірені TS/built команди й варіант для власного Kubernetes deployment через операторський kubeconfig/owner guards. Це локальна дія оператора, не public API або додаткові pods/exec права HTTP-сервісу.

Не призначай admin довільному наявному користувачу і не змінюй чужі ролі автоматично. Для demo README має давати короткий точний шлях: зареєструвати свій звичайний login → явно призначити саме його CLI → увійти/оновити сеанс → відкрити панель. Для перевірок створи лише власні випадкові акаунти, явно надай одному admin і потім зніми для negative test. Це не блокер, що невідомий користувацький login не було вгадано заздалегідь.

Перевір зміну admin→user з чинною cookie через інший handler: наступний admin API має дати 403 навіть за прогрітого кешу. Logout/expiry/401 прибирають приватні admin-дані; 403 після втрати ролі закриває admin-панель без розкриття старого snapshot. Загальні endpoints не повертають password_hash, session/token hashes, cookie або credentials. Cache-Control: no-store для всіх admin API outcomes.

2. ДЖЕРЕЛА СТАНУ Й ТОЧНЕ ЗІСТАВЛЕННЯ ПРОЦЕСІВ

PostgreSQL є джерелом jobs, власників, progress/terminal/cancel і реєстру executor. Kubernetes — джерело фізичних app pod/UID/phase/Ready/terminating/restart та конфігурації Deployment/HPA; Metrics API — джерело CPU/RAM. Це різні часові знімки. Відобрази походження/час/доступність, а не обіцяй одну атомарну транзакцію між БД і Kubernetes.

Нині executor_registry містить process instanceId, але не pod UID. Додай явне зіставлення, наприклад валідовані POD_UID/POD_NAME/POD_NAMESPACE через Downward API і нову additive SQL-міграцію 004 з nullable metadata реєстру. Назви/деталі можеш уточнити, але UUID процесу залишається реальним health instanceId; не замінюй його на pod name. У host/npm dev metadata може бути відсутня. Старі рядки/користувачі/сесії/jobs/results зберігаються. SQL 001–003 незмінні, нова міграція явна, runner/checksum/build/readiness й fixtures знають її версію.

Під час rolling upgrade старі процеси ще можуть писати реєстр без нових колонок: additive nullable/default-схема повинна це дозволяти. Heartbeat має не більше одного SQL у польоті, зберігає DB clock/freshness, claim/finalization busy та bounded shutdown. Нові metadata не додають серійних DB round trips після commit claim й не змінюють 21000 мс резерв, TTL або lost_after. CLI маршруту лишається незалежним від PostgreSQL/Kubernetes.

Покажи реальні Pending/NotReady/Ready/terminating app pod, навіть якщо вони ще не зареєстрували executor. Для запису DB без підтвердженого pod-збігу чесно познач «немає зіставлення»/«поза Kubernetes», а не вигадуй CPU. Pod UID стабільний при container restart, instanceId змінюється: попередня свіжа lease того самого pod не є другим фізичним сервером. Старі/дубльовані/прострочені реєстрації показуй окремо від поточних pod і доступних слотів. Не склеюй їх за порядком рядків, hostname-припущенням або схожим коротким UUID.

Busy визначається чинними claim/running/finalization, не CPU-відсотком. Старий idle heartbeat не робить committed running вільним; cancelRequested не означає фізично звільнений слот. Expired executor з running job позначається недоступним, але job не стає failed до чинного lost_after. Дані моніторингу не перепризначають jobs і не змінюють їхній стан.

Для CPU/RAM зіставляй namespace + pod name + container name=app з поточним Kubernetes pod UID; якщо UID у Metrics API відсутній, не вигадуй його. Перевір timestamp щодо поточного pod/container start і не приписуй старий sample новому процесу після restart. Чесний короткий unknown під час переходу кращий за неправильне зіставлення. Застарілий sample не стає свіжим лише від нового HTTP GET.

Обмежуй читання реєстру: усі поточні pod, свіжі виконавці й виконавці незавершених jobs потрібні; необмежена багаторічна історія heartbeat — ні. Можна показувати обмежене недавнє вікно недоступних записів із явною межею, не обрізаючи мовчки поточні активні дані. Визначення available capacity узгоджене з чинною чергою/ETA, а не з HPA desiredReplicas.

3. KUBERNETES-ДОСТУП ТІЛЬКИ НА СЕРВЕРІ

Панельний backend читає Kubernetes API з app pod напряму по HTTPS з cluster CA і окремим ServiceAccount з мінімальними read-only правами власного namespace. Наявного Node HTTPS достатньо; не запускай kubectl/docker через HTTP-handler, не монтуй операторський kubeconfig/Docker socket і не додавай sidecar proxy лише заради читання. Браузер звертається тільки до відносних /api/admin/* через Traefik, не до Kubernetes/Metrics Server напряму.

Додай власні namespaced ServiceAccount/Role/RoleBinding та явно потрібний projected/автомонтований token лише HTTP-app контейнеру, який читає API; migration Job/worker не отримують його як аргумент/env. Використовуй короткоживучий bound token, врахуй його ротацію: не кешуй початковий токен назавжди, не створюй довгоживучий Secret-токен. Зберігай readOnly/nonroot rootfs, працездатність читання CA/token для UID 1000 і правильний shutdown запитів. Token, CA paths і сирі headers не потрапляють у клієнт чи логи.

Достатні права: get/list app pod, get Deployment app і HPA app, get/list pod metrics групи metrics.k8s.io у цьому namespace; за потреби get/list EndpointSlices для фактичних ready backends. Для named get застосовуй resourceNames, де це придатно. Dynamic pod list обмежується namespace/RBAC і серверним label/owner selector: не стверджуй, що сам RBAC list фільтрує довільні labels. Немає прав secrets, pods/exec, pods/log, mutation/scale/delete/roles/impersonate/cluster-admin, немає читання чужих namespace або всіх nodes заради цієї панелі.

Джерело конфігурації namespace/owner/API address — server deployment/Downward API, не HTTP query/body. Дозволені API paths фіксовані й параметри URL безпечно закодовані. Namespace/selector не можна підмінити клієнтом. Не виконуй HTTP fan-out по довільних адресах усіх pod; для списку станів достатньо bounded list-відповідей. Owner/context guards provisioning лишаються для створення ServiceAccount/RBAC; чужі об'єкти не перезаписуються.

Використовуй фактичний metrics.k8s.io/v1beta1 нашого Kubernetes 1.36.1/Metrics Server 0.9.0; не копіюй приклад v1 лише тому, що поточні docs вже описують новіший Kubernetes. TLS до API-server нормально перевіряється cluster CA/hostname, без rejectUnauthorized:false/глобальних bypass. Вузькі локальні kubelet/aggregation TLS-винятки Metrics Server з блоку 8 не поширюються на цей клієнт або app HTTPS.

Для npm dev поза Kubernetes передбач явний disabled-режим джерела інфраструктури: авторизація й DB-частина панелі працюють, CPU/RAM/Kubernetes статуси unknown з поясненням. Не вгадуй ~/.kube/config чи сторонній кластер, не повертай фіктивні два сервери/0% CPU. Тимчасовий збій Metrics API/RBAC не вимикає звичайний HTTP/jobs/liveness/readiness, якщо БД/схема справні.

4. МІНІМАЛЬНИЙ ТИПІЗОВАНИЙ ADMIN API

Запропонований компактний контракт: GET /api/admin/overview для summary/server/executor/HPA/metric source status та GET /api/admin/jobs з пагінацією й фільтром status, за потреби executedBy. Назви можеш уточнити, не множ вимоги на зайві endpoints. Зберігай shared DTO і runtime-валідацію зовнішніх даних та клієнтських відповідей, як у чинному jobs UI.

Overview має дати:
- Лічильники queued/running та terminal-станів, кількість поточних app/Ready/terminating і підтверджених виконавців/зайнятих слотів; чіткі назви показників, щоб desired/Ready/executors не змішувалися.
- HPA min/max/current/desired і короткий стан за фактичними даними; недоступний HPA не підставляється дефолтними 2/4 як спостереженням.
- Поточні app-сервери з реальними pod UID/name, process UUID за наявності, phase/Ready/restarts, registry freshness/busy/current job, часами й nullable CPU/RAM + declared requests/limits. Втрачені/неузгоджені реєстрації відокремлені.
- Час DB snapshot, час спостереження Kubernetes і фактичні timestamp/window метрик, status джерел ok/unavailable/disabled/stale/partial або еквівалентний чіткий контракт.

Jobs list показує всі власні й чужі задачі адміністратору: id, owner id/username, status, реальний stage/percent/iterations, created/started/finished/updated, executedBy, cancelRequested та безпечну failure reason. Для моніторингу не треба масово повертати input/result/coordinates або claims/паролі/SQL-повідомлення. Використовуй projection, а не SELECT * і подальше приховування секретів. Не змінюй контракт звичайних owner endpoints.

Пагінація: розумний default 20, максимум 50, валідовані цілі limit/offset, допустимі status/UUID, відмова невідомим/масивним query. Стабільне сортування created_at/id або інший узгоджений порядок; при однакових датах сторінки не стрибають. Усі SQL значення параметризовані, рядки сортування/колонки не надходять довільно з клієнта. Count і page належать узгодженому короткому snapshot або їхня допустима часова різниця явно описана.

Неповні інфраструктурні дані не перетворюй на нулі. Якщо DB/auth справні, а Kubernetes/Metrics недоступні, overview може повернути явний partial/degraded контракт з актуальною DB-частиною і last-known даними, позначеними stale з початковими часами. Якщо останніх даних немає — null/unknown. Provider 401/403 від Kubernetes є збоєм джерела, а не 401/403 людської сесії; не розлогінюй admin через ServiceAccount/RBAC-помилку. Справжній людський 401/403 обробляється окремо.

CPU quantity коректно перетворюється з n/u/m/cores; RAM — з фактичних Kubernetes quantities у байти/MiB зі скінченними межами. CPU — використані ядра за window, memory — working set. Якщо показуєш відсоток, явно визнач denominator request/limit й не clamp до 100%: utilization від 250m може бути понад 100. Агрегат CPU/RAM — тільки сума придатних samples app, з coverage, наприклад 3/4; часткова сума не видається за весь кластер або Mac. Відсутня RAM не означає «0 MiB».

Не повертай raw Pod/HPA JSON: whitelist достатніх полів. ServiceAccount token, secret refs/values, env, kubeconfig, IP/endpoint credentials, password_hash, session hashes, claim token та повні внутрішні errors не мають потрапити в JSON/HTML/логи/bundle. Так само помилкові відповіді й кеш не обходять проекцію та роль.

5. ОБМЕЖЕНІ ЧИТАННЯ, КЕШ І СВІЖІСТЬ

Панель не повинна створювати N+1 SQL/API calls по всій історії, новий запит на кожний рядок, безмежний watch або необмежений список. Достатньо кількох паралельних bounded read запитів до БД/Kubernetes. Обмежуй count/size зовнішніх відповідей та registry/job rows; за порушення меж не позначай обрізані дані повними.

Для admin HTTP визнач спільний абсолютний бюджет від middleware перед auth, включно з pool acquisition, SQL, Kubernetes, parsing/commit. Орієнтир — до 8 с, нижче чинного client request timeout 10 с; API-source запит до 2 с, reply до кількох MiB. Остаточні значення узгодь із pool/SQL limits і запиши в README/тести. Timeout повинен фізично abort/destroy запит і звільняти ресурси; Promise.race без припинення залишеного запиту недостатньо. Не додавай необмежені retry.

Короткий per-process cache/single-flight інфраструктурного read, наприклад 5 с, допустимий для контролю навантаження. Він не кешує дозвіл admin або cookie й повертається тільки ПІСЛЯ актуального requireAuth/requireAdmin. Запізнілий refresh, збій джерела чи новий handler не оновлює timestamp старого sample. Після невдачі last-known snapshot явно stale; налаштуй й опиши межі віку sample/cache та відновлення. DB lease freshness визначається DB timestamp, не годинником браузера; локальний TTL кешу може використовувати monotonic time.

Метрики per-process cache різних backend можуть мати різний час; панель не обіцяє строго спадний/синхронний CPU-графік. Панельне читання не бере глобальний admission lock, не змінює jobs/registry й не впливає на HPA decisions. Перед завершенням сервера припини нові refresh/timers, фізично закрий видані HTTP-запити й не запускай нові SQL після Pool.end.

6. УКРАЇНСЬКА ПАНЕЛЬ У НАЯВНОМУ UI

Додай зрозумілий пункт «Адміністрування» тільки для актуального admin та можливість повернутися до власних маршрутів. Не переписуй основний layout/auth/jobs UI й не додавай фреймворк. Статичний HTML shell може бути публічним, приватні дані захищає API; не вбудовуй snapshot/secrets у сторінку до авторизації.

Достатня структура: невеликий summary, список/таблиця серверів і виконавців, пагіновані задачі всіх власників із фільтром стану. Показуй зрозумілі Ukrainian назви, читабельні стани/прогрес/час, CPU з одиницями й RAM MiB, поточну job/executedBy; повні UUID доступні без руйнування 360 px layout. Для HPA відокрем бажані/готові сервери, поточний worker busy і джерело метрик. Не називай Ready автоматично вільним виконавцем.

Polling, наприклад раз на 5 с, працює лише коли admin-панель відкрита й дозволена. Один керований цикл, максимум один запит відповідного виду в польоті; ні timer на кожний рядок, ні дублювання циклів після повторного входу/перемикання. Manual refresh, loading/empty/partial/error/stale доступні. За прихованої вкладки/виходу з панелі припини чи обґрунтовано уповільни polling. Зміна фільтра/сторінки не скидає фокус і не застосовує стару відповідь до нового вибору.

Використовуй AbortController і покоління сесії/панелі/запиту. Logout/401/403 втрати admin очищують приватний стан та забороняють запізнілим успішним відповідям відновити його. 503 або збій Kubernetes зберігає останнє коректне представлення тільки з явним попередженням про неактуальність. Дані текстом/textContent, без вставляння неочищеного HTML із логінів/помилок/API.

У 360 px можна мати контрольоване прокручування окремої широкої таблиці чи адаптивні картки; весь viewport не розповзається. Клавіатура, помітний focus, labels, пояснення unknown/stale, відмінність busy/idle/недоступний видимі не лише кольором. Не вигадуй history charts/спарклайни з неіснуючих даних; live snapshot достатній. Панель не виконує пошук маршруту в браузері й не формує фальшивий прогрес.

7. ДЕПЛОЙ ТА ЗБЕРЕЖЕННЯ ПОПЕРЕДНІХ ГАРАНТІЙ

Розшир наявні manifests/config/provision app ServiceAccount/RBAC/Downward API та новою явною compiled міграцією ДО rollout. Образ як і раніше nonroot, compiled runtime, без source/dev tools/operator kubeconfig/секретів у шарах. Нові TS/CLI/SQL файли включені в build/runtime; CLI не починає вимагати Kubernetes для звичайної роботи. Нові monitor-настройки мають явні валідовані межі, безпечний .env.example й працездатний host/npm dev fallback.

HPA й далі володіє replicas, новий/явний stopped bootstrap2, звичайний repeat не скидає 4→2/1. Збережи канонічний last-applied LF, surge0/unavailable1, bounds 2/4/CPU70%, bounded load, stop/HPA deletion/новий port-forward/CA-verified HTTPS readiness. Не змінюй спільний Metrics Server/його TLS лише заради панелі. RBAC конфігурація належить власному namespace/owner; HTTP SA не отримує cluster-admin навіть для «зручної перевірки».

Панель читає саме свій deployment namespace, включно з випадковим test namespace, а не hardcoded demo. Operator kubeconfig залишається тільки в deployment scripts. Test cleanup не видаляє shared metrics add-on чи demo. Неправильні/чужі owner/context, namespace, токени або відповіді провайдера дають явний fail/degraded, без fallback на інший кластер.

8. ОБОВ'ЯЗКОВІ ПЕРЕВІРКИ ДОСТУПУ, ДАНИХ І МЕТРИК

Змістовні unit/controller/parser перевірки:
- Рольовий gate: user/localStorage/spoof header не надають admin; кеш і source provider не читаються перед дозволом. Malformed response/quantities, null/0/stale/partial, request bounds й stop/abort не викликають неконтрольованих promises.
- Mapping pod UID/name/namespace/process UUID і restart: попередня lease не додає ще один live pod, Pending не стає executor, stale метрика не приписується новому контейнеру. Busy/finishing/cancelRequested/expired не змішуються з Ready.
- Client generations: logout/401/role403/зміна фільтра/сторінки/закриття панелі, запізнілий successful response, відсутність повторного polling/фокусу/приватних залишків.
- Absolute budgets/single-flight/cache freshness, фізичне припинення запитів, bounded відповіді; формування безпечних DTO. Не множ тести простим повторенням присвоєних констант.

Справжній PostgreSQL і два незалежні HTTP-процеси:
- Guard TEST_DATABASE_URL незмінний: явна окрема test-БД, перевірені фактичні host/port/database/роль без superuser й випадкова схема; робочі таблиці не очищуються.
- Міграція 001→002→003→004 із збереженими account/session/job/result/registry, repeat/concurrent compiled runner/checksum/readiness. Онови потрібні fixtures/очікування попередніх тестів під нову версію без послаблення їхніх meaningful assertions; SQL 001–003 незмінні.
- Normal user реєструється як user, admin роль надає тільки явний операторський CLI. Перевір unknown username/повтор/невалідну роль без небезпечної зміни. Адмін за однією cookie читає overview/всі jobs через A/B, звичайний user на кожний admin endpoint має 403, без сесії 401; public owner API й далі приховує чужі дані як 404.
- Демотуй свого test admin при активній сесії й прогрітому кеші через інший процес: наступний запит на A/B — 403. Logout/expiry — 401, DB-down — 503. Підвищення ролі через JSON/query/header/клієнтський стан не працює.
- Щонайменше два власники, понад одну сторінку jobs/однакові created_at, фільтри/пагінація/сталі лічильники/real progress, збереження історії після restart. Не генеруй зайві важкі jobs для тестування сторінок: bounded термінальні fixtures в ізольованій test-схемі допустимі, CPU-приклади перевіряються окремо справжніми worker.
- Перевір проекцію всіх outcome/cache/error: жодних хешів/токенів/credentials/claim/raw env/input/result у моніторинговому list. Невідомі/надмірні query відхиляються; читання не чекає admission lock й не дублює N+1.

Реальний Kubernetes/HTTPS/RBAC сценарій у власному тестовому namespace:
1) Підняті app image/явна 004/RBAC/SA/Downward API. Адмін входить через Traefik з Secure cookie; два process instanceId/pod UID коректно зіставлені. Міграційний/worker-контекст не використовує Kubernetes token як env/аргумент.
2) Фактичні pod CPU/RAM timestamp/window у admin API/UI зіставлені з raw Metrics API/kubectl top для тих самих pod/container. Порівнюй однаковий sample/time або поясни різницю sampling/округлення; не вимагай збігу двох незалежних живих вимірів до міліядра.
3) Справжній пошук займає worker: admin бачить відповідну job/owner/progress/executedBy і busy, CPU змінюється за реальною метрикою, HTTP лишається доступним. Після cancel/timeout/terminal slot і таблиця оновлюються; графічний маршрут owner UI не зламаний.
4) Права SA реально перевірені через kubectl auth can-i з конкретною ServiceAccount identity та actual read: потрібні pods/metrics/HPA дозволені, secrets/exec/logs/scale/delete й чужий namespace — заборонені. Не виконуй справжню небезпечну мутацію заради negative test; достатньо правового probe/безпечної відмови.
5) Тимчасово прибери лише необхідне metrics/read право власного app SA в test namespace або іншим вузьким способом виклич реальний provider 403. Shared Metrics Server/HPA/demo не вимикаються. Адмін бачить partial/unknown чи stale з первісним timestamp, звичайні tasks/auth/readiness працюють. Відновлення права повертає свіжі метрики. Provider 403 не підміняється людським logout/роллю.
6) Заміна/рестарт одного власного app pod показує новий process UUID, правильний pod UID/restarts і чесну доступність старого реєстру/метрик. Старий процес не додає фіктивний живий сервер, історія/сеанс збережені. Fault і terminal відповідають справжньому SIGTERM/server_shutdown або SIGKILL/worker_lost, не fake cancel; guard owner/context збережений.

HPA й панель перевір на одному реальному bounded циклі 2→4→2 із наявним load driver та admin observer:
- Чинний тест блоку 8 зберігає строгі proofs: HPA сам створив C/D, обидва мають positive progress→completed власних jobs, максимум 4, реальна queued ETA, один slot/process, не більше одного committed claim, repeat-at-four не скидає replicas, нормальні jobs не failed, cooldown/physical exit/registry exclusion/stop-start.
- Адмін API/UI автоматично показує C/D, фактичні CPU/RAM/джерело/час і всі jobs різних власників; бажані/Pending не видаються за Ready/live, після downscale недоступні записи позначені й не входять до живої місткості. Сесія працює через нові handlers без нового входу.
- Не додавай повторний повний стрес-тест лише заради другого скриншота. Можна доповнити існуючий driver одним окремим test admin без навантажувальних jobs і browser observer; три звичайні load-власники/всі budgets лишаються чинними.
- Додай safe діагностику при transport failure ДО cleanup, не повторюй невизначений POST. Відсутній 202 не зараховується до cancel proof; новий окремий bounded cancel-кандидат не приховує failed/restart. Невідтворений reset із блоку 8 не оголошується виправленим заднім числом.

Chrome: звичайний user не отримує панельних даних навіть прямим API, admin бачить summary/сервери/метрики/всі owner jobs, фільтр/пагінацію/refresh, partial/stale/RBAC-recovery, role403/logout/401 та очищення після запізнілих відповідей. Desktop/360 px/клавіатура, немає console/resource/mixed-content/viewport overflow. Фактично оглянь PNG server/job/partial/нові HPA executors. Внутрішні PNG не комітити/не публікувати; HTTP не називати візуальним прийманням.

Регресія: npm ci, typecheck/build, повний npm test (до змін 183 = 134 non-DB + 49 PG), TS/built CLI; нові осмислені тести додаються зверху. Повтори container/static deployment/HTTPS сценарії для зміненого app image/schema/SA/provision, збережи попередні assertions про runtime, міграції, auth/ownership/квоти/worker/cancel/SIGTERM/SIGKILL/PVC/stop. Статичний режим лишається autoscaling:false/2, HPA — окремий. Старі local Chrome-групи повтори для зміненого auth/client; не видавай історичний результат за новий pass. Великий benchmark незмінного алгоритму не повторюй.
