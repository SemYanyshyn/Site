# Courier Route — план проєкту

## Постановка задачі

Навчальний вебзастосунок знаходить короткий маршрут одного кур'єра на координатній площині: старт зі складу, відвідування кожної точки доставки та повернення на склад. Результат міститиме порядок відвідування, сумарну евклідову довжину й схему маршруту. Координати та одиниці довжини умовні; це не кілометри й не дорожня навігація.

Обрано ітеративний наближений пошук. Застосунок показуватиме найкращий знайдений маршрут без твердження про доведену глобальну оптимальність. Трудомісткість визначатимуть кількість точок та обмежений обсяг реального пошуку. Штучні затримки для імітації роботи заборонені.

Джерело вимог викладача — [docs/assignment.txt](docs/assignment.txt). У погоджений обсяг входять усі пункти 1–8 та HTTPS, включно з пунктами за додаткові бали. Проєктні рішення, зокрема межа масштабування у 4 екземпляри, не є числами з оригінального завдання.

Інтерфейс та інструкції користувача — українською; внутрішні ідентифікатори коду — англійською. Не додаємо реальні дороги, GPS, геокодування, адреси клієнтів, облік доставок, CRM, склад запчастин, оплату, сповіщення, AI-функції чи порівняння багатьох алгоритмів.

## Погоджений стек

| Частина | Рішення |
| --- | --- |
| Мова | TypeScript зі strict-перевіркою типів |
| Сервер | Підтримувана LTS-гілка Node.js, Express |
| Клієнт | HTML, CSS, TypeScript; Vite для розробки та збирання; без UI-фреймворків |
| Важкі обчислення | Node.js `worker_threads`, починаючи з блоку 3 |
| База даних і спільна черга | PostgreSQL; доступ із Node.js через `pg` |
| HTTPS і балансування | Traefik, починаючи з блоку 7 |
| Розгортання та масштабування | Docker, Kubernetes, Metrics Server, HPA |
| Залежності | npm та відстежуваний `package-lock.json` |

Заміна на C#, Bun, Deno, Python, Next.js, NestJS чи інший стек потребує окремого рішення керівника проєкту. Конкретні сумісні версії інструментів каркаса фіксуються в `package.json`, lock-файлі та README за результатами перевірки середовища.

## Архітектура і межі блоків

У блоці 1 створено один невеликий npm-проєкт із `src/server`, `src/client` і `src/shared`. Express надає `GET /api/health`; Vite проксіює `/api` в режимі розробки; зібраний клієнт та API віддає один Express-процес з одного походження. Health означає доступність процесу й не засвідчує готовності БД. У блоці 1 не було SQL-схем, Dockerfile, Kubernetes-маніфестів, авторизації, worker threads або алгоритму маршруту.

Блок 2 додає PostgreSQL як спільне джерело користувачів і сесій: `users`, `sessions`, облік SQL-міграцій; явний runner із транзакціями та advisory lock; асинхронний scrypt паролів; непрозора HttpOnly-cookie, хеш токена в БД, перевірка строку й відкликання сесії. Реєстрація, вхід, `/me` і вихід працюють через відносні API. `GET /api/ready` окремо перевіряє доступність БД та необхідної схеми. Виконавець пройшов 11 unit і 13 справжніх інтеграційних перевірок; два незалежні HTTP-процеси підтвердили спільність сесій. Керівник прийняв блок після перегляду коду та повторних доступних перевірок, включно з усіма 11 unit; 13 DB-сценаріїв він незалежно не повторював через відсутність придатного PostgreSQL. Балансувальник і обчислення на двох серверах цим не реалізовані. Схеми задач додано згодом у блоці 4.

Блок 3 реалізує внутрішній обчислювальний сервіс: runtime-валідацію, початковий маршрут найближчим сусідом, simulated annealing з 2-opt, детермінований seed, обмежені матрицю/бюджет та окремий worker. У `startServer` створюється один спільний executor; одночасний другий запуск отримує `executor_busy`, локальної черги немає. Важка підготовка й пошук виконуються у worker без DB URL, паролів або cookie (`env: {}`, `execArgv: []`). Прогрес містить фактичні лічильники та етапи; timeout/cancel реально припиняють потік і чекають його завершення перед звільненням слота. Shutdown HTTP-процесу включає executor. TS/built CLI та benchmark працюють без доступу до БД. Остаточні результати перевірок і виміри фіксуються у [docs/block-03-report.md](docs/block-03-report.md).

Початкові проєктні ліміти блоку 3: 500 доставок, 50000000 справжніх спроб та 30000 мс. Конфігураційні стелі: 2000 / 200000000 / 120000 мс; модуль координат ≤1000000. Матриця має `8 × (N+1)²` байтів, до 32032008 байтів при стелі N=2000; інші структури й runtime потребують додаткової пам'яті. Числа не походять із вимог викладача. Обмеження перевіряються до створення worker та копіювання надмірного масиву. На завершення блоку 3 це були внутрішні сервісні функції; HTTP-застосування додається в блоці 4, клієнтський UI — у блоці 5.

Блок 4 додає одну таблицю jobs та API власника; PostgreSQL є джерелом історії, станів, прогресу й cancel. Admission використовує спільний advisory transaction lock і READ COMMITTED, claim — коротку транзакцію FOR UPDATE SKIP LOCKED. Один dispatcher використовує наявний executor, зберігає один claim до terminal та не створює локальної черги. Базові ліміти: 3 active задачі власника, 100 outstanding системи, poll 250 мс; active/outstanding — queued+running, включно з очікуванням фізичного cancel. Після збереженого timeout діє фактичний recovery grace `max(configuredGrace, 2×poll + 21000)` мс; за стандартної конфігурації — 21500 мс. Готові результати фіналізуються відразу; recovery будь-якого процесу після deadline завершує втрату як worker_lost без повторного обчислення. Звичайна зупинка сервера — server_shutdown, SQL-відмова — database_unavailable; прийнятий cancel має пріоритет при нормальній фіналізації.

Блок 5 додає українську форму координат із перевіркою фактичних серверних лімітів, активні задачі, пагіновану історію, деталі, реальний прогрес і запит скасування. Один керований цикл читання використовує відносні API; AbortController та покоління сеансу/вибору захищають від запізнілих відповідей. SVG і текстовий порядок будуються лише з перевірених збережених completed input/result. Клієнт не повторює пошук. Реалізація та результати перевірок фіксуються у [docs/block-05-report.md](docs/block-05-report.md).

Подальша цільова схема: клієнт → Traefik з HTTPS → щонайменше два однакові серверні екземпляри → PostgreSQL. Кожен сервер обслуговує HTTP та виконує щонайбільше одну важку задачу у worker thread. База є спільним джерелом стану для всіх серверів; балансування не потребує прив'язки сесії до одного екземпляра.

Наступні обмеження обов'язкові для відповідних блоків; фактичний стан їхніх частин наведено в матриці:

1. За балансувальником працюють щонайменше два однакові серверні екземпляри, які реально виконують різні обчислювальні задачі. Два потоки одного процесу не замінюють два серверні екземпляри.
2. Один серверний екземпляр одночасно виконує одну важку задачу у worker thread та продовжує відповідати на HTTP-запити.
3. PostgreSQL централізовано зберігає користувачів, сесії, вхідні дані задач, чергу, статуси, прогрес, запити скасування й результати. Авторизація та керування задачею працюють через будь-який серверний екземпляр.
4. Призначення задачі виконавцю атомарне: два сервери не можуть почати одну задачу одночасно. У блоці 4 реалізовано короткі транзакції PostgreSQL з FOR UPDATE SKIP LOCKED та приватним claim token. Локальні лічильники окремих серверів не забезпечують глобальні ліміти.
5. Стани задач: `queued`, `running`, `completed`, `cancelled`, `failed`. Скасування реально зупиняє обчислення та звільняє виконавця. Перевищення часу зупиняє роботу і переводить задачу у `failed` з причиною `timeout`.
6. Ліміти розміру задачі, обсягу пошуку, часу виконання, незавершених задач користувача та загальної черги конфігуровані. Ліміти однієї обчислювальної задачі реалізуються й перевіряються вимірами у блоці 3; глобальні ліміти кількості та черги — у блоках 4/6. Припущення не видаються за числа оригінального завдання.
7. Приблизне очікування черги оцінюється за розміром задач, кількістю доступних виконавців і виміряною тривалістю. Прогрес відображає фактичну роботу.
8. Для демонстрації HPA обрано мінімум 2 та максимум 4 серверних екземпляри. Межа 4 — проєктне рішення. Нові екземпляри мають реально запускатися та виконувати задачі.
9. Адміністратор бачить усі серверні екземпляри, активних обчислювальних виконавців і задачі, прогрес, чергу та фактичне використання CPU й пам'яті.

Блок 1 прийнято після встановлення залежностей, перевірки типів, збирання, production/dev HTTP, документації та змістовних комітів. Критерії його завершення: typecheck/build; змістовні `node:test` алгоритму й executor; запуск TS та зібраного worker без вихідних `.ts`; справжні скасування, timeout і аварії з відновленням слота; HTTP health-відповіді саме під час pending пошуку в worker того самого процесу; SIGINT/SIGTERM з активним worker; регресія 11 unit і 13 PostgreSQL integration-сценаріїв на окремій тестовій БД; обмежений benchmark малого/середнього/важкого входів із реальними CPU/часом/прогресом/пам'яттю.

Доступна браузерна перевірка виконується окремо від HTTP; якщо вона недоступна, це прямо фіксується у звіті. Заблоковані перевірки не позначаються успішними. Непотрібні тимчасові процеси та worker після перевірок зупиняються; стан окремого PostgreSQL та команди керування записуються у звіті. Явне завдання дозволило тільки блок 8; після нього робота зупиняється перед блоком 9.

## Постійний процес Git для всіх блоків

Повні обов'язкові правила наведені в [AGENTS.md](AGENTS.md), розділ «Git і змістовні коміти». Це організаційна вимога користувача для всіх блоків і виправлень, а не окрема продуктова вимога викладача.

- Перед ініціалізацією перевірити фактичний Git-корінь, гілку, status та історію. Для нового власного репозиторію — `git init -b main`; наявну історію зберігати. Remote і push без окремого доручення не налаштовувати.
- Використовувати справжні налаштовані `user.name` і `user.email`. Не вигадувати ідентичність і не змінювати глобальний Git. За відсутності ідентичності завершувати незалежну роботу та чесно фіксувати блокування комітів.
- Робити регулярні коміти завершених логічних змін. Кожен коміт має один пов'язаний зміст, короткий англійський заголовок `type(scope): description` (scope необов'язковий), орієнтир до 72 символів.
- Перед комітом перевіряти `git status`, звичайний і підготовлений diff та доречні перевірки. Для коду обов'язкові `npm run typecheck`, `npm run build` і перевірки зміненої поведінки; для авторизації/БД — змістовні unit та integration перевірки на справжній окремій тестовій БД; у блоці 3 — алгоритм/executor/HTTP, TS/built та регресія auth. Документаційний коміт не потребує повторення перевірок незмінного коду. Відомі помилки не комітити; заблоковані перевірки явно фіксувати. Дослівний `docs/assignment.txt` не форматувати.
- Підготувати `.gitignore` до першого коміту та доповнювати перед створенням локальних даних. Не комітити `node_modules`, `dist`, тимчасові логи, локальні `.env`, PostgreSQL-кластери/дані, cookie-файли, дампи чи секрети; відстежувати lock-файл, безпечний `.env.example`, SQL-міграції та тести. Додавати файли вибірково, не захоплюючи сторонні зміни.
- Не переписувати історію та не відкидати сторонні зміни. Помилку після коміту виправляти окремим перевіреним `fix`-комітом.
- На завершення кожного завдання звітувати про створені коміти з короткими хешами й назвами, активну гілку та остаточний `git status --short`. Власні завершені зміни мають бути закомічені; залишені зміни пояснити. У звіті можна вказати відомі попередні хеші, а хеш фінального коміту зі звітом — у чаті, без циклу комітів заради власного хешу.
