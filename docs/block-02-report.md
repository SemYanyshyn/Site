## 3. Міграції та схема

`migrations/001_auth.sql` створює:

- `users`: UUID, логін, унікальний `normalized_username`, версійований `password_hash`, роль `user/admin`, `created_at timestamptz`; ASCII-перевірка логіна й узгодженість нормалізованої форми.
- `sessions`: SHA-256 токена як первинний ключ, FK користувача з каскадним видаленням, `created_at`/`expires_at timestamptz`, обмеження порядку часу; індекси `user_id` та `expires_at`.
- Runner веде `schema_migrations(version, checksum, applied_at)`.

Кожна нова міграція й запис її версії застосовуються в одній транзакції через один отриманий client. На цьому ж client протягом усього запуску утримується advisory lock; release виконується у `finally`. Повторний запуск пропускає вже застосовану версію; змінена контрольна сума зупиняє runner. Одночасні runner не дублюють міграцію. HTTP не запускає міграції автоматично.

Зібраний runner читає SQL з `dist/migrations`. Його додатково перевірено в тимчасовому артефакті лише з `dist`, package metadata й установленими залежностями, без вихідних SQL. Налаштування/міграції не використовують DROP/TRUNCATE робочої БД. Інтеграційні тести видаляють лише власну випадкову схему в перевіреній тестовій БД.

## 4. API та модель авторизації

| Маршрут | Фактичний контракт |
| --- | --- |
| `GET /api/health` | 200, `status: "ok"`, стабільний протягом процесу `instanceId`; незалежний від БД |
| `GET /api/ready` | 200 лише за доступної БД, потрібних версій міграцій та таблиць/колонок; інакше 503 |
| `POST /api/auth/register` | 201 `{ user }`, без автоматичного входу; 409 при конфлікті нормалізованого логіна |
| `POST /api/auth/login` | 200 `{ user }` та нова cookie; однакові 401 для невідомого користувача й неправильного пароля |
| `GET /api/auth/me` | 200 `{ user }` з чинною сесією; 401 без неї; `Cache-Control: no-store` |
| `POST /api/auth/logout` | Порожній JSON-об’єкт у запиті, 204 без тіла у відповіді; відкликання сесії й очищення cookie; повтор безпечний |

Безпечний користувач містить лише `id`, `username`, `role`, `createdAt`. Роль береться з БД; публічна реєстрація створює лише `user`. Надмірні поля, зокрема `role`, відхиляються.

Логін: після обрізання крайніх пробілів 3–32 ASCII-літери/цифри/`_`/`-`, потім приведення до нижнього регістру. Пароль: 15–128 коректних Unicode-кодових точок, без trim, зміни регістру, нормалізації чи скорочення. Клієнт і сервер використовують одну runtime-валідацію.

Паролі: асинхронний `node:crypto.scrypt`, N=32768, r=8, p=3, maxmem=64 MiB, окрема випадкова 16-байтова сіль і 64-байтовий ключ; параметри та версія збережені у форматі хешу. Перевірка використовує `timingSafeEqual` для буферів однакової довжини.

Сесія: випадковий токен із 32 байтів передається лише в `courier_session` cookie; у PostgreSQL зберігається його SHA-256. Cookie: `Path=/`, `HttpOnly`, `SameSite=Lax`, узгоджені `Max-Age/Expires`, без Domain; `Secure` керується `COOKIE_SECURE`. Строк за замовчуванням 28800 секунд, допустимо 1–604800. Час завершення визначає PostgreSQL. Кожен захищений запит перевіряє БД та строк; успішний повторний вхід транзакційно відкликає надіслану попередню сесію. Прострочені записи очищуються при успішному вході. Локального джерела чинності сесій немає.

Для auth-POST потрібні `application/json`, тіло не більше 16 KiB та точний нормалізований Origin із явного `APP_ORIGINS`. Відсутній/`null`/чужий Origin — 403; тип вмісту — 415; погані дані/JSON — 400; надмірне тіло — 413. Помилки мають стабільні `code` й українське `message`, без секретів, SQL чи stack trace. PostgreSQL-пул: максимум 5 з’єднань на процес, connect timeout 2 с, SQL timeout 2,5 с, query timeout 3 с, idle timeout 30 с. Завершення HTTP і пулу обмежено 5 с.

## 9. Доказ спільної сесії

Фінальний запуск мав різні процеси та ідентифікатори:

- A: `cda906da-51ec-4317-b3d5-89ea61d8f333`.
- B: `84ab4a0e-632e-4c3b-bb9e-528ff14ce5b9`.

Успішний вхід через A створив серверну сесію; передавання тієї самої cookie до B повернуло того самого користувача (200). Вихід через B відкликав запис (204), після чого та сама cookie через A дала 401. Значення cookie й хешів не логувалися. Це перевірка двох незалежних HTTP-процесів, а не двох app-об’єктів.

## 10. Перезапуски та недоступна БД

Інтеграція перевірила збереження користувача й чинної сесії після повного перезапуску HTTP-процесу.
