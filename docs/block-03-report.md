## 2. Алгоритм, точність і складність

Спочатку будується симетрична матриця евклідових відстаней через `Math.hypot`, без округлення. Найближчий сусід зі стабільним вибором за індексом утворює допустимий замкнутий маршрут. Далі власна TypeScript-реалізація simulated annealing розглядає реальні 2-opt розвороти лише доставок. Склад залишається на обох кінцях. Повний розворот усіх доставок, який змінює тільки напрям обходу, замінюється належним сегментом.

Непогіршення приймаються; додатна дельта — з імовірністю `exp(-delta/T)`. Розклад геометричний: `T0 = initialLength/(N+1) × 0.25`, `Tend = T0 × 0.0001`, множник `exp(log(Tend/T0)/iterations)`; є нижня межа `Number.MIN_VALUE`. PRNG Mulberry32 має власний 32-бітовий стан, зокрема коректний seed `0`. Пошук не користується глобальним `Math.random`.

Поточний і найкращий маршрути зберігаються окремо. Перед збереженням нового best довжина перераховується компенсованим сумуванням; додатковий перерахунок виконується кожні 32768 спроб або 2048 прийнятих змін. Фінальна довжина обчислюється за фактичним `order`, а executor незалежно перевіряє перестановку, лічильники й довжину. Допуск executor: `EPSILON × max(length, initialLength) × max(16, 8N) + MIN_VALUE × N`. Накопичена сума дельт не видається за перевірений best.

Звичайний пошук виконує весь дозволений бюджет; відсутність покращень не є причиною зупинки. Для 1–2 доставок і нульової довжини повертається коректний маршрут із 0 реальних ітерацій та явною причиною. Однакові нормалізований вхід, seed і завершений бюджет дають однакові `order`/`length`; час і кількість проміжних повідомлень можуть відрізнятися. Результат — **найкращий знайдений маршрут**, без доказу глобальної оптимальності.

Для N доставок матриця й найближчий сусід потребують `O(N²)` підготовки; дельта спроби — `O(1)`, прийнятий розворот сегмента — `O(k)`, точний перерахунок/копіювання — `O(N)`. Найгірша загальна оцінка для I спроб — `O(N² + I×N)`. Пам'ять матриці — `8(N+1)²` байтів, маршрутів та індексів — `O(N)`.

Як технічну довідку звірено [TSP](https://developers.google.com/optimization/routing/tsp) і [пошукові межі та simulated annealing](https://developers.google.com/optimization/routing/routing_options). OR-Tools не встановлювався; production-алгоритм написано в цьому проєкті.

## 3. Фактичні контракти

`src/shared/route.ts` містить:

```ts
RouteInput = {
  warehouse: { x: number; y: number };
  points: Array<{ x: number; y: number }>;
  iterations: number;
  seed?: number;
}
```

Склад має індекс 0, доставки — `1..N` за початковим порядком масиву. Збіг координат не об'єднує доставки. До створення worker відхиляються зайві/відсутні поля, нечислові й нескінченні координати, надмірні розмір/бюджет, дробові лічильники, непридатний seed, пропуски масиву й accessor-поля. Надмірна довжина масиву перевіряється до огляду елементів, копіювання та матриці. Помилки `invalid_input` мають конкретне українське повідомлення. Вхідні об'єкти не змінюються.

Нормалізація копіює перевірені координати та завжди містить `seed`: якщо його немає, сервер генерує uint32 через `crypto.randomBytes`. Це зерно повертається у результаті; block 4 надалі має зберігати саме нормалізований вхід.

`RouteResult` містить `order: [0, ..., 0]`, `length`, `initialLength`, `seed`, `iterationsRequested`, `iterationsCompleted`, виміряний у worker `elapsedMs`, `approximate: true`, `terminationReason: budget_exhausted | trivial_input | zero_length`.

`RouteProgress` містить `stage: preparing | searching | finishing`, `completedIterations`, `totalIterations`, `percent`. Події пошуку обмежені приблизно 150 мс, перевірка годинника відбувається кожні 1024 спроби. Лічильники й відсоток монотонні; до перевіреного успіху `<100`. Термінальні стани `RouteOutcome`: `completed` із result, `cancelled`, `failed` із reason `timeout | worker_error` та українським message. Timeout не повертає частковий маршрут як completed. На один запуск припадає один кінцевий результат.

Внутрішній `start()` синхронно повертає `{ runId, threadId, result: Promise<RouteOutcome> }`. Це сервісний контракт, не новий HTTP API.

## 4. Кінцеві ліміти

| Параметр | За замовчуванням | Допустима серверна конфігурація |
| --- | ---: | ---: |
| `ROUTE_MAX_POINTS` | 500 доставок | 1–2000 |
| `ROUTE_MAX_ITERATIONS` | 50000000 спроб | 1–200000000 |
| `ROUTE_TIMEOUT_MS` | 30000 мс | 1–120000 мс |
| Модуль координати | 1000000 | Константа; не підвищується з JSON |
| Seed | Генерується за відсутності | 0–4294967295 включно |

Конфігурація приймає додатні цілі десяткові значення й перевіряє жорсткі стелі. JSON не може підвищувати жоден максимум. Мінімум — одна доставка; iterations — додатне безпечне ціле.

Матриця при 500 доставках займає 2008008 байтів, при конфігураційній стелі 2000 — 32032008 байтів; це лише матриця, не RSS. На Apple M5 стандартний важкий набір 500/50 млн завершився приблизно за 1,09 с, виміряний максимум RSS процесу — 81313792 байти. Значення 500/50 млн/30 с залишені без підвищення. Стелі обмежують випадкове надмірне налаштування; вони не гарантують завершення будь-якого дозволеного входу на повільній машині — тоді діє timeout.

Щоб отримати кілька секунд реального пошуку на цій машині, benchmark окремо запущений із серверним `ROUTE_MAX_ITERATIONS=200000000` у межах жорсткої стелі. Він виконав усі 200 млн спроб за 4,33 с. Зміна діє лише для цього процесу, не переписує `.env` і не підвищує стандартну межу HTTP-сервера. Штучних затримок, порожніх циклів чи повторів готового розрахунку немає.

## 6. Worker, зайнятість і завершення

`startServer` створює рівно один спільний executor для HTTP-процесу. Busy встановлюється синхронно до створення Worker; конкурентний start отримує `executor_busy`, другого worker і локальної черги немає. Матриця, найближчий сусід і пошук виконуються у справжньому окремому thread.

У TS-режимі `dev-worker.mjs` явно реєструє `tsx/esm/api` та імпортує `worker.ts`; у build запускається `worker.js`. Шляхи обчислюються від модуля, не cwd. Worker отримує лише runId/нормалізований вхід, `env: {}` і `execArgv: []`; DB URL, паролі, cookie та preload батьківського процесу не успадковуються. У worker немає pg або DB-конфігурації.

Батьківський `performance.now()` контролює повний час від створення worker через підготовку, пошук, перевірку результату до фактичного exit. При cancel/timeout викликається `worker.terminate()`, а слот і Promise звільняються після справжнього exit/завершення terminate. Граничний час включає запуск, а `result.elapsedMs` вимірює алгоритм усередині worker. Семантика terminate/exit звірена з [документацією Node.js 24](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html#workerterminate).

Перше рішення про зупинку зберігається; повторний cancel, старий runId та пізні повідомлення не замінюють результат. Кандидат на успіх перевіряється незалежно, а 100% надходить лише після його перевірки й exit з кодом 0. Таймери, listeners і callback очищуються. Синхронна помилка або відхилений Promise споживача прогресу ізольовані від executor.

Shutdown одночасно закриває прийом HTTP і викликає executor.shutdown, потім закриває pg.Pool. Повторне завершення безпечне; після shutdown нові задачі відхиляються. Граничне завершення процесу — 5 секунд.

## 9. HTTP саме під час pending пошуку

`tests/fixtures/route-http-harness.ts` імпортує production `startServer` й запускає його executor у **тому самому процесі**, з реальним Worker threadId>0. Старт перевіряється за `searching` із completedIterations>0. Тест через IPC звіряє PID, pending=true, busy=true та реальні лічильники до і після кожної HTTP-відповіді.

П'ять справжніх `/api/health` повернули 200 за **16,80; 1,98; 1,87; 1,80; 1,62 мс**. Для всіх п'яти відповідей Promise обчислення ще pending; жоден terminal не надійшов до закінчення вимірів. Це не обчислення в незалежному сусідньому процесі. Harness має закритий PostgreSQL loopback-порт: liveness не вимагає БД, успішну авторизацію не імітовано. Тестових production HTTP-маршрутів немає.

## 10. Доказ зупинки й відновлення

Executor-тести утримують посилання на справжні Worker й перевіряють `threadId === -1` до визнання завершення та наступного запуску. Після completed, cancel, timeout, crash/exit/invalid result і помилки конструктора наступна коротка реальна задача успішно завершується.

Скасування виконується після події пошуку з додатним лічильником, дає рівно один cancelled, не надсилає 100%, не приймає пізній прогрес та звільняє слот лише після зупинки. Перевірені раннє/повторне скасування, старий runId, cancel після completed і синхронний busy без створення другого worker. Помилки синхронного й async callback прогресу не залишають незавершений Promise.

Короткий серверний timeout **1000 мс** реально перервав пошук після виконаних ітерацій: failed/timeout, threadId=-1, успішний наступний запуск; тест із відновленням тривав 1023,485 мс. Аварійні fixtures використані лише для error paths; успіх/cancel/timeout запускають production-алгоритм.

SIGINT і SIGTERM надіслані процесам зі справжнім активним worker: відповідно **7,60 мс** та **7,15 мс** до підтвердженого завершення. Обидва процеси вийшли з кодом 0, активна задача дала один cancelled, busy=false, HTTP більше не відповідав. П'ятисекундний shutdown не чекав стандартних 30 секунд задачі.
