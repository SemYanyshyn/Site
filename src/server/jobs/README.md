# Збережені задачі й черга

Тут керую життям задачі від приймання до кінцевого результату

Для себе читаю цей шлях так: router → repository → PostgreSQL → dispatcher → RouteExecutor → worker → repository

`queued` означає очікування, `running` — виконання, а `completed`, `failed`, `cancelled` — кінцеві стани

Claim — це атомарне захоплення задачі сервером, а приватний claim token захищає записи від застарілого виконавця

Реєстр показує живі процеси та зайнятість їхніх слотів, прогноз черги оцінює час до старту без гарантії точного моменту

## Моя мапа файлів

- [`config.ts`](config.ts) — задаю місткість черги, особистий ліміт задач і частоту її перевірки
- [`executor-config.ts`](executor-config.ts) — налаштовую heartbeat і TTL запису виконавця у спільному реєстрі
- [`executor-registry.ts`](executor-registry.ts) — повідомляю PostgreSQL, що процес живий і має один обчислювальний слот
- [`router.ts`](router.ts) — описую API задач для авторизованого користувача
- [`repository.ts`](repository.ts) — зосереджую SQL для створення, читання, виконання та скасування задач
- [`dispatcher.ts`](dispatcher.ts) — з’єдную спільну чергу PostgreSQL з одним локальним RouteExecutor
- [`queue-snapshot.ts`](queue-snapshot.ts) — читаю узгоджений набір даних для прогнозу часу очікування queued-задачі
- [`queue-estimator.ts`](queue-estimator.ts) — приблизно оцінюю час до початку задачі, не звертаючись до мережі чи PostgreSQL

Докладні пояснення основних блоків залишаю безпосередньо в коментарях відповідних файлів
