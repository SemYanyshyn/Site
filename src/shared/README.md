# Як я використовую shared

Тут тримаю спільну мову frontend і backend — формати даних та невеликі перевірки без залежності від Express, PostgreSQL чи DOM

Інтерфейси й типи допомагають TypeScript знайти помилки під час розробки, але після компіляції зникають і самі не перевіряють JSON

Функції перевірки та константи залишаються у JavaScript, тому можуть виконуватися і на сервері, і в браузері

## Моя мапа файлів

- [auth.ts](auth.ts) — публічний користувач, дані входу, формат помилки та перевірка логіна й пароля
- [health.ts](health.ts) — відповідь живого HTTP-процесу без підтвердження готовності бази
- [route.ts](route.ts) — координати, вхід, обмеження, прогрес і результат розрахунку маршруту
- [jobs.ts](jobs.ts) — збережені задачі, історія, стани, прогноз черги й серверні ліміти
- [admin.ts](admin.ts) — адміністративний огляд задач, виконавців, pod, метрик і HPA
- [public-api.ts](public-api.ts) — перевірка публічної HTTPS-адреси API для клієнтської збірки

## Що собі запам’ятовую

- `interface` описує поля об’єкта, `type` також дозволяє перелічити кілька варіантів значення
- `extends` додає поля до іншого інтерфейсу або уточнює їх
- Знак `?` після назви поля означає, що воно може бути відсутнє
- `null` — явне значення відсутності або невідомості, воно не дорівнює нулю
- `unknown` змушує мене перевірити зовнішні дані перед використанням
- Поле `status` або `ok` допомагає розрізняти варіанти відповіді й доступні в кожному з них поля
- Сам факт спільного типу не надає прав доступу, сервер усе одно перевіряє сесію, роль і власника задачі
- Усе, що імпортує frontend, може потрапити в публічну збірку, тому секретів тут не зберігаю
